# The dashboard

## 1. Purpose

The dashboard is where all three audiences meet Sekhemet. For **developers** it is a board that reads like Jira, Linear or GitHub Projects and a review instrument that gets a decision in under a minute. For **beginners** it teaches the practice where it happens, through a Learn layer they can switch off. For **non-developers** it is a status page in plain words and a conversation with the project manager that can start a project — without a terminal. For a **team** sharing one install it adds sign-in, the Projects page, an inbox and the pages an Admin needs ([teams](teams.md), [DEC-35](../DECISIONS.md#dec-35--one-product-two-setups-solo-and-team)). It serves the spine by making **the human the rate limiter** visible (Review WIP, back-pressure, *Needs you*) and by never letting the interface claim more than the evidence says. Behaviour behind the views lives in [planner-pm](planner-pm.md), [review-git](review-git.md), [design-stage](design-stage.md) and [integrations](integrations.md); the HTTP API is [runtime](runtime.md); PM shapes are [PM_CONTRACT](../PM_CONTRACT.md).

## 2. Behaviour

### 2.1 Stance

1. Every screen answers, in order: **What needs me? Can I trust it? What do I do?** That order sets the navigation, the default route and the hierarchy inside each view.
2. **State is colour; everything else is neutral.** Colour is reserved for the five state roles, and each is paired with an icon and words. Colour is never the only signal.
3. **Density over whitespace, evidence first, keyboard-complete, both themes first-class** (Basalt dark is the default; Sand light is tuned, not inverted). The theme is a choice kept per browser, made in the account menu (§2.2.6): *Dark* (Basalt), *Light* (Sand) or *System*, which follows the operating system's `prefers-color-scheme`; otherwise the operating system does not pick it.
4. **Sentence case everywhere**; no all-caps letter-spaced labels. **Gold (`--accent`) appears in exactly four places**: the primary action (Accept), the active-nav indicator, the focus ring and the brand glyph.
5. **Every number has a unit and a basis** ("8 of 40 steps", "waiting 12m", "16.8k tokens in"). **Nothing is generic**: empty states say what a view is for and what fills it; errors say what failed, why, and what to do.
6. **Nothing the interface says outruns the evidence**: an empty gate contract, an altered ledger, a gate that did not run, a requirement whose tests pass without meeting their strength rule are shown as such. No model's confidence, and no model's claim that work is complete, is ever displayed.

| More (collapsible) | **Runs** `#/runs` · `g u`; **Dependencies** `#/graph` · `g d`; **Playbook** `#/playbook` · `g k`; **Integrations** `#/integrations` · `g n`; **Machine** `#/machine` · `g m`; **Ledger** `#/ledger` · `g l` | Runs: after the first completed run.    A view with nothing in it is **hidden, not empty**; the sidebar never shows a dead link. Items that count something show a count badge (Inbox: unread; Review: cards waiting; Playbook: rules awaiting approval). **Inbox is a page again** (superseded by [DEC-35](../DECISIONS.md#dec-35--one-product-two-setups-solo-and-team), which reverses the earlier merge into Review): it lists what reached the person across projects, grouped by reason (§2.17.2); Review › *Needs you* stays the project's queue of decisions, and an Inbox *Needs you* item opens there. **Projects** replaces the Workspace rollup, and `#/workspace` opens it (§2.11). Machine and Ledger move from the old System footer menu into More; Theme and Keys move into the account menu. Pages reached only from the account menu (Profile, Notifications, Members, Audit) are in the palette and have no chord. **Registry** and **Settings** are merged into **Configuration** (§2.16): `#/registry` opens its Benchmark section and `#/settings` its This browser section.
2. **Widths.** ≥ 1280 px: sidebar 216 px. 1024–1279 px: a 176 px sidebar that **keeps its labels** (no icon-only rail; the `--rail-w` token is retired). < 768 px: no sidebar; a **bottom tab bar — Status · Review · Board · PM** — with 48 px targets. Topbar 44 px (16 px padding, 12 px gaps): view title, crumb, scope filters, ⌘K, live status.
3. **Status at the bottom of the sidebar**, text plus one dot: the **Agent status line** — the Agent's state in one line (*Agent working on CHR-12 · step 14 of 40*, *Agent idle*, *Worker paused after step 5 while Seshat replies*, lapis, while it is), with the queue in the Team setup (*2nd in queue, about 6 minutes*, [teams](teams.md) item 31); under it, in 11 px secondary, *Live* / *Reconnecting…* / *Offline since 14:42*, *Ledger intact · 236 entries* and memory. Who you are is the account menu (§2.2.6), not a footer line (superseded by DEC-35). Memory turns amber only when it changes behaviour (a pause is imminent or active), never as a permanent state.
4. **Shell bars** (one at a time, priority: ledger altered > offline > no Worker model > memory pause > review full > Worker paused for Seshat), each 32 px under the topbar:

| State | Trigger | Treatment |
| --- | --- | --- |
| Loading | Before the first board response | Skeleton of the real geometry, no spinner; after 3 s *Connecting to Sekhemet…* |
| Reconnecting | Stream error | Amber dot; content stays; actions enabled for 10 s |
| Offline | No stream for > 10 s and `/api/meta` fails | A full-width 32 px bar under the topbar in `--bg-raised` with a 1 px `--state-parked` bottom border: **Offline since 14:42:30.** *Showing the last known state. Actions are disabled.* `Retry`. Every triage button is disabled with the reason *Offline* beside it; timestamps freeze (they don't count up) |
| Read-only | `meta.triage === false` | Triage replaced by one line: **Read-only.** *This server was started without triage. Restart with `sekhemet serve` to accept or send back.* `a/r/p` show the same line as a toast |
| Review full | `backpressureActive` | **Review is full (3 of 3).** *Finished cards wait until you clear one.* `Open review` |
| No Worker model | The Worker role has no assigned model that fits this machine | **No model is set up for the Worker yet.** *Sekhemet can plan and show the board, but nothing is built until the Worker has a model.* `Set up models` (opens Configuration › Models) |
| Memory pause | Level critical, or the last stop was `memory_pressure` | **Paused for memory: 94% used.** *Sekhemet stopped the Worker safely before the system would swap. Work resumes below 85%.* `Machine`; the running tile flips to *Paused for memory* |
| Ledger altered | Chain verification fails | Red, not dismissible: **Ledger altered at entry #7.** *An entry no longer matches its hash. Stop and inspect before accepting anything.* `Open ledger`. Accept is disabled everywhere with that reason |
| Worker paused for Seshat | `PmStatus.workerPaused` | **Worker paused after step 5 while Seshat replies.** `Open Seshat`. Lapis rule, not amber: nothing is wrong |

5. **First run and default route.** The first visit asks one question: *I write code · I manage the work · I'm learning*. It sets the default route and the Learn default — *I write code*: Review when its queue is non-empty, else Board, Learn off; *I manage the work*: Status, Learn off; *I'm learning*: Board, Learn on; the answer is kept per browser and changeable in Configuration › Preferences (DEC-31: *Preferences*, never "This browser"). The question is a bar above the view that blocks nothing and takes no focus, with *Not now* beside the three answers; answering on the page the dashboard opened on takes the person to that answer's page. With no answer, a person who has never accepted a card lands on Status. **In the Team setup a person's profile label sets the default route instead** — a Product owner or a Stakeholder lands on Status, a Developer on the Board, or on My issues when they have any ([teams](teams.md) item 8) — and the question sets only Learn. **When no model is set up — no role's weights are found in any model folder — `sekhemet` opens the dashboard on Configuration › Models instead of the default route, on the first run and on every later run until a model is set up** ([surface](surface.md) item 5b; §2.16), and the role question follows once a model is set up. With some roles set up but not the Worker, the default route stands and the *No Coding model* bar says what is missing.

6. **The account menu** (the avatar and name at the bottom of the sidebar; replaces "the footer shows who you are", §2.15.7). Its header shows the person's initials avatar, name and email — in Solo, the name and *This computer* ([teams](teams.md) item 1). Items: **Profile** (name, initials avatar, email, profile label, and in Team the personal access tokens, [teams](teams.md) item 15); **Notifications** (which reasons reach the person by email or chat, within the notification budget, [integrations](integrations.md) items 21–23a); **Keyboard shortcuts** (the cheat sheet, §2.3.3); **Theme** — *System*, *Light*, *Dark* (§2.1.3). In the Team setup also **Members** (and **Audit** for an Admin; §2.17), **Switch workspace** (another Sekhemet server the person has signed in to — one install holds one workspace, [teams](teams.md) item 5) and **Sign out**. Solo shows no Members, Audit, Switch workspace or Sign out.

### 2.3 Keyboard

1. Three tiers: **navigation and triage** (learned in a day), the **command palette** (`⌘K`/`Ctrl+K`; anything in it needs no shortcut, and a palette entry is the default for a new action), and **`g` chords**, one per *visible* view. A chord is the **first letter** of the view's name where that letter is free; where it is taken, the keymap names a fixed alternative: `g u` Runs, `g k` Playbook, `g n` Integrations, `g x` Inbox, `g y` My issues; Projects keeps Workspace's `g w`. Configuration is `g c`. The previous chords (`g a` PM, `g f` Insights, `g q` Runs, `g e`, and `g ,`, which opened Settings and now opens Configuration › This browser) keep working silently for one release; `g s`, `g p` and `g i`, which meant Integrations, Playbook and Inbox before, take their new meanings at once and the cheat sheet says so for one release.
2. **No destructive or surprising action has a bare single-key binding**: there is no bare `t` for theme; theme and Learn are toggled from the palette, the account menu and Configuration › This browser.
3. **The cheat sheet (`?`) is the specification**: it and the palette are generated from one keymap, and an action not in it has no shortcut. It is a 720 px-wide modal that fits a 900 px-high window (scrolling inside), in four columns: Global, Navigate, Cards, Review. Keys that do not apply to the current view are dimmed.
4. Keys are ignored while focus is in a text field, except `Esc` and `⌘↵`.

| Where | Keys |
| --- | --- |
| Global | `⌘K` palette (`>` commands, `#` cards; no match offers *Ask Seshat: <query>*) · `?` keys · `g` + letter · `⌘J` Seshat panel · `Esc` close/back |
| Board | `h/l` columns, keeping the row index, clamped to the target column's length; `j/k` cards (cross lane boundaries; `h/l` stay in the lane) · a mouse click selects a tile; `Space` (or double-click) peeks · `Enter` open · `x` select · `c` new card · `v` board/list · `⇧V` pipeline stages · `/` filter · `⇧S` cycle grouping · `Home/End` column ends |
| Board and list, focused card or selection | `⇧P` priority · `⇧E` points · `⇧L` labels · `⇧C` cycle · `⇧A` owner · `.` any field · in menus `1–9`, `↑↓`, `↵` |
| List | `x` · `⇧J/⇧K` extend · `⌘A` all visible · `Esc` clear · shift-click range · `Space` on a group header collapses it |
| Review and card | `a` accept · `r` send back · `p` park · `z` undo accept (grace window) · `x` acknowledge the focused finding · `j/k` next/previous · `o`/`Enter` open card · `[` `]` attempts · `f` facts rail · `u` unified/split · `n/N` next/previous annotation · `Space` expand file · `1–5` card tabs |
| Composer | `↵` send · `⇧↵` newline · `@` mention an issue — in an issue's comment box also a person or an AI teammate ([teams](teams.md) item 23) · `Esc` returns focus to the page without closing the panel |
| Proposals | `y` apply · `n` discard · `⇧Y` apply all in the group · `j/k` move |
| Decision request | `1–9` pick · `↵` answer |

### 2.4 Board

1. **Five professional columns over the nine stored states** (the same mapping the Jira export uses, so the board and the export agree; the names are [NAMING](../NAMING.md)'s):

| Column | Stored states | Status badge on the tile |
| --- | --- | --- |
| **Backlog** | backlog | — |
| **To do** | ready, planning | *Being planned* (pencil) · *Blocked · waits on X* |
| **In progress** | in_progress, verify | *Editing src/hasher.ts* (running; the step count is the issue's, never the tile's: DB-N7-3) · *Running Tests…* (naming the check that is running) · *Waiting for AI review* · *Types failed · retrying (rung 1 of 4)* (fail) · *Paused for Seshat* |
| **In review** | review | *4 of 4 checks passed · waiting 2h* (amber after 2 h) · *Accepted · PR #n open* (held `awaitingMerge`, not counted against the limit, [review-git §2.5.7](review-git.md)). The Review WIP limit sits here |
| **Done** | done | *Merged ba1338e · 2h ago* |
| *On hold* (only when non-empty) | parked | *Paused for memory*, *Looping · parked*, *Decision needed*, or the person's note |
| *Won't do* (a filter, not a column) | rejected | — (split parents read *Split into 3 cards*) |

   Verify still gates entry to In review (a transition, not a column). **Pipeline stages** (`⇧V`) splits To do and In progress back into the nine machine columns for operators, named as stored, in sentence case (Backlog, Ready, Planning, In progress, Verify, Review, Done, Parked, Rejected; [NAMING](../NAMING.md)); the choice is kept per browser. Moving a card past a failing check is never a board gesture: a check override (a gate override, internally) is a recorded human decision with a reason, made from the CLI or the API ([kernel](kernel.md)); the card view shows that it happened.
2. **Columns.** Fluid (`min 200px`, `max 300px`, 8 px between columns and 8 px between tiles; 8 px body padding, 16 px board padding). **Empty columns collapse into chips above the board** (*Done 4 ›*), never rotated rails; Done is a full column whenever it has cards. In review and On hold are pinned in view when the board scrolls horizontally. Once more than six columns hold cards (as in Pipeline stages), the columns beyond the viewport are windowed horizontally; In review and On hold stay pinned, because the person's queue is never the part that gets scrolled away. Cards in a column keep their recorded order (a fractional `order_key`, [kernel](kernel.md)), except In review and On hold, which sort by wait time, longest first.
3. **Column header** (36 px, 0 12 px padding): name · `count / limit` for WIP-limited columns · the column's points sum (*13 pts*), only when Preferences → Estimation is *Story points* (DB-N7-2) · a 2 px capacity bar (`--text-secondary`; amber at capacity; red over) · a Tips *?* when Tips are on · a `⋯` menu (sort by priority, wait time or recently changed; collapse). The In review limit is always shown with its derivation (*limit 3, from 60 review minutes a day at ~20 min per card*); no limit is hidden for being large. At capacity the header says, as visible text in its popover, *Full. The agent holds finished cards until you clear one.* On hold, when it holds cards, sits far right and shows its count in the parked tone (`--state-parked`).
4. **Tile anatomy** (88 px compact; 112 px comfortable adds a one-line spec excerpt and budget detail; the heights are fixed because the board's windowing depends on them; width follows the column; 8/12 px padding, 4 px row gap, 6 px radius):

```
┌──────────────────────────────────────────┐
│ ◇ CHR-12              3 pts  JD  Agent   │ row 1: issue type icon · issue key · points (only with estimation on) · owner (a person's avatar) · delegate chip
│ Implement canonical JSON and SHA-256     │ row 2: title 13/500, 2-line clamp
│ ▮▮▯  Ledger  api  security  3 subtasks   │ row 3: priority glyph (hidden when none) · epic chip · ≤2 labels, then +n · subtasks
│ ✕ Types failed · 3 errors · 22h          │ row 4: status badge (icon + colour + words) · check pips · work item age
└──────────────────────────────────────────┘
```

   - **Issue type** (DEC-31): the icon and word of the standard issue type — *Story* (new behaviour), *Bug* (a fix), *Task* (a refactor, upgrade or characterization, a review card, or a card of the `task` tier), *Spike* (a spike or research card), *Epic* (an epic; an initiative keeps *Initiative*) — derived from the stored `kind`, `change` and tier by `issueTypeOf` (`vocabulary.ts`). The internal kind labels (Contract, Storage, Flow, Rules) are retired from every screen.
   - **Points** show on the tile, the column header, swimlane and group headers, the bulk bar, the list's Points column and the reports only when the project's **Preferences → Estimation** is *Story points* (DB-N7-2); with it *Off* (the default) no points show, the sprint header and burn-up count issues, and the *Unestimated* view and filter are not offered.
   - **Owner and delegate.** A person stays the card's **owner** and may have an avatar (a 20 px monogram of their initials); the agent, or another person, is the **delegate** that builds it, shown as a **text chip** (*Agent*, or the person's name) — the convention Linear, Cursor, Codex and Copilot use. **A role never has an avatar** ([NAMING](../NAMING.md)). The fields are [kernel](kernel.md)'s (`owner`, `delegate`); the export mapping is [integrations](integrations.md)'s.
   - **The status never truncates its cause**; it may wrap to two lines inside the 88 px by dropping row 3's labels.
   - **Blocked.** A card with a `blockedReason` or an unfinished dependency carries a **blocker flag in the fail tone, with the link icon and the word *Blocked*** and its cause (*Blocked · waits on @hasher*); colour is never the only signal.
   - One badge is icon + colour + words, and **never combines a stage with a failure mark** (no "✕ Planning"): it says what is true now (*Needs a new plan*).
   - **Priority glyph**: a fixed 12 px slot; three rising bars (1–3 lit, unlit bars in `--border-strong`, stroke 3 so the icon test holds) for Low/Medium/High in `--text-secondary`, a boxed exclamation for Urgent in `--text-primary`; the shape, not colour, carries priority. No glyph for *No priority*; the list's Priority column is where priorities scan as a column.
   - **Epic chip** uses one of eight muted epic hues (chrome stays neutral). **Labels**: 11 px secondary text in a 1 px `--border-subtle` outline.
   - **Check pips**: one 12×12 box per check the card's evidence ran, in `gates.toml` order — ✓ passed, ✕ failed, – skipped, ring running, empty not run — with no letters; each glyph is a 1.5 px line in `--on-state` on the state fill for passed and failed, and *not run* is a 1 px `--border-strong` outline; and **never a check the evidence did not run** (no synthesised *Parse: pass*); the popover (focus or hover) lists each check's name, state, duration and first error line.
   - **No step counter and no model name on the tile** (DEC-31, DB-N7-3): the step budget (*8 of 40 steps*) and its bar are the issue's (its Steps tab and Facts), and model names are Configuration's and Machine's. Difficulty moves to the peek drawer and Facts.
   - **Work item age** shows on every In progress and In review tile (Kanban Guide), turning amber past the 85th-percentile cycle time.
   - **Tile states**: hover `--bg-overlay`; focus the global 2 px accent outline, offset 1 px (§2.14.5; the column body's 8 px padding keeps it unclipped); selected (`x`) a `--border-strong` border and a checkbox; focus and selection are visibly distinct and can co-exist. Done tiles are secondary text with no bars.
5. **Moves between columns happen only through recorded, gated actions** (triage, decisions, proposals); there is no drag between columns. **Reordering within a column** (drag or keys) is allowed and is recorded as one event.
6. **Peek drawer** (`Space` or double-click, 480 px): gates, failures, outcome, *Done when*, kind and difficulty, owner, delegate and suggested accepters ([review-git §2.4](review-git.md)), a compact file list, and triage keys that work inside it. `Enter` opens the card view; `Esc` closes the drawer and returns focus to the tile.
7. **Quick create** (`c`, or the `+` on a column): a one-line title and optional description that goes through the planner pipeline as a create proposal ([planner-pm](planner-pm.md)) and is shown for Apply. No path ends in "use the CLI".
8. **Live updates** patch only changed tiles, keyed by id; they never re-render the board or reset scroll, focus or an open drawer; a focused card that changes column keeps focus and is scrolled into view, and no other card scrolls; a tile that changed shows *just now* for 10 s; no motion. A change made through the API (a park by `curl`) appears within 1 s. **A reload rebuilds the same state** from `/api/board` and the stream's replay (`?since=`, `Last-Event-ID`; `server.ts:574-580`), so what a person sees never depends on having watched live.
9. **Scale.** Windowed columns and cards (an overscan of 3 cards) keep 500 synthetic cards scrolling with no main-thread task over 50 ms and under 50 MB of DOM memory. Swimlanes are not windowed (they are for filtered views).
10. **Board states:** *No cards yet* with a **Start a project** button (opens Seshat) and beside it **Take over a project** (opens Seshat with the take-over conversation, for a repository someone started and did not finish: [design-stage](design-stage.md) §2.10, DS-TO-16; [DEC-43](../DECISIONS.md#dec-43--take-over-a-project)), and a secondary *or plan a feature* line; empty-column copy at the top of each column (Backlog *Ideas and split-off work.* · To do *Cards whose dependencies are done, and cards being planned.* · In progress *No agent running.* · In review *Nothing waiting for you.* · Done *Accepted cards appear here.* · On hold *Nothing parked.*); *No cards match "Type: Bug"* with `Clear filter`; review full and memory pause as shell bars, with *Holding for review* on held tiles. In Pipeline stages the machine columns keep their own empty copy: Ready *Cards whose dependencies are done.* · Planning *The planning model is writing plans and tests.* · Verify *Nothing being checked.*

### 2.13 Visual system

**The professional standard** (owner, 2026-09-25, from the mockup review). The dashboard reads like Linear, Jira or GitHub, never like a chatbot or a template:
- Activity is a timeline — system events as one compact line with a small icon, comments as a name, a time and plain text — never chat bubbles.
- One level of container: a page, a sidebar, a list or a table; no boxes inside boxes. Properties sit in a label/value list without cards.
- Real icons (inline stroke SVG, one set, one weight), never text glyphs (✓ ✕ × ···) or emoji.
- Copy is terse: a label or a short fact, never an explanatory sentence where a label will do; explanations belong in Tips.
- One primary action per view (the dark button); everything else is a secondary button or a link. The brand gold marks only the active item and the logo.
- The vocabulary is DEC-31's.

1. **Tokens** are the single source of truth for colour, published as CSS custom properties and JSON (`tokens.ts`, `/tokens.css`, `/tokens.json`); components never hard-code a colour. Sixteen roles per theme — `bg-base`, `bg-surface`, `bg-raised`, `bg-overlay` (the surface ladder: depth by luminance, **no drop shadows**), `border-subtle`, `border-strong`, `border-control` (P12), `text-primary`, `text-secondary`, `text-muted`, `accent` (Egyptian gold), `state-pass` (Nile green), `state-fail` (red ochre), `state-running` (lapis), `state-parked` (needs you), `state-blocked` — plus derived `on-accent`, `on-state`, `scrim`, `tint-{pass,fail,running,parked}` (12% Basalt, 10% Sand) and layout constants. The values are in `tokens.ts`, not here; the contrast test (§2.14.1) is what holds them.
2. **Colour roles (P12):** the warning/parked hue is moved clearly apart from the accent (a copper: the mockups' `#C8743A` / `#9A4F1C` measured only 16° from the gold, so the copper sits 23° from the gold); **the copper keeps its hue, 7–10° from the red ochre of a failure, and is told apart from it by glyph and by lightness, never by hue alone** (lead decision under [DEC-42](../DECISIONS.md#dec-42--the-owner-delegates-the-outstanding-decisions-to-the-lead), B4.2): parked carries the pause glyph and fail the cross (`STATE_GLYPHS`, `vocabulary.ts`), and parked sits **at least 10 L\* further from the ground than fail** — lighter on Basalt, darker on Sand (`tokens.ts` holds `#DD8967` Basalt / `#743217` Sand; the earlier `#D46A3F` / `#9E4420` measured 1.8 and 0.3 L\* from fail). **Disabled buttons use a neutral fill**, never faded gold; a **`--border-control`** role at ≥ 3:1 edges every input; **`--text-muted` is decorative only** (line numbers, disabled controls, decorative glyphs) and never carries text a person must read, placeholders included.
3. **Colour per tone.** A rule is 2 px — on the left of a tile, row or block, or on top of a gates segment. The running, failed-and-retrying and On hold tiles carry one in their tone. ### 2.14 Accessibility

1. Every colour pair used as text or as a control's only edge meets WCAG 2.2 AA **as used**, asserted by a test over the tokens in their actual pairings (placeholders, Sand accent on raised, state text on tiles): text ≥ 4.5:1, with body text (`--text-primary` on base and surface) ≥ 7:1; controls' edges, state icons and the accent ≥ 3:1. State-coloured text sits only on base or surface; on raised tiles state is carried by the icon (≥ 3:1) with secondary words.
2. **Nothing a person needs is only on hover**: WIP reasons, full status lines, gate names and priority meanings are in keyboard-reachable popovers or visible text. A `title` is only ever a pointer duplicate: its words are also visible, the element's accessible description (`tip()`, `dom.js`), or a keyboard and touch disclosure (a column's WIP reason is the first line of its options menu).
3. Landmarks (`nav`, `header`, `main`, `aside`); each board column a `group` labelled by its header, holding a vertical `listbox` of `option` tiles with roving tabindex, `aria-selected` and `aria-describedby` pointing at the status line; the list a real `table` with `aria-sort` on the sorted header and `aria-selected` on rows; the gates strip a list of named buttons (*Types: failed, 3 errors, 0.7 seconds*); diff annotations `role="note"` and focusable; WAI-ARIA tabs; palette and cheat sheet as modal dialogs that trap and return focus (the palette a combobox); the Seshat panel a `complementary` landmark labelled *Seshat, project manager*, with its thread as `role="log"`, announcing only final replies (*Seshat replied. 2 proposed changes.*), and the pending block's current row `aria-busy="true"`; proposals a list of labelled groups with Apply/Discard names including the summary; field diffs as `dl`; the bulk bar a toolbar announcing *3 selected*; toasts `role="status"` or `role="alert"`; one polite live region for the focused or selected card and triage results; background changes are not announced.
4. Focus order in Review: queue → Reviewer findings → gates strip → failures → diff files → triage bar; `Tab` inside the diff visits file headers and annotations, not lines.
5. Focus: a 2 px accent outline, offset 1 px, on `:focus-visible` (≥ 3:1 on every surface). Targets ≥ 24×24 px on desktop (copy buttons included) and ≥ 44×44 px on a phone (one query below 768 px, `base.css`; desktop density is unchanged). Layouts hold at 200% zoom. Every control has an accessible name.

### 2.15 How it is built

1. **Static, build-free ES modules** served from `packages/ui/web` under `/app/`; no framework, no CDN, works air-gapped; the served page is a small shell. Presentation logic is pure TypeScript in `packages/ui/src` (vocabulary, board model, tile model, nav model, keymap, learn content, filter language, flow maths), served as `/app/lib/*.js` and unit-tested with exact values; web modules only render. How `/app/*` is served safely (no `..` traversal, correct MIME types) is [runtime](runtime.md)'s.
2. Live data arrives on the server-sent event stream (`/api/stream`: `append` for ledger events including `card/step`, `pm` for PM status, `machine` every 5 s, `tokens` for the running model's output); windowing is the page's own (`virtual.js`); CSS is organised per component. The server enriches each card with a `display` object from the vocabulary (title, kinds, key, state label, status line, stop label, tone, entered-column time, waits-on, evidence summary) and publishes the vocabulary as `/vocab.json` for plugin panels.
3. **Responsive.** 1440 px: everything at full size. 1024–1279 px: labelled narrow sidebar; board columns min 220 px with horizontal scroll and In review / On hold pinned; Review's facts rail as a disclosure. < 768 px: the bottom bar; the board as one column with a segmented column switcher (*To do 4 · In progress 1 · In review 1 …*) and full-width tiles; the card view shows Evidence only; triage is one tap on 48 px buttons with send-back in a bottom sheet; no create or bulk actions; Status and PM fully usable.
4. **Palette.** 600 px at 12vh, `--bg-raised` with a 1 px `--border-strong` edge and no shadow, over `--scrim`; a 48 px, 15 px input; groups *Actions on the focused card* (Accept, Send back, Park, Open, Copy id), *Cards* (title, kind, state icon), *Go to* (with chords), *Preferences* (theme, density, Learn), and *Seshat* — first, *Start a new project* for a query made of its words ("new project", "start"), and *Ask Seshat: <query>* when nothing else matches, which sends the query with what the person is looking at and opens Seshat (DB-P5-4); matched characters in `--text-primary` against the rest in `--text-secondary`; each row shows its shortcut; `⌘↵` opens a card in the card view; the empty query shows recent cards and top actions.
5. **Verification of every UI change**: seed a fixture project, open it at 1440×900, 1100×800 and 400×812 in both themes, compare with `docs/design/mockups/`, exercise the change's keys with the keyboard only, and require an empty error console; check each view against a contract-shaped fixture server **and** a server with the endpoints absent, so every "not on this server yet" state is seen.
6. **Security, page side (S3c):** every mutating request carries the per-session token the server issued to this page (not a constant header); the page runs under a Content-Security-Policy with no inline script and `frame-ancestors 'none'`; model and repository text reaches the DOM only through escaping renderers. The server side (Host check, token issue, headers) is [runtime](runtime.md) and [security](security.md).
7. **Team setup, page side** ([DEC-35](../DECISIONS.md#dec-35--one-product-two-setups-solo-and-team); replaces the company-server wording of D7): the account menu shows who you are (§2.2.6; superseded: "the footer shows who you are"); a control a person's access level does not allow is disabled, with the level they hold and who can do it written beside it (*You're a Stakeholder on Chronicle. A Member can start the Agent on this issue.*, [teams](teams.md) item 9); Accept is disabled with *This project's Accept rule doesn't include you* when the project's Accept rule ([teams](teams.md) item 7) does not name you, and, on a project where two or more people hold the Accept permission, with *You built this card; another person must accept it* or *You delegated this card to the Worker; another person must accept it*, naming who may ([review-git §2.4.1](review-git.md)) — the delegator being whoever recorded the latest delegation to the Worker, so a person who became the card's owner later, and neither built nor delegated it, sees Accept enabled (RG-N5-8); ledger and thread entries name people, not "human".

### 2.16 Configuration

`#/configuration` (`g c`), in the System menu and always visible; each section is addressable (`#/configuration/models`, `/benchmark`, `/review`, `/preferences`, `/project`; the older `/browser` still opens Preferences), `#/registry` opens Benchmark and `#/settings` opens Preferences. It is reached from navigation, the palette (*Configuration*, *Set up models*, *Benchmark models*), the first run when no model is set up (§2.2.5, [surface](surface.md) item 5b), the *No Coding model* bar, each role on Machine, and every message that says a role is not configured (the Reviewer's unfilled-role reason in Review links here). It replaces the Registry and Settings views (owner decisions O2 and O3, [DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue)); the scan, the recommendations and the download are [models](models.md)'s (NEW-models-12), the benchmark's mechanics [measurement](measurement.md)'s (NEW-measurement-5), and the shapes [PM_CONTRACT §3](../PM_CONTRACT.md#3-endpoints) *Configuration*. A lede, once: *Choose which models do each job, and compare them on this machine. Nothing is downloaded, loaded or run until you press the button.*

1. **Models.**
   - **Model folders**: each configured folder with where it was set (configuration file, `--models-dir`, `SEKHEMET_MODELS_DIR`), whether it could be read (and why not), and how many models it holds. **Add folder** offers the likely folders that exist on this machine as one-click choices, and a path field; **Remove**; **Scan** re-reads every folder, with progress per folder. A folder is only read, never written.
   - **Models found**: a table of every model the scan found — name, size in GB, quantisation, context length in tokens, family, **Fits this machine** (*Yes*, *Yes, swaps with the other roles*, or *Needs N GB*, with the reason in words: *13 GB of 16 GB usable*), and whether it matches the registry's published hash (*Verified*, *Not a registry model*, *Hash differs*). A model that does not fit is listed, never hidden.
   - **Roles**, always in the order Coding model, Planning model, Review model, Research model (DEC-31; internally Worker, Planner, Reviewer, Researcher), the Planning model row saying *Seshat, the project manager, runs on this model*: each role's **current model by name**, its state (*Resident*, *Swapped out*, *Not configured*), its benchmark score when there is one, and the **recommended model with its reason** in one plain sentence (*Recommended: Gemma-4-26B-A4B. It is a different family from the Coding model, which the Review model needs, and it fits at 14 GB.*). Actions: **Assign** a found model to the role, **Load**, **Unload**, and, for a recommended model that is not present, **Download…**. A role left unfilled says why in words (the Reviewer's reason is [review-git §2.3.7](review-git.md)'s).
   - **Assign** follows the models spec's adoption rule ([models](models.md) rule 30a): a person may assign any model verified on this machine (*qualified*, internally), with or without a benchmark; where the model is not yet verified on this machine, the button reads **Verify on this machine to assign** (a check of a few minutes: tool calls, a multi-turn tool conversation, recall — [models](models.md) rule 27a) and assigns when it passes. The Review model refuses a model of the Coding model's family, saying so. The previous assignment is kept and **Restore previous** brings it back.
   - **Load** and **Unload** go through the residency scheduler, never around the memory guard: a load that would not fit says why and which model would be unloaded; unloading a model a running card is using waits for the next step boundary, and the row says so (*The agent stops after step 5, then unloads*).
   - **Download…** never starts on its own. It opens a confirmation with the model, its source host, its size, the published SHA-256 (mono, with Copy), the folder it will be written to with its free space (the first configured folder that is there and writable now — an unplugged drive's folder is never offered, never created, and the server refuses any folder but a configured, present, writable one), and one line on what leaves the machine (*A request for this file to its source host. Nothing about your project is sent.*); then **Download** (primary) or Cancel. Progress shows bytes, rate and time left, then *Verifying…*, then *Verified. Ready to assign.* — or *The file's hash didn't match the published one, so it was deleted.* When `[network] mode` does not allow the source host, Download is disabled with the setting named; a model with no registered source and hash offers no download. A file of the same name already in the folder is never replaced: the confirmation asks for another name. It is the same implementation as `sekhemet models fetch <model>` ([models](models.md) NEW-models-7).
   - **Use the recommended models** does all of this in one path for a person who does not want to choose: one confirmation listing every download it needs (each with source, size and hash) and the folder they go to — the confirmation names back each download's model and hash and the folder, and the server refuses it when they differ from the plan it recomputes — then the downloads, then the quick benchmark of the recommended combination, then the assignment of each recommended model that is verified on this machine (a model that is not yet verified gets its check first, [models](models.md) rule 27a), and a sentence saying what was done and anything it could not do.
1a. **Model details, combinations and placement** — Smart Swap's part of Models ([DEC-45](../DECISIONS.md#dec-45--smart-swap); [models](models.md) rules 20d–20k; built in B4.1). It helps a person choose models, engines, placement and combinations from measured facts, as part of this section, not a new view. **Every number carries its grade**, shown beside it in words: *Measured* (recorded on this machine by a run), *From the file* (read from the model's file itself — its size, its header — never called *Measured*), *Estimated* (computed before a measurement, with its spread where it has one) or *Design value* (a D value of ours, not yet tuned by replay).
   - **Per model** (opening a row of Models found):
     - **identity:** family, total and active parameters, quantisation, engine (GGUF on llama.cpp; MLX), size, maximum context, licence, source and hash;
     - **memory:** weights, KV at the role's context and KV type, compute buffer and prompt cache, set against the live headroom (the lower of the GPU and system measures, [models](models.md) rule 20g), with what-ifs for the context size and the KV type that recompute it without loading anything;
     - **speed:** decode and prefill per engine — first estimated (efficiency × bandwidth ÷ bytes per token, [models](models.md) rule 20d), then measured with llama-bench (one warm-up, five runs at the role's depth, accepted at a spread of 3% or less) when a person presses **Measure speed…** and confirms the model and the memory it loads; time to first token with and without the prefix cache, from the same action; cold and warm load time per volume, with the placement advice;
     - **per role:** qualification status for the full combination (engine build, template, MTP and the rest, [models](models.md) rule 27a), quick-benchmark scores, tool-call validity, and the record on the person's own projects;
     - **warnings,** in words: won't fit; slow drive; unqualified; licence; Ollama requantisation; an aging cap that cannot be met (the predicted wait shown instead);
     - **before a download:** memory and speed estimated from a remote GGUF's metadata alone — by our own estimator over `@huggingface/gguf`, each range answered with a 206 and the bytes read capped — with no weights fetched. gguf-parser-go is given a local file only (`--path`), never its `--url`, which would fetch outside the `[network]` policy.
   - **Per combination** (an assignment of models to roles): the hard filters (the Reviewer's family differs from the Worker's; everything fits), each exclusion with its reason; peak memory and what co-resides; C_pair for each role pair; predicted wait p50 and p90 per class, Seshat's included; **time per card** = E[attempts] × compute + E[swaps] × C_pair, E[swaps] from a closed-loop replay of the person's last N cards under this combination (median and p90 with N; *Estimated* while N < 20); and accepted cards per night. Combinations are ordered by every role's quality floor, then the least time per card, then the smaller footprint; **no weighted combined score** is computed or shown ([models](models.md) rule 4c).
   - **Placement:** a what-if per model on a slower volume — *Copy to internal storage: saves about 6 swaps' worth of loading, 40 minutes a day* — chosen as a knapsack by swaps per day × load time saved ÷ GB, keeping at least 20 GB of internal space free; a copy that would break that is not suggested, and the page says why. **Copy to internal storage…** opens a confirmation with the model, its size, the destination, the free space left after it, and the published or recorded SHA-256; nothing is copied until the person presses **Copy**. The copy is verified by hash before the registry points to it; a copy whose hash differs is deleted and the registry is unchanged; the original is never deleted.
   - **Across the page:** a 24-hour residency timeline from the recorded loads and unloads, with the realised θ per hour; an engine comparison per model (its llama.cpp and MLX builds, where both are found); and every benchmark run, quick and full (finalists on the role's qualification cases), stored so the page improves with use.
2. **Benchmark — two tiers for comparing model combinations.** People mix and match one model per role from the models they have, up to the strongest this machine can run, to find the best combination. The **quick** tier answers in minutes; the **overnight** tier settles what the quick tier could not tell apart. The page says so once, in these words: *The quick benchmark shows speed, fit and large differences; the overnight benchmark settles close calls.* The mechanics of both are [measurement](measurement.md)'s (NEW-measurement-5); applying a winning combination is always a person's choice.
   - **Combination builder**: one picker per role (Coding, Planning, Review and Research model), each offering only the models that fit this machine — a model that does not fit is shown disabled with *Needs N GB* — and showing, for each model, its cached quick score for that role with its interval, or *No quick score yet*; a role whose screen is not built yet shows *Not measured yet* instead, for every model (the Reviewer's screen arrives with B4.8 and the Researcher's with B4.4, [measurement](measurement.md) rule 30a). The combination in use is pre-filled and marked *Current*; the recommended one is one click away.
   - **Run quick** carries its estimate in minutes, stated before anything runs and computed from what is not yet cached: at most about 17 minutes for a new Coding model, its load included (6 cards, each capped at 2 minutes); at most about 5 minutes for each new Planning, Review or Research model; at most about 10 minutes for the end-to-end check; so under about 45 minutes for a whole combination with nothing cached ([measurement](measurement.md) rule 32); an estimate over a target is marked before the person confirms, and *Already measured: no run needed* shows when every role is cached. Each role is scored once per candidate model and cached, so changing one role re-runs only that role; a combination's score is assembled from its roles plus a short end-to-end check.
   - **Schedule overnight** runs a thorough, paired, repeated comparison of the combinations the person picks — by default the top combinations the quick tier could not separate, up to 3 — and says how many fit tonight's window, from about 5 hours per combination (recorded throughput when there is one): *Tonight 22:00–03:00 (5 h): 1 of 2 combinations fits; the other runs tomorrow night*. It runs only in the machine's overnight window ([models](models.md) rule 20b), stops at the window's end and resumes the next night, and never runs while a card runs or while the machine is reserved — inside reserved hours even when the person is idle, or after *Reserve now* (§2.11).
   - **State and Stop**: each run is *Queued* (with when it will start), *Running* (the tier, which role and model or which combination is being measured, cards done of total, elapsed and time left), *Stopped* or *Done*, and has **Stop**, which ends it and keeps every result already measured, marked partial. One run at a time: while another run holds the runner, Run quick is disabled and names it, and an overnight run waits.
   - **Comparison**: a table of the combinations measured on this machine, one row each — the model per role, each role's score, the end-to-end check's result, the combination's score with its interval, and its tier — sorted by score, with the recommended combination marked and its reason. **Two candidates are labelled *No clear difference* (DEC-31; *indistinguishable*, internally) when the paired sign test on the same items does not reject** — two models for a role on the cards, briefs, defects or questions both ran, and two combinations on each role in which their models differ ([measurement](measurement.md) rules 10 and 35); interval overlap decides nothing. Candidates with no clear difference are shown as tied, and the page never ranks one above another it cannot tell apart; every score keeps its interval. Beside each role's score are its **secondary measures** — seconds per card, valid tool calls, steps — which is where the quick tier tells close models apart. A role that reads *Not measured yet* is left out of the comparison, and the table says so. After an overnight run the table leads with the **morning report**: which differences the overnight comparison resolved (*A is better than B*) and which still show *No clear difference*, in words. A row whose models are all verified on this machine ([models](models.md) rule 27a) offers **Assign this combination**; a row with a model not yet verified offers **Verify on this machine to assign** instead. A benchmark is never required to assign (rule 30a), and nothing is assigned without that press.
   - **History**, per combination: every recorded run of either tier with its date, settings and scores, and the recorded frozen baseline for reference, compared with [measurement](measurement.md)'s paired statistics (*Better than the baseline*, *Worse*, or *Not established: the difference is smaller than the suite can show*, never a bare difference). It absorbs the bake-off matrix by hardware tier that Registry showed (`writeBakeOffMatrix`).
3. **Review capacity**: review minutes per day, editable by a person holding the Accept permission, or by an Admin in the Team setup; the change is a recorded config event and ReviewWIP is recomputed at once and shown with its derivation (*limit 4, from 60 review minutes a day at ~15 min per card*). A value of 0 or less is refused beside the field ([review-git §2.2.3](review-git.md)).
4. **Preferences** (DEC-31; formerly *This browser*): theme, density, Tips and first-run role, kept per browser; and **Estimation** — *Off* (the default) or *Story points* — kept per project (`project/settings_changed`, `PATCH /api/projects/:id/settings { estimation }`), changed by the project's lead or an Admin (`project.settings`), read-only with that reason for anyone else (DB-N7-2); and **Apply Seshat's suggestions automatically** — Labels, Priority, Duplicate link, Split, each off until an Admin turns it on for the project (`PATCH /api/projects/:id/settings { auto_apply }`, `auto_apply.enable`), read-only with that reason below Admin, never the assignee or health (`autoApplyView`, `packages/ui/src/settings.ts`; [planner-pm](planner-pm.md) PM-N9-2, [teams](teams.md) TEAM-41). A suggestion a rule applied shows on the issue as *Applied by <Admin>'s rule: …* with *Undo*, and in its Activity (B4.8).
5. **Project configuration**: the effective configuration, read-only, each value with where it came from (default, user file, project file, flag, environment) and where to change it; above it, **Agent queue** — *Agent issues per person*, the queue's per-person cap ([teams](teams.md) item 30), with its source, which an Admin saves to the user configuration (`PUT /api/config/queue`, `queue.caps`; recorded as the Admin's configuration change) and anyone else sees read-only with the level note beside it.

**Who may change it.** In the Team setup every change to the server's configuration on this page — Models, Benchmark, Project configuration, the queue's per-person Agent cap and slots ([teams](teams.md) items 30–32) — needs the **Admin** level, and Review capacity needs an Admin or a person the project's Accept rule names (superseded by DEC-35: before it, every section needed the Accept permission); each change is recorded with the person who made it; a person without the level sees those sections read-only, with that reason beside each control, and folders are paths on the server. **Preferences** is the exception for its browser settings: theme, density, Tips and first-run role are that browser's own, so anyone may change them, with no permission and nothing recorded on the server; its Estimation is the project's and needs `project.settings`. 3. **My issues** (`#/my-issues`, `g y`; Team only) — the issues the person owns, is delegated or is asked to review, across the projects they can see, in the List view's table (§2.4.15) grouped by project.
4. **Members** (`#/members`; from the account menu) — a table: the person (initials avatar, name, email, presence dot), access level, per-project overrides, profile label and last active. An Admin sees **Invite** (primary), which creates a single-use link with a level, an optional project and an expiry (7 days by default) and shows it once to copy; per row, change level, override for a project, change label, issue a password reset, unlock a locked account and remove; and pending people — from open sign-up or first seen through the identity proxy — with *Approve* and *Decline* ([teams](teams.md) items 6–10). Others see the table read-only.
5. **Audit** (`#/audit`; Admin only) — the event log read as a table: time, actor (an AI teammate with its badge and *on behalf of* the person who started it), action and target; filters by person, action and project; **Export** as CSV or JSON. It includes every sign-in, level change, invite, model change and configuration change, and is a read of the ledger, not a second store ([teams](teams.md) item 27).

### NEW-models-14 (the view) — model details, combinations and placement
*[models](models.md) owns Smart Swap (NEW-models-14, rules 20d–20k, [DEC-45](../DECISIONS.md#dec-45--smart-swap)) and the measurement of placement is [measurement](measurement.md)'s (rule 16d); this spec carries the page (§2.16 item 1a). Workstream **B4.1**. Each criterion is tested on a server with fixture ledgers, a fake memory probe and fake benchmark results, loading no model.*

- **DB-NM14-1** WHEN the model section renders any number THE SYSTEM SHALL show beside it its grade, *Measured*, *From the file*, *Estimated* or *Design value* — a value read from the model's file (its size, its header) is *From the file*, never *Measured*, and an unknown size is said so, never shown as 0; a test rendering one of each finds each labelled, and a number without a grade fails the test.
- **DB-NM14-2** WHEN a person opens a model THE SYSTEM SHALL show its identity (family, total and active parameters, quantisation, engine, size, maximum context, licence, source, hash) and its memory breakdown (weights, KV, compute buffer, prompt cache) against the live headroom; WHEN they change the context size or KV type in the what-if THE SYSTEM SHALL recompute the breakdown and load nothing.
- **DB-NM14-3** WHEN speeds are shown THE SYSTEM SHALL show the efficiency estimate as *Estimated* until a llama-bench run of one warm-up and five runs at the role's depth has a spread of 3% or less, then that result as *Measured*; a run with a larger spread SHALL be shown as not accepted and not used; llama-bench SHALL run only on an Admin's **Measure speed** confirmed by the model's name and the memory it loads, inside one benchmark run of the residency scheduler (no other role loads meanwhile; only what it loaded is unloaded), recorded as `model/speed_measured` with the principal; and THE SYSTEM SHALL show time to first token with and without the prefix cache and cold and warm load time per volume. Because llama-bench, like a qualification from the page, loads the weights where the residency scheduler cannot see them, the run first unloads every idle resident model and refuses while one is in use (`BenchmarkLease.exclusive()`).
- **DB-NM14-4** WHEN a model has a warning (won't fit, slow drive, unqualified for a role, licence, Ollama requantisation, an aging cap below C_pair) THE SYSTEM SHALL state it in words, and for an infeasible cap SHALL show the predicted wait instead ([models](models.md) MD-N14-20); per role it SHALL show the qualification status of the full combination.
- **DB-NM14-5** WHEN a person asks for a pre-download estimate of a remote model THE SYSTEM SHALL read only its GGUF metadata through its own estimator over `@huggingface/gguf` and the `[network]` policy's fetch, refuse a host that ignores Range (anything but a 206) and stop past a byte cap, label the result *Estimated*, and fetch no weights (a test observes only metadata range requests); gguf-parser-go SHALL be given a local file only (`--path`), never its `--url`, which bypasses the `[network]` policy.
- **DB-NM14-6** WHEN combinations are shown THE SYSTEM SHALL exclude, with the reason, any that breaks the family rule or does not fit; SHALL show for each the peak memory, the co-residence, C_pair per role pair, predicted wait p50 and p90 per class (Seshat's included), time per card (*Estimated* while fewer than 20 of the person's cards were replayed) and accepted cards per night; SHALL order them by quality floors, then time per card, then footprint; and SHALL show no combined score.
- **DB-NM14-7** WHEN placement is advised THE SYSTEM SHALL show, per model on a slower volume, the swaps' loading time saved per day, suggest copies as a knapsack that keeps at least 20 GB of internal space free, and say why a copy that would break that is not suggested.
- **DB-NM14-8** WHEN no person has pressed **Copy** in the confirmation (showing size, destination, free space after, and hash) THE SYSTEM SHALL copy nothing; WHEN one does THE SYSTEM SHALL verify the copy's SHA-256 before pointing the registry at it, record the copy on the ledger with the person's principal, in an event registered as structural only ([models](models.md) MD-N14-40a), and keep the original; WHEN the hash differs THE SYSTEM SHALL delete the copy, leave the registry unchanged and say so.
- **DB-NM14-9** WHEN the section renders THE SYSTEM SHALL show a 24-hour residency timeline built from the recorded `model/loaded` and `model/unloaded` events with the realised θ per hour, an engine comparison for each model found in both llama.cpp and MLX builds, and every stored benchmark run of either kind with its date and settings.
