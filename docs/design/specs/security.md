# Security: sandboxing, permissions, egress, secrets, workspace trust, air-gap

## 1. Purpose

The harness runs code written by a local model on the owner's machine. The v1 Worker is uncensored ([DEC-04](../DECISIONS.md#dec-04)), so the sandbox, the permission engine and fail-closed confinement are its **only** guardrails, and every item in this spec is v1-blocking. It serves the spine rule that the model never certifies its own work: a model that can leave its sandbox can edit the machinery that judges it.

## 2. Behaviour

### Threat model

1. **Untrusted:** everything the Worker writes (worktree files, `package.json` scripts, `.gitattributes`, a worktree's `gates.toml`), every repository the user has not trusted, and all external text (issues, PR comments, fetched pages, synced items).
2. **Trusted:** the harness process, the user's own configuration directory, and repository configuration the user has explicitly trusted (§ Workspace trust).
3. **The rule that follows:** anything the harness runs on untrusted input runs confined. Code outside the sandbox never executes a program named or written by untrusted input.

### Confinement: one execution path

4. Every process that executes code from a worktree — Worker commands and background processes, gates (including per-package gates), the visual gate's dev server and browser, the `browse` tool's headless browser, language servers, onboarding probes, `--validate-tools` — runs through one chokepoint, `runConfined()`, in the card's sandbox with an allowlisted environment (S3a). The Worker's own commands and the gates run through `ProcessSandbox` (`confinedSandbox()`) with the harness-chosen root, which is the same confinement one layer down; moving them under `runConfined()` is a refactor, not a security change. *Named exception:* `act`, which runs a project's CI workflows in Docker containers that Seatbelt and bubblewrap cannot confine. It is opt-in, refused under `--restricted`, and says so when it runs (found in B1).
4a. **`--validate-tools` is kept and confined, not cut** (decided 2026-09-24, §8 Q1). It runs command strings mined from the Worker's trajectories — on-the-fly tool synthesis, held at `triaged` in [RESEARCH_REGISTER.md](../../research/RESEARCH_REGISTER.md) (R6) — so each candidate is Worker-written code: it runs through `runConfined()` in a scratch worktree created from the base branch for the validation and deleted after it, with no network, the allowlisted environment of item 6 and its 60 s timeout, never in the main checkout. A validated candidate is only written to `.sekhemet/tool-candidates/`; it never joins the Worker's tools (R6 stays `triaged`). Built in B1 with the rest of S3a (SEC-17a). *Changed from the code:* today it runs with `execFileSync` in the repository root with the harness's full environment (`wave2.ts:863-876`).
5. Processes the harness trusts (its own git, model servers, the dashboard) run through `runTrusted()`, from a written allowlist of call sites. No other module spawns processes. Instead of a lint rule, a test enumerates every module importing `node:child_process`, and every importer of `runTrusted`, against a written allowlist with a reason per module (`packages/sandbox/child_process.allowlist.json`, SEC-18; B1).
6. The sandboxed environment carries only `PATH, HOME, USER, LOGNAME, SHELL, LANG, LC_ALL, LC_CTYPE, TMPDIR, TERM, NODE_ENV, CI`, a private `TMPDIR`, the proxy variables when an egress proxy runs, and variables the caller names. API keys and tokens never enter it.
7. **Fail closed (S3b).** A host with no confinement mechanism runs no Worker command and no gate. The only opt-out is `SEKHEMET_ALLOW_UNCONFINED=1`; when set, every card's evidence bundle records `isolation: "none"`. No code path passes `requireConfinement: false` on the user's behalf.
8. The isolation level in force (`seatbelt`, `bubblewrap`, `none`) is recorded on every card and in its evidence bundle, and `sekhemet doctor` reports it.
8b. **Installed is not usable (R9, SEC-17c).** An engine counts as in force only once it can start a sandbox on this host. On Linux, once per process, the sandbox starts `/bin/true` under bubblewrap with a new session, `/proc`, and the namespaces a card's commands get, the network one included (`bubblewrapUnavailableReason`, `bubblewrap.ts`). If bwrap is installed but cannot start one, the isolation level is `none`:
   - item 7 refuses every command with bwrap's own error and the fix;
   - srt, which runs bubblewrap on Linux, is unavailable for the same reason.

   The known case is Ubuntu 24.04, whose `kernel.apparmor_restrict_unprivileged_userns` refuses unprivileged user namespaces unless an AppArmor profile allows them for bwrap (the README's Linux requirements give a one-line profile, `userns` for `/usr/bin/bwrap`; Ubuntu 24.10's own `bwrap-userns-restrict` is a stricter alternative). `sekhemet doctor` names the mechanism actually in force, and passes its escape probe only after a harmless command has run inside the sandbox (`judgeConfinement`, `doctor.ts`). *Found in R9:* before this, doctor counted bwrap's own start-up failure as the escape refused, and on Linux called the mechanism "seatbelt". Srt's missing-program match also accepts bash 5.2's wording for an absolute path (no `exec: ` prefix), so a missing program is `notStarted` under srt on Linux too.
8a. The harness, never the model, decides a sandbox's writable roots and working directory: from the card's record, canonicalised (symlinks resolved) before the profile is generated. A model-supplied `cwd` or path never widens them (the Codex CVE-2025-59532 class).

### macOS profile (Seatbelt)

9. Deny by default. Writes only to the granted roots and a private scratch directory. `.git` at any depth and in any case under a root is never writable (later rule wins).
10. Reads are allowed broadly except the user's secret-bearing paths, the workspace's `.sekhemet/events.db` wherever it lives (S3c; [kernel](kernel.md) rule 38a), and, item 10a's, the workspace's other state, the other cards' worktrees and every other project's root. The paths come from one table, `HOME_SECRET_PATHS` (`secret_paths.ts`), that every engine reads, so the Seatbelt, bubblewrap and srt lists cannot drift (B-2): SSH and GPG keys; cloud credentials (`~/.aws`, `~/.config/gcloud`, `~/.azure`, `~/.kube`, `~/.docker`); registry and git-host tokens (`~/.npmrc`, `~/.pypirc`, `~/.netrc`, `~/.git-credentials`, `~/.config/gh`, the cargo and gem credentials, `~/.pgpass`); the Sekhemet user directory (`~/.sekhemet`, `~/.config/sekhemet`, and wherever `SEKHEMET_CONFIG_DIR` points); keychains and password stores (GNOME Keyring, KWallet, pass, 1Password's CLI); browser profiles, the Flatpak ones included; AI tools' sign-ins (Claude Code, Codex, Copilot) and tokens kept inside otherwise readable caches (Hugging Face), `~/.vault-token`, Terraform's and hub's credentials. The session's sockets outside the home are item 15's. Toolchains and package caches stay readable (`homeToolchainPaths`), because a build needs them; build configuration that builds read (`~/.m2/settings.xml`, `pip.conf`, `.yarnrc.yml`) is not masked.
10a. **A card sees only its own project** (NEW-security-13; [DEC-57](../DECISIONS.md#dec-57--a-server-is-a-workspace-with-many-projects)). A server now hosts many projects ([teams](teams.md) item 5), and a person's level can be overridden per project, so a card must not become a way to read a project its person cannot see. Every engine therefore denies a card's command, gate and background process, for reading and writing, three sets of paths, named one by one and never the whole `.sekhemet/` folder, because a card's own worktree lives inside one (`<project root>/.sekhemet/worktrees/<card>`, `git_adapter.ts:228`; [runtime](runtime.md) item 2a):
   - **(a) the workspace's state**, wherever the workspace folder lies relative to the card's root: the ledger and every other database there (`.sekhemet/*.db` with its WAL and SHM files, as `ledgerReadDenies` already lists them, `seatbelt.ts:116`), and the blob, evidence, transcript, observation, live, log, run, process and backup folders, the locks and `daemon.json`;
   - **(b) the other cards' worktrees**: every `.sekhemet/worktrees/<card>` but this card's own, in its project's root and in any other;
   - **(c) the root of every other project** of the workspace.

   The card's own worktree stays readable and writable as its granted root (item 9), whether or not the workspace folder is also its project's root, which it is on every install made before DEC-57. A project root never lies inside another project's root or contains one ([teams](teams.md) TEAM-60), so (c) can never cover a card's own worktree. The paths come from the workspace's `projects` table and the running cards at the card's start, and join item 10's table for that run, so the Seatbelt, bubblewrap and srt lists cannot drift. The Worker's own file tools already resolve inside the worktree (`resolveInWorktree`).
11. *Not built (open, S3):* `mach-lookup` limited to an allowlist of services toolchains need, with AppleEvents and LaunchServices lookups denied. Today the native profile allows every `mach-lookup` but item 11a's keychain services, and srt's profile uses srt's own allowlist (DEC-39), which names `com.apple.coreservices.launchservicesd`. Both profiles start from `(deny default)` and allow neither `lsopen` nor `appleevent-send`, but no test has tried to open an application or send an AppleEvent from inside the sandbox (docs/research/SANDBOX_REUSE.md asks for that canary), so SEC-15's macOS clause is unproven and waits on this item.
11a. **No keychain from inside the sandbox** (SEC-23b; W2b finding, fix round F1). Under both engines a sandboxed command may not look up the services that hold or hand out keychain secrets, nor read a keychain file. The services are one table, `KEYCHAIN_MACH_SERVICES` (`secret_paths.ts`): `com.apple.SecurityServer` (securityd, every file keychain), every `com.apple.securityd.*` (secd's data-protection and iCloud keychains, the System keychain's daemon), the password and authorization agents (`com.apple.security.agent`, `.agent.login`, `.authhost`, `.authtrampoline`), the login password's stasher (`com.apple.security.KeychainStasher`), iCloud Keychain's (`com.apple.security.octagon`, `.kcsharing`, `.escrow-update`, `.cloudkeychainproxy3`) and CryptoTokenKit's (`com.apple.ctkd.*`, smart-card and Secure Enclave keys). Also denied, since no build needs them (fix round F1 review): iCloud Keychain's sharing messenger (`com.apple.keychainsharingmessagingd`) and escrow backup (`com.apple.SecureBackupDaemon*`), and the Touch ID and password prompts of `com.apple.LocalAuthentication.*` and `com.apple.CoreAuthentication.*`, which gate items with an access control and would let a card put a system password dialog in front of the person. The files are the user's keychains (`~/Library/Keychains`, item 10), the System keychain's directories (`SYSTEM_KEYCHAIN_PATHS`: `/Library/Keychains`, `/Network/Library/Keychains`), any file named `*.keychain` or `*.keychain-db` in any case, wherever it lies (`KEYCHAIN_FILE_SUFFIXES`), with the save file securityd writes beside one (`<name>.keychain-db.sb-<hex>-<random>`, `KEYCHAIN_SAVE_SUFFIX`), and the keychain `SEKHEMET_KEYCHAIN_FILE` names, by its path whatever its name (`keychainFileDenies`), since a keychain file can be made anywhere and its database, read out, can be attacked offline for its password. Such a name may not be written either — created, renamed, swapped, hard-linked or unlinked — so a keychain inside a granted root cannot be moved to a name the rules miss and then read; a clone (`clonefile(2)`, `cp -c`) of one, or of its directory, keeps a denied name. Seatbelt ranks a rule that names an operation above a wildcard one whatever their order, and srt allows `file-write-create file-write-unlink` in its roots by name, so the write denial names those two as well as `file-write*` (measured: with `file-write*` alone a rename and a create went through under srt). One text, `keychainRules()` (`seatbelt.ts`), is placed last in both profiles, where it wins over every allow before it: the native profile's broad `(allow mach-lookup)` and granted roots, and srt's own allowlist, which names `com.apple.SecurityServer` and `com.apple.securityd.xpc` with no setting to remove them; srt's profile is a single-quoted shell word in its command, so the rules go before the word's closing quote, and a command without that profile is refused, not run (`withKeychainRules`, `srt_engine.ts`). Certificate trust (`com.apple.trustd*`) stays reachable: TLS needs it and it holds no secret. *What this costs, measured* (`keychain_containment.spec.ts`, *the cost*, both engines): a card cannot sign with the person's code-signing identity (its key is a keychain secret; ad-hoc signing, what the linker does for every arm64 binary, and `codesign --verify` still work), and a program that lists the system's trust settings in its own process (`SecTrustSettingsCopyCertificates`, as Rust's `rustls-native-certs` does) gets none, where outside the sandbox it gets the system's roots (157 on this host, macOS 26); trust *evaluation* (`SecTrustEvaluateWithError`, the route of SecureTransport's `curl`, Go and `native-tls`; the test uses `security verify-cert` on a system root) still trusts a system root under the native engine, and under srt fails with or without these rules (srt's allowlist leaves out trustd). A card cannot create or rename a file named `*.keychain` or `*.keychain-db`. Git runs outside the sandbox and is untouched. Not yet measured: Chromium browser gates under these rules (Playwright's `--use-mock-keychain` is expected to keep them working) and Node's `--use-system-ca` (it lists no system roots on this host even outside the sandbox). *Residual:* a keychain file outside the home under a name no pattern matches, and not the one `SEKHEMET_KEYCHAIN_FILE` names, is readable and can be copied out, because Seatbelt judges a file by its path and never its content; its database could then be attacked offline for its password. Its items cannot be asked for from inside the sandbox (the services are refused), and Sekhemet's own items, in the login keychain or the `SEKHEMET_KEYCHAIN_FILE` keychain, are not exposed. *Not yet:* the native engine still allows every other `mach-lookup`; the allowlist of item 11 is open.
12. Network is denied except to the egress proxy's port, when one runs, and the card's own loopback ports.
12a. Unix sockets outside the grant are unreachable, with the network granted too (SEC-15a). Seatbelt's `(allow network*)` includes connecting to any Unix socket by its path — the ssh-agent at `$SSH_AUTH_SOCK` or launchd's agent sockets under `/private/tmp`, a gpg-agent, the Docker daemon — so a card granted the network refuses every Unix-socket connect, then allows its granted paths (its own dev server or test socket) and the system resolver (`SOCKET_CONNECT_ALLOW`: `/var/run/mDNSResponder`, every DNS lookup), then refuses the home secrets and session sockets of the shared tables again, even inside a grant (`unixSocketRules` in `seatbelt.ts`). Both engines use the same text: the native profile ends with it, and srt — whose open-network profile says only `(allow network*)`, its own Unix-socket rules applying only when it restricts the network — has it placed right after that line; a profile without that line exactly once is refused, not run (`withUnixSocketRules`, `srt_engine.ts`). With the network off Seatbelt refuses every socket.
13. `sandbox-exec` is deprecated by Apple. It stays the macOS mechanism behind the sandbox interface, with containment tests that fail loudly if its behaviour changes. This is a **recorded known liability** (open question 4): if Apple removes it, a Mac has no confinement, item 7 stops every card, and the fallback is a VM per card (§7).

### Linux profile (bubblewrap)

14. `--ro-bind / /`, writable binds for the granted roots, then every `.git` under a root (any depth) re-bound read-only; `--unshare-all`, `--die-with-parent`, `--new-session`, a private `/tmp` (S1/G2, S3).
14a. **Item 10's secrets on Linux (B-2).** After the writable binds, each existing path of the shared table is hidden: a directory behind an empty tmpfs, a file behind a read-only `/dev/null` (as srt does), resolved through symlinks to where it really lives; then the ledgers above each root the same way. A granted root that lies inside a masked directory is bound again after the mask, since the harness chose it (item 8a); nothing beside it shows. Under `denyHomeReads` the home is an empty tmpfs before the grants, with its toolchains bound back read-only. *Differs from Seatbelt:* a masked file reads as empty instead of refusing, and a masked directory is an empty, private, writable tmpfs whose writes vanish with the sandbox; a path absent when the command starts gets no mask, because bubblewrap cannot create a mount point on the read-only root. *Also differs, found in R9 (Lima, Ubuntu 24.04, both engines):* a write to a visible path outside the grant fails `EROFS` (the read-only root) where Seatbelt says `EPERM`, and a path under the host's `/tmp` is not seen at all (`ENOENT`, the private `/tmp`), so the containment tests keep their canary directories under `/var/tmp` on Linux, where the refusal is a real one; under `denyHomeReads` a key in the home reads `ENOENT` (the empty tmpfs) where Seatbelt refuses, each such test with a control proving the same path readable without the deny; and the command has its own pid namespace, so the pids it sees are not the host's (`confined.spec.ts` maps them through `NSpid` in `/proc/<pid>/status` before asserting `stop()` ended each). Under srt, `denyHomeReads` reads srt's own `vendor/` back with the toolchains (`srtFilesystem`): its `apply-seccomp` helper lies in Sekhemet's installation, usually under the home, and without it every command exited 127 with the home emptied — the `browse` tool's browser among them (R9; `confined.spec.ts` *denyHomeReads with the real home*).
15. Host UNIX sockets are unreachable. What a mount can hide is masked, whether or not the network is granted, since an empty network namespace does not isolate a socket reached by its path (`SESSION_SECRET_PATHS`, `sessionSecretDenies` in `secret_paths.ts`; bubblewrap mounts an empty tmpfs or `/dev/null` over each, srt receives them as `denyRead`):
    - `/run/user` (every session's runtime directory, with the D-Bus session bus that answers for the Secret Service and KWallet, gpg-agent, the keyring's ssh-agent, Wayland and the sound server), and the paths this session's environment names: `XDG_RUNTIME_DIR`, `SSH_AUTH_SOCK`, `GNUPGHOME`, tmux's socket (`$TMUX`, and `tmux-<uid>` in `$TMUX_TMPDIR`) and screen's (`$SCREENDIR`);
    - the system bus `/run/dbus` (logind, udisks and PackageKit power the machine off, mount disks and install packages for the active session without a password);
    - the daemons that are root on the host: both Docker sockets, `/run/podman`, `/run/containerd`, `/run/libvirt`, LXD's and Incus's sockets;
    - the smart-card daemon `/run/pcscd`, and screen's sessions `/run/screen`;
    - in the home (item 10), the 1Password and Bitwarden SSH agents' sockets.

    Everything under `/tmp` is gone with the private `/tmp`: X11's `/tmp/.X11-unix`, ssh-agent's default `/tmp/ssh-*`, tmux's default `/tmp/tmux-<uid>`. Under srt, seccomp refuses creating any `AF_UNIX` socket (the proxy is reached through sockets srt binds before its filter applies), so no Unix socket is reachable at all (DEC-39). *Residual, the native engine on Linux (fix round F3):* bubblewrap cannot filter a connect by path, so a socket at a path neither table names and outside `/tmp` stays reachable; and with the network granted the command shares the host's network namespace, and with it every abstract socket — X11's `@/tmp/.X11-unix/X0` (which a same-user Xwayland grant lets any process of the person's use: read keys, type into any window) and a session bus listening on an abstract address. Closing both needs srt's filter, which DEC-39 makes the default once both platforms pass, or the same `socket(AF_UNIX)` refusal added to the native engine's seccomp program, which would also refuse a card's own Unix sockets (a dev server's, a test's) — the owner's choice, not taken here.
16. The harness refuses to run git in a root whose `.git` it did not create itself (G6).
17. Linux runs bubblewrap, not Landlock ([DEC-21](../DECISIONS.md#dec-21--accepted-substitutions)); Landlock and seccomp are hardening layers on top.

### Git run by the harness (S1, G3)

18. The harness runs git outside the sandbox, at an absolute path, version ≥ 2.50.1, with `GIT_DIR` and `GIT_WORK_TREE` pinned from its own record of the worktree (`<main>/.git/worktrees/<name>`), so a rewritten `.git` pointer changes nothing. Every harness git call passes its arguments as an argument vector (`execFileSync("git", args)`, `runGit` in `packages/sync/src/git_adapter.ts`), never as a shell command line, so a model-authored commit message, card title or branch name never reaches a shell.
19. Pinned for every harness git call: `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GIT_NO_REPLACE_OBJECTS=1`, `GIT_OPTIONAL_LOCKS=0`, `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=true`, `GIT_PAGER=cat`, empty `GIT_ASKPASS`/`SSH_ASKPASS`, `GIT_CEILING_DIRECTORIES`; and through `GIT_CONFIG_*`: `core.fsmonitor=false`, `core.hooksPath=/dev/null`, `core.untrackedCache=false`, `core.sshCommand=false`, `core.symlinks=false`, `credential.helper=`, `gpg.program=false`, `commit.gpgSign=false`, `log.showSignature=false`, `diff.external=`, `protocol.file.allow=never`, `submodule.recurse=false`, `diff.ignoreSubmodules=all`, `safe.bareRepository=explicit`. Found in B1:
    - `include.path=` and `diff.external=` are not pinned. Git refuses an empty include given on the command line, and an empty external diff makes git try to run "" on every diff that prints a patch. The item 21 preflight refuses both in repository config instead, and every harness diff passes `--no-ext-diff --no-textconv`.
    - `core.symlinks=false`, `protocol.file.allow=never` and `GIT_CEILING_DIRECTORIES` are pinned only for git in a card's worktree (`guardedGitEnv`), never process-wide. In the user's own checkout they would write symlinks as text files and refuse local-path clones. `GIT_CONFIG_GLOBAL` points at a harness-written file holding only the user's `[user]` name and email, so commits keep the user's identity and a repository's own identity still wins.
20. `diff`, `log` and `show` run with `--no-ext-diff --no-textconv`; commits with `--no-verify`; nothing uses `--recurse-submodules`.
20b. **Closed in B1:** the review diff's difftastic now runs confined (`packages/sync/src/review_diff.ts`); before, `git -c diff.external=difft --ext-diff` ran it over worktree content outside the sandbox. A program the harness runs over worktree content outside the sandbox must be on a fixed allowlist, resolved by absolute path, run with the hardened git environment, no network, and time and memory limits; otherwise it runs confined. Carried by S3a.
21. **Preflight:** before git runs in a worktree, the harness reads its config with `--no-includes` and refuses on any of `core.fsmonitor|hookspath|sshcommand|pager|editor|askpass|gitproxy`, `filter.*`, `diff.*.(command|textconv)`, `merge.*.driver`, `include*`, `gpg.*`, `credential.*`, `remote.*.(uploadpack|receivepack)`; scans the worktree for embedded bare repositories (a directory holding `HEAD` and `objects`), `.git` files or symlinks below the root, and carriage returns in `.gitmodules` (CVE-2025-48384); and fails the card if the staged diff adds a gitlink (mode 160000) or a nested bare repository. *Scope (the lead's ruling under [DEC-42](../DECISIONS.md#dec-42--the-owner-delegates-the-outstanding-decisions-to-the-lead), B4.1):* for the read-only history secret scan of item 34c, a repository whose **only** finding is `core.hooksPath` (Husky's `.husky/_`) is scanned, because the scan only reads history and every git it runs has item 19's `core.hooksPath=/dev/null` on the command level — `GIT_CONFIG_COUNT` for its own git, `GIT_CONFIG_PARAMETERS` for gitleaks' (a hardened global file alone is outranked by the repository's own config) — so no hook can run; every other finding still refuses the scan, and the preflight still names the key.
22. "Already hardened" is decided by checking the keys are present, never by trusting an environment flag.
23. Consequence, stated to the user by `doctor` and the README: Sekhemet's own git commands never run git hooks or fsmonitor. The project's pre-commit checks belong in gates, run confined from the base branch's hook files ([review-git](review-git.md) owns Accept and LFS).

### Dependency trees (S2, G4)

24. The shared dependency tree is never writable from a card — `node_modules`, a Python `.venv`, and any other dependency directory the harness links into a worktree. Each worktree gets its own `node_modules` directory whose entries are links into the main checkout; caches (`.vite`, `.vite-temp`, `.cache`, `.tmp`) are created inside the worktree and deleted with it. A `.venv` is linked whole and read-only: an interpreter that cannot write bytecode caches there runs without them, and a card that needs a new Python package adds it through the supply-chain gate (item 44), not by installing into the shared environment. No write grant reaches outside the worktree.

24a. **Per-card worktrees.** Each card works in its own git worktree under `.sekhemet/worktrees/<card>`, the only writable root its sandbox is granted (plain worktrees, not copy-on-write clones: [DEC-21](../DECISIONS.md#dec-21--accepted-substitutions)).

### Permission engine

25. Three tiers, **Allow**, **Ask**, **Deny**; Deny wins. Allow: reads inside the repo, writes inside the declared scope. Ask: destructive commands (recursive force-remove, `git reset --hard`, `git clean -f`, `sudo`, `kill -9`, `chmod 777`), network commands to allowlisted hosts, external binaries not provided by the toolchain or the project. Deny: writes outside scope, paths that resolve outside the worktree, and protected paths — gate files, test globs the project protects, `.git` at any depth, `.githooks/`, `.sekhemet/` state and extension files (`hooks.toml`, `mcp.json`, `skills/`, `plugins/`), and the harness's own loop, gate runner and sandbox sources. The agent cannot override a Deny.
25a. **How an Ask is answered.** An Ask-tier call posts a `permission` decision request on the card — "Allow <tool>: <command or path>?", options deny and allow, recommendation deny — answered from the board, the CLI or `/api/decisions`. With no answer within 60 s (`approvalTimeoutMs`) the call is denied; with no approver attached (a headless caller) it is denied at once; either way the model is told why and not to retry. The Worker keeps its slot while it waits. In the Team setup only a person the project's Accept rule names may answer ([integrations](integrations.md) item 26, [teams](teams.md) item 7).
26. The engine decides on the **resolved** path (symlinks followed), not the string the model supplied.
27. The engine is a usability layer; the sandbox is the security boundary. No protection may exist only in the engine.

### Egress (S3)

28. One network policy, in the one schema [surface](surface.md) item 24 owns: `[network] mode`, `fetch_allow`, `fetch_deny` and `research`. `research` is **the one exception to `mode`**: it covers only the Researcher's harness-side requests (item 32), always through `NetworkPolicy` and logged, and it never reaches a sandbox (item 29a). The user's `config.toml` is authoritative; a project's `config.toml` may only add hosts to `fetch_deny`, narrow `fetch_allow` and set `research = "no"` for itself, never widen `mode` or `research`; `fetch_deny` wins over everything. A card's sandboxed commands are narrowed once more by the repository's `gates.toml` `[project] network_allow` (empty: the card's commands reach nothing), which can never add a host the effective `fetch_allow` lacks.
29. Offline is the default. With `mode = "offline"` no sandboxed command has a route out, and harness-side requests reach only loopback — except the Researcher's requests under `research = "yes"` (item 29a), the one exception to `mode`.
29a. **Research asks once** (the default of owner decision [O16](../../reference/OPEN_QUESTIONS.md#owner-decisions), pending). Research before building needs the network, and nothing may leave the machine without a person's yes. So the first time a person starts a new project, the harness asks one question — whether research may use the network — before any outbound request; the question and its effect are [design-stage](design-stage.md)'s (S8). The answer is recorded once, as `[network] research = "yes"|"no"` in the user's `config.toml` (the one authoritative source, item 28; [surface](surface.md) item 24), and applies to every later project without asking again; `mode` is not changed by it. A yes enables only the harness-side research requests of item 32, through `NetworkPolicy` and logged; it never opens a route for a card's sandboxed commands, which stay narrowed by `network_allow` (item 28). **What a yes reaches** (lead's decision, 2026-09-24, on the final check's F1): the hosts in the effective `fetch_allow` if that list is non-empty, otherwise any public host, minus `fetch_deny` — whatever `mode` says. So a yes never widens a list the person wrote: a person who chose `allowlist` gets no wider policy for research than for anything else. A project's `config.toml` may set `research = "no"` for itself (item 28), never `yes`. A no, or no answer, keeps research offline (NEW-security-8, SEC-52, SEC-52a, SEC-52b). **A yes covers exactly the research hosts its question named** (lead ruling, review of B4.5): the harness's own research hosts (`RESEARCH_HOSTS`: the registries, GitHub's API and the paper indexes) are reached only when the yes named them, recorded as `[network] research_hosts`; a host added later is asked about once, on a new project's plan, and is refused and logged until a yes names it ([design-stage](design-stage.md) DS-S8-8). Other hosts a yes reaches are as above.
30. With an allowlist, sandboxed commands reach the network only through the harness's proxy, whose list is the effective `fetch_allow` narrowed by `network_allow`, minus `fetch_deny`. The proxy: treats an empty allowlist as deny-all; canonicalises hostnames and rejects NUL bytes and non-hostname characters; resolves names itself and refuses loopback, private, link-local and metadata addresses after resolution; allows only ports 80 and 443; and records every request, allowed or refused, as a `card/egress` event with the SHA-256 of its payload.
31. The sandbox has no resolver of its own (DNS is itself an exfiltration channel).
31a. An allowlist names exact hosts. The proxy decides on the hostname the client supplies and does not inspect TLS, so a broad or upload-capable entry — a wildcard, a code host such as `github.com`, a registry's publish endpoint — is an exfiltration path: it is accepted only with a warning shown when it is added and recorded on every card that runs under it.
32. Every harness-side outbound request that input from the Worker or a repository can influence — registry lookups for the supply-chain gate, research fetches, repository clones — goes through one `NetworkPolicy` wrapper that applies the mode — or, for a research fetch only, `research` and `fetch_allow` as item 29a says — and logs to the ledger. Registry lookups never run inside a worktree (so a worktree `.npmrc` is ignored).
33. Integrations the user connected (GitHub, Slack, ntfy, OTLP) are allowed destinations because connecting them is the consent; they are still logged, and `offline` blocks all of them except loopback.
33a. **What leaves the machine is listed and shown** (NEW-security-11; FINDINGS INS-08). The records of items 30, 32, 33 and 47 are shown to people, not only kept. **The list:** the user guide's *Privacy and network* page is generated from the network policy's own host list — every host any code path can reach — naming for each its purpose, what is sent and the setting that turns it off; a test fails when code can reach a host the page does not list. **The view:** Configuration › Project › *Network activity* and `sekhemet egress [--since <time>]` read the recorded `harness/egress`, `card/egress` and `model/downloaded` events and list for each the host, the purpose, allowed or refused, the size, and the issue or person that caused it; with none recorded they say *Nothing has left this machine*. The view reads existing events and records nothing new. It shows a person only what their access lets them read, as every view does, and a private part erased by `ledger/erased` as erased. The card is [dashboard](dashboard.md) §2.16 item 5's (NEW-dashboard-24, DB-N24-1 to -3), the last card of Project configuration, because the approved mockup fixes Configuration's tabs (dashboard DB-N19-5) and the events are the project's ledger's; *the D1 review moved it from Configuration › Privacy, which no tab holds*. The guide page is the user guide's (C5).

### Secrets (S3c)

34. Command lines, observations, context packs, gate excerpts and evidence are redacted with the secret scanner **before** they are persisted or published. Redaction is the plan; erasure is the backstop: once the kernel's erasable `private` part exists ([kernel](kernel.md) NEW-kernel-1, hash chain v3), a secret the scanner missed can be erased without breaking the chain (item 34b). Until then the hash-chained ledger cannot be purged, so a secret must never reach it.
34a. **Nothing personal or secret is committable by accident.** Evidence bundles, transcripts, artifacts, research pages, observations, live token files, tuning data, traces and the queue report can hold names, prompts and redaction misses; the first run ignores all of them in `.gitignore` ([surface](surface.md) item 5.6, SUR-34). Only `config.toml`, `gates.toml` and documents exported for the team are meant to be tracked. Git history cannot be cleaned without rewriting every later hash, and forks keep the data, so no ledger erasure can reach a committed transcript.
34b. **A secret found after the fact** is handled in this order (erasure amends spine rule 2 — anything a model saw can be reconstructed *except content erased by a recorded `ledger/erased` event, which replay names as a gap*; owner decision O1, decided 2026-09-24, [DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue)): the person is told to rotate it first; then the affected `private` fields are erased with reason `secret` and every blob holding it is deleted; the evidence bundle keeps its identity because its gate excerpts and command lines sit in an erasable part whose commitment the bundle id covers (NEW-security-7; the mechanism is [kernel](kernel.md)'s, the bundle is [gates](gates.md)').
34c. **A taken-over repository's history is scanned for secrets, offline** ([design-stage](design-stage.md) §2.10, [DEC-43](../DECISIONS.md#dec-43--take-over-a-project)). Before anything from a repository someone else wrote reaches a prompt, every commit of its history is scanned: by gitleaks (MIT) as a confined subprocess when it is installed — run only after the item 21 preflight, with the hardened git environment of item 19 and its history read with item 20's `--no-ext-diff --no-textconv` (passed through gitleaks' `--log-opts`), so no repository filter, textconv or external diff runs during the scan, and with an explicit harness-owned configuration (the vendored gitleaks v8.30.1 rule file the bundled scan reads, so both report the same rule ids whatever gitleaks version is installed) and an empty ignore path, so the repository's `.gitleaks.toml` and `.gitleaksignore` cannot silence it (a repository shipping a `.gitleaksignore` is scanned by the bundled rules instead, since gitleaks honours one in the scanned directory); when the preflight refuses, the scan does not run and *history not scanned*, with the preflight's reason, is a finding — otherwise by the bundled offline rule set, which is gitleaks' own rule file vendored ([DEC-44](../DECISIONS.md#dec-44--what-to-reuse-for-the-rest-of-phase-b)), so both report the same rule ids; which one ran is recorded, and a vendored rule JavaScript cannot run is named in the scan's reason. **A scan that could not read the history is never a clean one:** any non-zero git exit (a dangling ref, a repository git refuses as of dubious ownership, a missing object) gives *history not scanned* (`scanner_failed`) with git's reason, never zero findings. Recon, failure reasons and half-done text read from the repository are passed through the secret redaction of item 34 before they are stored, public or private part. Nothing leaves the machine: TruffleHog-style live verification, which sends each candidate secret to its provider, is not used. A finding is recorded with its commit, path and rule and never the secret (item 34), and the person is asked to rotate it; history is never rewritten on Sekhemet's initiative (item 34a says why it cannot be cleaned).
35. Integration secrets — the Slack webhook URL and bot token, the push token, the SMTP password — live in the OS secret store: the keychain on macOS (`security`), the Secret Service on Linux (GNOME Keyring, KWallet, KeePassXC) through libsecret's `secret-tool`; each through the tool's standard input, never a command line, and read back to confirm (`keychain.ts`). Webhook URLs are secrets. Where there is none — no `secret-tool`, no keyring answering in the session (a headless Team server, typically), or `SEKHEMET_KEYCHAIN=off` — the product says so plainly, in `sekhemet doctor` (*Secret store*) and on Integrations where secrets are typed, and **stores nothing in cleartext without the person's explicit, recorded choice**: a secret is refused, and nothing is saved, until the person chooses on Integrations to keep secrets in a private file (`PUT /api/integrations/secret-store`, an Admin's in the Team setup), recorded as `[secrets] cleartext_file = "yes"` with its time in their config.toml and on the ledger as `config/changed` with the person (TEAM-44). With that choice, a secret goes to a file of mode 0600 inside a directory of mode 0700 in the user directory, which the sandbox cannot read (item 10). A secret an older file already holds in cleartext is left there (never deleted without the person), moves into the store on the next read where one exists, and does not block saving other settings. A secret the store holds but cannot give back on a read (a locked keyring, no session bus in an SSH session) is kept, in the store and in the file's list, by every write that does not replace or remove that setting. `secret-tool` is taken only from `/usr/bin` or `/usr/local/bin`, or the absolute path `SEKHEMET_SECRET_TOOL` names, never from `PATH`, which `npx` and `pnpm` put a project's `node_modules/.bin` in front of. The sandbox cannot reach the Secret Service's daemon either: its session bus lies under `/run/user`, masked (item 15). Research API keys (`BRAVE_SEARCH_API_KEY`, `TAVILY_API_KEY`, `SEMANTIC_SCHOLAR_API_KEY`) are read from the environment only and never stored. *Changed from the old design's "keychain only, never written to disk":* a Linux host without a secret service has no keychain, and a file the sandbox cannot read, chosen by the person, is the least-bad fallback. *Limitation:* the file is protected by file modes and the sandbox's read denial only, not encrypted; anyone with the person's operating-system account (or root) can read it. *Departure (fix round F1), the keychain's access list:* each item is still written with the default access list, which trusts the tool that wrote it, `/usr/bin/security`, so any process running as the person outside the sandbox can read it silently. An access list without it was considered and not adopted: the product reads its own items through that same tool, so every read — an unattended notification included — would raise a password dialog, and the only other programs it could name instead (`node`, `osascript`) run anything any process of the person asks them to, so they would protect nothing more. The boundary is the sandbox, which can no longer reach the keychain at all (item 11a, SEC-23b). A signed Sekhemet helper with its own code identity, named in the access list, would close this; it needs a signing identity and an installer, and is not in v1.
35a. **The credential store** (Team setup, [teams](teams.md) item 16) holds what people sign in with: password hashes (scrypt), passkey public keys and personal-access-token hashes, and the setup token's hash until it is used (the token itself is only in the 0600 file of [teams](teams.md) item 2). It is one file of mode 0600 in the server's data directory, in a directory of mode 0700 named by the workspace's id (`<user dir>/identity/<workspace id>/`, NEW-security-14; [DEC-57](../DECISIONS.md#dec-57--a-server-is-a-workspace-with-many-projects): nothing is shared across workspaces, so two servers of one operating-system user never share a store or a setup token), **outside `events.db`**, which the sandbox cannot read (item 10). It is included in every backup and restored with it, and **never exported**: no project export, audit export or tracker sync reads it. The event log records only that a credential was created, used, reset or revoked ([teams](teams.md) TEAM-11). An existing file with wider modes is corrected at start-up, as for item 35's token file.
36. The gate host's CA key is stored encrypted and certificates are valid for at most one year.

### Dashboard as an attack surface (S3c)

37. One guard at the top of the server (`web_guard.ts`), before any route or the Team identity layer: **Host.** A request whose `Host` is not a name this server answers to is refused with 421 and nothing runs, GET included (DNS rebinding: a rebound page names its own host). The names are loopback (`127.0.0.1`, `localhost`, `[::1]`), the bound address (a wildcard bind adds this machine's interface addresses, which no other site can own) and, in the Team setup, the host of `[identity] public_url`; a Team server behind a proxy that passes the public name on sets `public_url`. The names are fixed at start, so `serve` warns when a Team server bound off loopback has no `public_url` (`hostAllowlistWarning`): a proxy's or tunnel's name, a hostname or an address the machine gets later would be refused. A Host carrying anything but a name or address and a port (`evil@127.0.0.1`), a trailing dot, or none at all is refused; the refusal names no address. **Token.** In Solo every write (any method but GET, HEAD, OPTIONS) carries a random per-start token (256 bits) that the page receives from `GET /api/session` as `csrf` and sends as `X-Sekhemet-CSRF`, the field and header a Team session's token already uses (teams item 13); without it the answer is 403 `csrf`, with or without an `Origin`. A write with an `Origin` must also come from the page's own origin (another loopback port is another site). That Origin rule is the guard's, for every route, not left to each route; the Team setup applies it to every write too (a signed-in page on another loopback port is refused), and there a write with no `Origin` is a program's (a bearer token, the CLI), which a browser never sends. `X-Sekhemet-Action: 1` stays required alongside. `GET /api/session`, which carries the token, is answered with `Cache-Control: no-store`. The one exception is the GitHub delivery route (`/webhooks/github`), authenticated by its signature. No other site can read the token: the server grants no CORS and answers no other Host. **Streams.** `GET /api/stream` and the `/api/ws` upgrade check the Host, and an `Origin`, when sent, must be the page's own. **Headers**, on every response: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; style-src-elem 'self' 'sha256-…'; style-src-attr 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-src 'none'; worker-src 'none'; frame-ancestors 'none'` (the page's one inline `<style>`, its theme tokens, allowed by a hash taken from the page itself; style attributes, which run no code, allowed), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` refusing camera, microphone, geolocation, payment, USB, serial, HID, Bluetooth, MIDI and display capture, `X-Content-Type-Options: nosniff`, and `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` of `same-origin`. Binding and per-person sessions for the Team setup are in [runtime](runtime.md) and [teams](teams.md) (DEC-35).

### Workspace trust (S9)

38. Repository-supplied configuration that makes the harness run code outside the sandbox — `.sekhemet/hooks.toml`, `.sekhemet/mcp.json`, skill `scripts/` — is inert until the user trusts it. Plugins are not in this list because they are cut in B0, before workspace trust is built: nothing is loaded from `.sekhemet/plugins/` in any workspace ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O4; [extensibility](extensibility.md) item 29, EXT-28). [Extensibility](extensibility.md) lists what each gates.
38a. **Another agent's configuration is inert until a person approves it.** A repository may carry configuration for other coding agents — `.claude/`, `.cursor/`, `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.envrc`, and git hooks (`.githooks/`, `.husky/`, `.pre-commit-config.yaml`) — which another tool runs or obeys on open; one did so before its trust prompt (CVE-2025-59536). Sekhemet never executes any of it, never sources `.envrc` and never starts a server `.mcp.json` names, and its text reaches a prompt only as untrusted content (item 42). A person may approve a file. The approval is stored exactly as workspace trust is (item 39): in the user directory, keyed by the repository's real path and the file's SHA-256, never in the repository. A ledger event, `trust/agent_config_approved`, is only an audit record of it and grants nothing on replay. Only then may the file's commands and gotchas enter the draft playbook, and a changed hash is unapproved again. This holds for any repository opened, onboarded or taken over. Language servers and every other repository process start only after workspace trust ([surface](surface.md) item 9, SUR-56; [design-stage](design-stage.md) §2.10).
39. Trust is recorded in the user directory, never in the repository, keyed by the repository's real path and the SHA-256 of each trusted file. A changed hash is untrusted again, including after an Accept merges a Worker's edit to one of these files. In the Team setup only an Admin may trust a repository or approve another agent's configuration in it (item 38a; [teams](teams.md) item 6).
40. The trust prompt shows exactly what would run. Headless and non-TTY runs never trust implicitly; `--trust` must be given per invocation.
41. The Review evidence flags any diff to files that execute later outside the sandbox: the paths in item 38, `.githooks/`, `.husky/`, `.pre-commit-config.yaml`, `.gitattributes`, `.gitmodules`, editor and container task configuration (`.vscode/`, `.idea/`, `.devcontainer/`), `.envrc` (direnv), CI workflows (`.github/workflows/`), and **other coding agents' and tools' configuration, which another tool runs or obeys on the developer's machine**: `.claude/` (its `settings.json` hooks), `.cursor/`, `.mcp.json`, `.codex/`, `.windsurf/`, `.continue/`, `.github/copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md` and `mise.toml` — all matched without regard to case (NEW-security-1; `.envrc`, CI workflows and case-insensitivity added in the B1 review; the agents' configuration added by [DEC-55](../DECISIONS.md#dec-55--working-alongside-other-tools-the-ecosystem-report), NEW-security-12). A Worker's edit to one of these is code that runs later even though Sekhemet never runs it (item 38a): the next person to open the repository in that tool runs or obeys it.

### Untrusted content

42. Issue text, PR comments, fetched pages, synced data and imported rows (by origin — a card touched by an applied import is recorded `card/imported`, whatever its external reference; B4.9) enter prompts wrapped as `<untrusted_content source="…">…</untrusted_content>`, with a system contract that instructions inside issue no tool calls. A step whose context holds untrusted content cannot use Ask-tier or network commands.
42a. **The Worker's browser.** `browse` reaches only the card's own app on loopback, except on research cards; its pages are untrusted content unless loopback; the browser runs confined (item 4); it reads a page's text and its accessibility tree, and screenshots it — nothing else; a tool that clicks or types into a page needs the card's scope to name a URL allowlist, and its screenshots go to the evidence bundle.
42b. **Prompt injection has no model-level fix, and the v1 Worker has no refusals.** Abliteration removes the refusal direction while leaving capability intact, and shifts the model's judgement in untargeted ways; refusal training does not carry over to agents even when present. Policy is therefore enforced deterministically outside the model — the sandbox, scope-confined writes, egress denial, a person deciding every irreversible action (Accept, push, merge), and checkpoint rollback — and never relies on the Worker declining.
42c. **Tested against this Worker.** A fixed set of injection fixtures — issue text, fetched pages, file contents and gate output that instruct destructive or exfiltrating actions — runs with the configured Worker, and the sandbox must hold with canary markers absent (NEW-security-4).

### Restricted mode (`--restricted`)

43. For auditing an untrusted repository: the shell tool and every writing tool are removed from the catalog; the sandbox has no network; and nothing from the repository executes — no dev server, browser, language server, package gate, mutation run, hook or repository script. What runs is read-only inspection: the harness's own parse and outline of files (the TypeScript compiler, [DEC-20](../DECISIONS.md#dec-20)) and static checks the harness runs itself, never through a repository script. A structural diff preview joins once review-git's difftastic path writes nothing to the repository ([review-git](review-git.md) RG-S5-19): today it can run `git add -A` or `checkout` in the repository root when the worktree is gone ([review-git](review-git.md) §4), which an audit of an untrusted repository must never do.

### Supply chain

44. Before a dependency is added, the harness checks, and fails the card's security gate on: a name that does not exist in the registry (or the air-gap mirror) — hallucinated names are an exploited vector; a package first published fewer than 30 days ago (`MIN_PACKAGE_AGE_DAYS`), which needs a person; and a name within Levenshtein distance 2 (1 for names of four characters or fewer), or equal after removing separators, of an existing dependency or a widely used package (typosquatting). Each manifest is checked against **its own registry** — `package.json` against npm, `requirements.txt`/`pyproject.toml` against PyPI, `Cargo.toml` against crates.io, `go.mod` against the Go proxy — because a Python name checked against npm is not a check. The **download profile** is advisory, never blocking (a new or internal library sits below any useful floor): under 100 downloads a week on npm or PyPI, or 1,000 lifetime on crates.io (which reports no weekly figure), the gate reports the number for the reviewer; Go has no floor. Vulnerabilities are scanned offline with `osv-scanner`.

### Air-gap kit

45. With no network, a machine can install from source ([DEC-21](../DECISIONS.md#dec-21--accepted-substitutions)), calibrate ([models](models.md) rule 7: calibration measures only the local machine and needs no network), work cards, add mirrored dependencies and look up documentation.
46. **Mirrors:** an allowlist exported from the lockfiles (for pnpm, the store is filled from the lockfile with `pnpm fetch`, so `pnpm install --offline` works); the supply-chain gate resolves against it, so an unmirrored package cannot be installed — the correct default when there is no network.
47. **Models:** the harness never downloads weights on its own. Weights are downloaded only when a person explicitly asks, from the **Configuration page** ([dashboard](dashboard.md) NEW-dashboard-6; [models](models.md) NEW-models-7, NEW-models-12), where the harness recommends a model per role and a person chooses to download it; the published SHA-256 is verified before the weights are used, and a file whose hash differs is deleted, never registered (owner decision O2, decided 2026-09-24, [DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue); DEC-25 R7). The download is a harness-side request under the one network policy — logged on the ledger with its source, refused in `offline` mode with the reason shown on the page (item 29) — and weights never pass through a sandbox (NEW-security-9, SEC-53). In air-gap mode weights are copied in by hand. A manifest lists each approved model's checksum, quantisation, chat-template checksum and the tier it qualifies for; weights are registered only when both checksums match, and the qualification suite still runs on this machine, because a model that qualifies on one machine may not on another. A signed manifest is required in air-gap mode.
48. **Documentation:** a library's docs are prefetched into the research cache on a connected machine, exported as one bundle with its SHA-256, and imported on the air-gapped one — the same route carries the whole research cache. The bundle holds docsets and `llms.txt` snapshots at the versions the lockfiles pin, and is marked stale (and named by the self-test) when a lockfile changes after it was built (NEW-security-5).
49. **Updates:** by signed bundle (`ssh-keygen -Y`, namespace `sekhemet-update`), applied by hand, with a compatibility note for the event-log schema; the ledger is backed up before any update, and the log is never migrated in place without that backup. Skill updates travel the same signed route in air-gap mode (NEW-security-5). Plugins have no update route: they are cut (item 38).
50. **Self-test:** a full card run produces no outbound connection attempt, checked at the proxy; every gate command is runnable; every registered model loads; the docs index answers a known query. The result goes to the audit log.

### S1 — git metadata (remaining: G2, G3, G6)
*Harness git still honours most program-running config, and bubblewrap protects only the root `.git`.*

B1 comes before that table (T3, built in B2.1), so B1 adds the reason to today's closed list, `CARD_STOP_REASONS` (`packages/kernel/src/types.ts:72`), and T3 carries it into the table (confirmation review N7c).
- **SEC-2a** WHEN the harness records or compares a worktree's path, its repository's or its gitdir record THE SYSTEM SHALL compare them as one spelling — absolute, symlinks resolved (`/tmp` is `/private/tmp` on macOS), a relative gitdir record read against its own directory — so a repository named by a relative or symlinked path runs its cards, and only a pointer that names another gitdir stops one (live-test F18: `run_suite.mjs --work ../relative/path` stopped the first card with "no recorded gitdir for this worktree").

- **SEC-5** WHEN `SEKHEMET_GIT_HARDENED=1` is set but the hardened keys are absent THE SYSTEM SHALL apply them.
- **SEC-6** WHEN a card's staged diff adds a gitlink THE SYSTEM SHALL fail the card's integrity check.
- **SEC-6a** WHEN a worktree contains an embedded bare repository or a `.gitmodules` with a carriage return THE SYSTEM SHALL refuse to run git there and name the path.
- **SEC-6b** WHEN a tool call supplies a working directory or path outside the card's recorded root THE SYSTEM SHALL generate the sandbox profile from the recorded root only.

*Justification: taking over a project someone else wrote ([DEC-43](../DECISIONS.md#dec-43--take-over-a-project)) opens a repository whose agent configuration and history nobody here has read; another coding agent ran such configuration before its trust prompt (CVE-2025-59536). - **SEC-54** WHEN a repository carrying `.claude/`, `.cursor/`, `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.envrc` or git hooks is opened, onboarded or taken over THE SYSTEM SHALL execute none of it, source no `.envrc`, start no server `.mcp.json` names, and pass each file's text to a prompt only as untrusted content; WHEN a person approves one of these files THE SYSTEM SHALL store the approval in the user directory keyed by the repository's real path and the file's SHA-256, write nothing into the repository, record `trust/agent_config_approved` on the ledger as an audit record only, and treat the file as unapproved again once the hash changes; WHEN the approval store holds no entry for a file THE SYSTEM SHALL treat it as unapproved whatever the ledger or the repository says; and WHEN a person in the Team setup who is not an Admin tries to trust a repository or approve one of these files THE SYSTEM SHALL refuse and record nothing as approved.
- **SEC-55** WHEN a repository is taken over THE SYSTEM SHALL scan every commit of its history for secrets with gitleaks when installed and the bundled offline rule set otherwise, SHALL run gitleaks only after the item 21 preflight, with item 19's hardened git environment and `--no-ext-diff --no-textconv` on its history read, so that a fixture repository whose attributes name a textconv driver runs no driver, SHALL record *history not scanned* with the reason when the preflight refuses or when git or the scanner exits abnormally (never zero findings), SHALL read none of the repository's own gitleaks configuration or ignore file, SHALL make no outbound request for the scan or to verify a finding, and SHALL keep every secret out of the ledger, the evidence and the screen, recording only the commit, path and rule.

## 6. v1 acceptance

SEC-1 to SEC-37b, SEC-44 to SEC-53, SEC-N11-1 to SEC-N11-3 and SEC-N12-1 to SEC-N12-2 (including the lettered criteria; SEC-17a is B1's, with the rest of S3a; SEC-52 holds O16's default until the owner answers; SEC-50 and SEC-51 once [kernel](kernel.md) NEW-kernel-1 and NEW-kernel-7 land in B3.1 — erasure itself is decided, [DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O1), the `.gitignore` criterion SUR-34 in [surface](surface.md), plus these behaviours already built and to be kept under test:
- **SEC-38** WHEN a sandboxed command writes `<root>/.git`, `<root>/sub/.GIT/config` or through a symlink into `.git` on macOS THE SYSTEM SHALL fail the write and leave the target unchanged.
- **SEC-39** WHEN an allowlist is empty THE SYSTEM SHALL refuse every proxied request.
- **SEC-40** WHEN a step's context holds untrusted content THE SYSTEM SHALL refuse Ask-tier and network commands in that step without asking.
- **SEC-41** WHEN a card adds a dependency that is absent from the registry, younger than 30 days, or within the typosquat distance of item 44 THE SYSTEM SHALL fail the supply-chain gate and name the rule.
- **SEC-42** WHEN a signed update bundle is tampered with THE SYSTEM SHALL refuse it and leave the ledger untouched.
- **SEC-43** WHEN the containment suite runs in CI THE SYSTEM SHALL run it under a real bubblewrap on Linux as well as Seatbelt on macOS, with no test skipped on either. *Reading (R9, the lead; tightened after R9-L3's review):* a test that exercises a mechanism only one platform has — the keychain, macOS's session sockets, Seatbelt's own rules and its refusal of git metadata at any depth (DEC-49) on macOS; bubblewrap's masks and Linux's host sockets on Linux — is named platform-only in B1's runner (`PLATFORM_ONLY`, `appliesTo`, `scripts/milestones/b1.mjs`) and may be skipped on the other platform. Every other test must pass on both. A test counts only where it passed: skipped, failed or absent from a run it applies to is a gap (`acrossPlatforms`). The Linux half runs on a Linux host or in the Lima VM `SEKHEMET_LINUX_VM` names, with the tree identity taken before and after and the result not counted if it changed. Consequence: item 15's residual — the native engine's abstract socket with the network granted, skipped because it is known open — keeps B1 short of PASS until it is closed (srt as the default, DEC-39, or the native seccomp refusal).
- **SEC-43a** WHEN a card adds a Python dependency THE SYSTEM SHALL look it up on PyPI, not npm, and WHEN its weekly downloads are under 100 THE SYSTEM SHALL report the number as an advisory and not fail the gate for it.
- **SEC-43b** WHEN the Worker's tool sandbox is built with no explicit confinement setting on a host without a mechanism THE SYSTEM SHALL refuse the command.

## 7. Later

- **`@anthropic-ai/sandbox-runtime`, Smokescreen, nsjail/landrun, secretlint, `@napi-rs/keyring`** — proposals from the review; each needs the owner's yes. The profile requirements above hold whichever implementation is chosen.

- **Crypto-shredding of backups and exports** — deleting the `private` rows plus a declared backup window covers v1 (runtime's backup and restore re-apply erasures); per-subject keys add key management the product does not otherwise need ([research](../../research/DESIGN_RESEARCH_TEAMS_DATA_CHANGE.md) §5).
- **Plugin signing** — v1 has no plugins (cut, [DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O4); signing comes only with a plugin API ([extensibility](extensibility.md) §7).

## 8. Open questions

1. **Keep the `--validate-tools` execution path, or cut it?** *Decided 2026-09-24 (lead, on the confirmation review's M3): keep it, confined* — item 4a, SEC-17a, built in B1. Confining it under S3a removes the risk without cutting reachable code, which would need the owner; R6 stays `triaged`, so a validated candidate never becomes a Worker tool.
2. **Which mach services does the allowlist contain?** *Recommendation:* start from sandbox-runtime's published list, then add only what the frozen suite's toolchains fail without, each with a test.
3. **A repository's pre-commit hooks as gates** — run from the base branch's copy, confined. *Recommendation:* yes, owned by [gates](gates.md); until then `doctor` states that hooks do not run.
4. **The `sandbox-exec` liability.** Apple deprecated it years ago and offers no supported per-process replacement for arbitrary command lines. *Recommendation:* keep it behind the sandbox interface with loud containment tests (item 13, SEC-38); if a macOS release breaks it, confinement fails closed (item 7) and the VM-per-card route in §7 is researched then, not now.

5. **Husky's `core.hooksPath` and Git LFS's `filter.lfs.*` in the repository's own config.** *Decided in B1 (lead, on the B1 review; this spec's own recommendation):* the harness records the program-running keys the repository sets when a card's worktree is created, in its gitdir entry under the main `.git` where the Worker cannot write (`writeConfigBaseline`). The preflight refuses only keys that differ from that record. The pinned config already neutralises hooks, so the user's own setup is not the attack, and a key added or changed during the card still stops it.
