# Models: hardware, the registry and inference

## 1. Purpose

This subsystem runs the local models: it measures the machine, obtains and verifies the weights, launches and supervises the inference server, keeps the machine out of swap, and records which model, on which settings, is qualified for which role. It serves the product's promise that **v1 inference is 100% local**, and the spine rule that a result means something only with the settings that produced it: a number without its settings is not admissible.

## 2. Behaviour

### The v1 models

1. **In v1 every model runs on the user's machine** ([DEC-03](../DECISIONS.md#dec-03)). Cloud models are a planned post-v1 option per role, never a silent fallback. A local engine that forwards prompts to a cloud service does not make a model local: Ollama's cloud models are refused (rule 14c, [DEC-55](../DECISIONS.md#dec-55--working-alongside-other-tools-the-ecosystem-report)).
2. **The measurement-baseline Worker is Cyber-Tiel-Coder-35B-A3B MTP at IQ3_XXS** ([DEC-04](../DECISIONS.md#dec-04); *amended in C3: [DEC-47](../DECISIONS.md#dec-47--the-finish-line-decisions) O-5, the later ruling, makes nail-mtp the shipped and recommended Coding model (rule 3), and Cyber-Tiel stays the profile the frozen suite and the baseline run on*): 16,384-token context, 4,096-token answer cap, sampling from its model card (temperature 0.6, top_p 0.95, top_k 20, min_p 0), served by llama-server on port 8098 with `--jinja`, flash attention and KV at `q8_0`. It is uncensored (abliterated); the model's own card demands OS-level sandboxing, so the sandbox and permission layer is the only defence against destructive actions and every security item is v1-blocking ([security.md](security.md)).

### Getting the weights

4. **Named defaults are obtainable, never downloaded on the harness's own initiative.** Each default model has an acquisition source recorded in the component register and a SHA-256. The harness never downloads weights by itself ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O2; [security.md](security.md) item 47). A person may download a registry model in two ways that are **one implementation**: **Download…** on the Configuration page (rule 4c, NEW-models-12) and its terminal form, `sekhemet models fetch <model>` (NEW-models-7). Both are a person's explicit choice, never automatic; both verify the published SHA-256 before the file is used and delete a file whose hash differs; both are harness-side requests under the one network policy, logged on the ledger with their source and **refused in `offline` mode** with the setting named ([security.md](security.md) items 29 and 47). A default with no acquisition path is not a default. **Sources are verified, never guessed** (C3): a shipped row's repository, file, SHA-256, size and SPDX licence are filled only from a lookup that can be checked — the hub's tree API (the file's LFS SHA-256 and size) and its model card (`cardData.license`) — cross-checked against the hash the reference host's registry recorded, or computed from its copy; the download sources (`MODEL_SOURCES`) are derived from that one table (rule 8a). A role whose file cannot be verified ships with **no source** and says why: the person brings their own file (Configuration, or `sekhemet models add`). The terminal form takes a model, a role or the set: `sekhemet models fetch <model> | --role <coding|planning|research|review> | --recommended [--yes] [--folder <path>]`; a role with no shipped model (Review, while unfilled) is named and nothing is fetched.

### Finding, fitting and recommending models (NEW-models-12)

*The Configuration page ([dashboard.md](dashboard.md) §2.16, NEW-dashboard-6) is where a person points the harness at their models and chooses one per role ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O2, O3). This spec owns what the page shows about models; [measurement.md](measurement.md) NEW-measurement-5 owns the benchmark it runs.*

4a. **Scan the folders a person names.** The model folders are those a person adds on the Configuration page (kept in the user configuration), plus `--models-dir` and `SEKHEMET_MODELS_DIR` (rule 6). The page **suggests** the likely folders that exist on this machine and are not yet configured — `SEKHEMET_MODELS_DIR`; Ollama's model store; LM Studio's models folder; the Hugging Face hub cache; llama.cpp's cache — each added only when a person chooses it, and none scanned until then (MD-N12-8). Each folder is only read, never written, and nothing outside the configured folders is read. Scanning reads metadata only — headers and sizes — and **never loads a model**. A scan walks each folder and **identifies weights by their headers, never by loading them**: a GGUF file's header gives its architecture, name, quantisation (file type), context length, parameter count and, where present, its base model; a split GGUF (`-00001-of-0000N`) is one model; a vision projector (`mmproj`) is a companion of its model, not a model; a safetensors or MLX directory (a `config.json` beside its weight files) is listed with its format and, where no adapter serves that format on this host, the words "no engine here serves this format" (rule 14). A file that cannot be parsed is listed as unreadable with the reason. The SHA-256 is computed in the background after the scan, never blocking it, and a model is *Verified* only when it matches the registry's published hash.
4b. **Fit to this machine.** For each found model, and for each role, the scan computes its footprint — weights plus KV at the role's context and KV type (rule 10) plus the engine's buffers — against usable memory (rule 7), and labels it **fits**, **fits, swaps with the other roles** (it fits alone but not beside the resident roles, rule 22; the swap's time is shown from measured load times), or **needs N GB** (the shortfall, with the reason in words). A model that does not fit is listed, never hidden, and never loaded or benchmarked.
4c. **Recommend one model per role, with its reason.** For each role the recommendation is the best candidate that fits, chosen from (1) **quick-benchmark scores** for that role on this host ([measurement.md](measurement.md) NEW-measurement-5), when they exist for the current cache key, and otherwise (2) the model's **qualification record** (rule 27a) and **the registry** (managed defaults, family, tool arm, measured throughput); the Reviewer's candidates exclude the Worker's family and any model whose family is unknown (rule 3). The reason is one plain sentence naming its evidence (*"Gemma-4-26B-A4B: a different family from the Worker, which the Reviewer needs; it fits at 14 GB; no quick score yet"*). When the paired sign test on the two best candidates' per-item quick scores does not reject at 0.05 ([measurement.md](measurement.md) rule 35) — always, for the Planner and the Researcher, whose screens are too small to resolve correctness — the recommendation says they are indistinguishable on the quick benchmark and prefers the one with **the least time per card including swaps** (rule 20k), then the smaller footprint, then the registry default. A **combination** is recommended the same way: every role's quality floor first (qualified, and not worse on its evidence than a candidate it cannot be told apart from), then the least time per card including swaps, then the smaller footprint — **never a weighted combined score** (*amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap), the later ruling, which replaced the footprint-first tie-break and the combined quality score first proposed for Smart Swap (DEC-45)*). A role whose screen is `not_measured` (measurement rule 30a) is recommended from (2) alone. "Up to the strongest this machine can run": a registry model not present in any folder is recommended when it fits and beats every present candidate on its evidence, with **Download…** offered (rule 4); the recommendation never assigns, loads or downloads anything by itself.
4d. **Assigning is a person's act.** A person assigns a found model to a role, for their own use, on the strength of the quick benchmark or with no benchmark at all — it is their machine (rule 30a). The assignment needs only rule 27a's qualification on this host for that role, never a bake-off (rule 30a), is recorded on the ledger with the principal, and keeps the previous assignment restorable (MD-N10-2).
4e. **Downloads resume and fit** (NEW-models-18; FINDINGS CFG-18). An interrupted download keeps its `.part` file and resumes with an HTTP Range request, re-hashing the bytes it kept, so a failed 14 GB download does not start again from nothing. The kept bytes are hashed first, then `Range: bytes=<kept>-` is sent: only a `206` whose `Content-Range` starts at the kept length is appended; a `200` (a source that ignores ranges) starts again from nothing, and a `416` discards the kept file and starts again. A cancelled download keeps its `.part` too; a file whose final hash differs is deleted, as before. A download that needs more space than the destination volume has free (`statfs`; the need is the size still to fetch) is refused before it starts, naming both sizes; so is the recommended set as a whole. Before a person says yes to fetching the recommended set, the page and `models fetch --recommended` show the set's total size and each model's licence (`recommendedSetPlan()`); in a script `--yes` gives the yes, and with no one to ask and no `--yes` nothing is downloaded — silence is never a yes. The engine's download (rule 6b) follows the same rules through the same function (`downloadVerified(source, dest)`, `model_download.ts`).
5. **`doctor` verifies the weights** named by the resolved profiles — existence, readability and hash — before anything else reports green.
6. **Model folders are the only location setting:** the folders named on the Configuration page (rule 4a), `--models-dir` and `SEKHEMET_MODELS_DIR`. No other per-model environment variable is a configuration surface, and no path in shipped source refers to an absolute location, an external volume or an author's directory.

### The first hour: the engine and the floors (NEW-models-16, NEW-models-19)

6a. **The engine is found and its build checked** (NEW-models-16; FINDINGS CFG-01). First run and `doctor` find llama-server (rule 6b's order), read its build number and compare it with `minLlamaBuild`, which every shipped roster entry records — at least the build it was tested on, not only Spark's. Below the floor they say *llama-server bNNNN found; bMMMM or later needed*. When llama-server is missing they name this platform's fixes: **Get the inference engine** on Configuration where a pinned build exists (rule 6b), and otherwise Homebrew on macOS or, on Linux, the user guide's Install section (CUDA, Vulkan and ROCm builds). No fix names a file or page that does not exist; the Linux fix that pointed to the deleted `HARNESS_DESIGN.md` is the defect this replaces.
6b. **Get the inference engine** (NEW-models-19; [DEC-53](../DECISIONS.md#dec-53--design_gaps-c-decided) c7). A person who cannot use a terminal or Homebrew gets llama.cpp the way they get weights (rule 4): on a click, never on the harness's own initiative. The shipped source pins one llama.cpp release — at or above every shipped roster entry's `minLlamaBuild` — and, for each platform it covers, the asset (operating system, architecture and backend: Metal on macOS; CPU or Vulkan on Linux, as that release publishes them) with its SHA-256, recorded in PROVENANCE with its licence (MIT). *Get the inference engine* on Configuration shows the release, file, size and licence, and only after the person's yes downloads that asset from llama.cpp's own release through the one network policy (refused in `offline` mode, with the setting named), verifies the pinned hash before unpacking, deletes a file whose hash differs, and installs it under `<user dir>/engines/llama.cpp-b<build>/` — nothing outside the user directory, no administrator rights — recording `engine/downloaded {release, asset, sha256, bytes}` with the principal. Where no pinned asset fits the platform and its GPU (CUDA on Linux, for example), it says so and names the user guide's build instructions. llama-server is resolved in one order: `SEKHEMET_LLAMA_SERVER` when set, otherwise the newer of the downloaded engine and the one on `PATH` that meets the floor; `doctor` names which engine it uses and where it came from. A later engine is a new pin in a new release, never a download of "the latest".
   *Decided in C3 (DEC-56, design before build), where the rule was silent:*
   - **The pin** (`ENGINE_PIN`, `packages/models/src/inference_engine.ts`): llama.cpp **b10809**, the build installed and tested on the reference host (`llama-server --version`: build 10809) and the shipped set's floor (`ENGINE_FLOOR`, equal to `SHIPPED_ENGINE_FLOOR`; a test holds them equal and the pin at or above every shipped `minLlamaBuild`). Assets, each with the SHA-256 and size GitHub's release API publishes for the tag (read 2026-10-04): macOS arm64 Metal `llama-b10809-bin-macos-arm64.tar.gz`, Linux x64 CPU `llama-b10809-bin-ubuntu-x64.tar.gz`, Linux x64 Vulkan `llama-b10809-bin-ubuntu-vulkan-x64.tar.gz`; PROVENANCE repeats them. CUDA and ROCm on Linux, Intel Macs and Windows take MD-N19-3's path. The backend is detected (NVIDIA's driver → CUDA, `/dev/kfd` → ROCm, a Vulkan driver → Vulkan, else the CPU).
   - **Hosts**: the pin names `github.com` and its release-asset hosts (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`); the download follows each redirect itself, refusing a hop to any other host, a hop from https to http, and any hop `[network]` refuses, so every hop is decided by the one policy and recorded as `harness/egress` with the purpose *engine download* (a signed hop's URL is recorded as its origin only). Network activity lists those hops and `engine/downloaded`.
   - **Unpacking**, with no new dependency and no system tool: every pinned asset is a `.tar.gz`, read with Node's `zlib` and a tar reader (`parseTar`: ustar, pax and GNU long names, header checksums). Before anything is written, an absolute path, a `..`, a link whose target leaves the archive's folder, or an entry that is not a file, folder or link refuses the whole archive (zip-slip). The hash is checked again just before unpacking; files are written into a fresh `engines/.staging-<id>/` (never over a file, links last), the folder is moved to `engines/llama.cpp-b<build>/` only when its llama-server reports the pinned build, and the archive is deleted. *(The scoper proposed system `tar`/`unzip`; no pinned asset is a zip, and the reader avoids depending on which tar a machine has.)*
   - **The terminal form**: `sekhemet engine [status]` names the engine, where it came from and its build against the floor, with the fixes below it (exit 1 while missing or below the floor); `sekhemet engine get [--yes]` shows the release, file, size and licence and downloads only on `--yes` or a yes at a terminal (with neither, nothing, exit 2). Same implementation as the page (`config_engine.ts`): `GET /api/config/engine`, `POST /api/config/engine/get` with `{ confirm: true }` (PM_CONTRACT §3), and the card module `config_engine.js`.
6c. **The memory floor is stated** (NEW-models-16; FINDINGS CFG-06). **v1 supports 24 GB of memory and above** ([DEC-47](../DECISIONS.md#dec-47--the-finish-line-decisions) O-5). On a machine with less, first run and `doctor` say so, the person may continue at their own risk, and the 24 GB set is never presented as fitting (rule 9).
6d. **Ollama's role in v1 is stated where it is used** (NEW-models-16). The README names llama.cpp's llama-server as v1's engine. When `doctor` passes on an Ollama endpoint, it says which roles that endpoint serves under that statement, in the README's words, so `doctor` and the README never disagree.

### Calibration and tiers

7. On first run, and on a hardware change or on demand, `sekhemet calibrate` measures the usable memory budget (the Metal wired limit if set, else the driver default: two thirds of memory up to 36 GB, three quarters above; VRAM plus system RAM where expert offload applies), memory bandwidth, and for each candidate model prefill and decode throughput at several context lengths; it sweeps prefill batch size and expert offload and keeps the setting one step back from the memory cliff. The result is the machine profile, keyed by a hardware fingerprint.
8. The tier decides co-residency and parallelism, never a longer prompt:

   | Tier | Budget | Planner | Worker | Co-loaded | Working context | Parallel cards |
   | --- | --- | --- | --- | --- | --- | --- |
   | S | 16 GB | Same model, planning mode | Small MoE (~3B active) | n/a | 12–16k | 1 |
   | M | 24–32 GB | Dense, swapped on schedule | ~30B-A3B MoE | No | 16–24k | 1 |
   | L | 48–64 GB | Dense or mid MoE | ~30B MoE | Yes | 24–32k | 1–2 |

The Budget column is the machine's **installed** memory; usable memory decides what fits within the tier. Model names are absent on purpose: the registry fills them from measurement. Calibration never lowers the Worker's window below the size its measured prompts need.

### Inference settings

10. KV cache at 8 bits (`q8_0` or FP8); 4-bit KV is refused for a tool-calling model, and anything below 8 bits needs a qualification run with it. Flash attention on; prefill batch size swept per machine; expert offload only when the model does not fit, tuned to just below spill. Prompt-cache settings are [context.md](context.md)'s (`--cache-ram`, `--ctx-checkpoints`, `--checkpoint-min-step`, no `--cache-reuse`).
10a. **Batch size is a property of the host.** "One request at a time" holds only on the single-user profile. On a multi-user host the number of concurrent requests an engine serves correctly — its parallel slots or batch capacity — is read from that engine's qualification (rule 27a), never assumed, and cache and memory budgets are set per slot. How many cards run at once (one slot lease per qualified slot), and how model time is shared between people (fair share per person, interactive replies first, aging), is [runtime.md](runtime.md)'s NEW-runtime-6; this spec supplies the qualified capacity.
11. Sampling parameters, context window and reasoning support are stored **per model in the registry** and read from it; factories only supply defaults for an empty registry. *Amended by NEW-models-21 (C3-3, DEC-56):* a person's values are kept **per (model, role)** beside the model's own (`ModelEntry.roleSettings`), so the same weights may run Coding and Review differently; every value a role runs at is resolved by one function with its grade (*Measured*, *From its makers* (the model card's values; DEC-31 keeps *card* for a board's tile, so the page says *makers*), *Estimated*, *Default*, or *Set by* a person), and the roster applies the resolved values wherever that model runs that role (MD-N21-1, MD-N21-2). Every other component that sizes work by a model's window reads it from the registry entry of the **resolved** model, never from its own constant: in particular INVEST's *Small* is sized to the **resolved** Worker, not to the planner's 32,768 default (`planner/src/constants.ts:60`), which sized cards for a window the Worker does not have: it is one number, **the card's Zone 3 content fits Zone 3's cap at the resolved Worker's prompt budget — 3,792 tokens on the reference Worker** (16,384-token window) — measured once by the context allocator at the `ready` entry condition ([DEC-27](../DECISIONS.md#dec-27--context-budgets-are-fixed-in-tokens-at-the-reference-window); [context.md](context.md) rule 10, CX-N2-2; [kernel.md](kernel.md) rule 27; [planner-pm.md](planner-pm.md) §2.4). The earlier "25% of the window, 4,096 tokens of context pack" was a second number for the same check and is withdrawn (confirmation review N5).
12. Chat templates are pinned per model build by SHA-256; a template change invalidates that model's qualification.
13. **Speculative decoding is off until measured** on this host, per thinking policy — native MTP heads and a separate draft model (`-md`) alike. The measurement is an A/B on the same GGUF and the same server build, speculation on against off, replaying real Worker step prompts, reporting prefill seconds, decode seconds and total seconds per step separately, the draft acceptance rate and tokens per verify step, and the Metal working set. MTP uses two draft tokens (`--spec-draft-n-max 1 --spec-draft-p-min 0.0` (the model card's own sweep, which supersedes the earlier two-token figure; DEC-42)). It is enabled only where it lowers seconds per step **and** the qualification's tool-call checks still pass with it on, with prefix caching on as it runs in production — speculation and prefix caching are qualified together, never separately, because the combination has corrupted tool calls on another engine (vLLM issue #47194: prefix caching with MTP-3 on a Qwen3.6 hybrid left 2 of 10 tool calls correct, 0 of 10 needle recalls and 0 of 5 multi-turn tool conversations, while the path without MTP was correct). The decision is recorded in the registry with the engine, the host fingerprint and the thinking policy it was measured under. MTP speeds decode only and slows prefill, and agent steps are mostly prefill, so decode speed-up alone never justifies it.
14. **Engines are adapters, qualified per combination.** Every engine is reached through one OpenAI-compatible adapter. llama.cpp's server over HTTP is the baseline everywhere and the single-user default; Ollama is supported as a client, except for its cloud models (rule 14c, [DEC-55](../DECISIONS.md#dec-55--working-alongside-other-tools-the-ecosystem-report)); on a multi-user NVIDIA server **vLLM is the approved optional multi-user engine** ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O8: a separate process over its OpenAI-compatible API, Apache-2.0; llama.cpp stays the default) and the throughput path — SGLang stays *proposed* — because on a team server the engine choice is a throughput choice and on a laptop a memory choice. MLX exists only as an engine label (`bakeoff.ts:17`) with no adapter; an MLX path is Later. Choice is by measurement per machine, weighting cross-step cache retention above raw decode speed. No engine-specific assumption (a single slot, a llama.cpp flag) is allowed outside that engine's adapter.
14a. **Token streaming.** A request with a token callback streams the reply (`stream: true`, with usage in the final chunk for OpenAI-compatible servers) and hands each delta to the caller as it is decoded (`http_adapter.ts:711-725`, `:872-933`, `:956-964`). The runner writes the Worker's deltas to the card's live file, buffered and flushed every 250 ms, restarting the file at each new generation, which the dashboard's Steps view follows (`execute.ts:484-486`, `:683-700`; the stream route is [runtime.md](runtime.md)'s).
14b. **Every adapter answers a health check** (`healthCheck()`, `http_adapter.ts:747`): for an OpenAI-compatible server `/health` answering ok, distinguishing a server that is loading from one that is down, so a healthy machine with a model still loading is never reported as a dead model.
14c. **Ollama's cloud models are refused** (NEW-models-20; [DEC-55](../DECISIONS.md#dec-55--working-alongside-other-tools-the-ecosystem-report)). An Ollama model whose tag ends in `:cloud` or `-cloud`, or whose details from Ollama name a remote host, runs on Ollama's cloud service: the harness's request goes to Ollama on loopback and the prompt leaves the machine where the network policy cannot see it. Such a model is refused for every role — when it is assigned or added, and on every run of a role whose configuration already names it — with words that name the model and say that its prompts would leave this machine, and no request is sent to it. `doctor` fails that role's check with the same words. A cloud model per role remains the post-v1 option of rule 1, never this path.
15. **Server identity.** Before adopting a server already listening on a managed port, the adapter reads its `/props` and refuses it unless the loaded model path (and, for the managed Worker, the context size and MTP state) matches the profile. The evidence records the running server's reported settings and build, never the adapter's intended ones.
16. Per step, the adapter records prompt, cached, evaluated, thinking and answer tokens, `finish_reason`, and the draft statistics when speculative decoding is on.
17. The Worker server is started once and every card attaches to it; the harness never unloads a model another card is about to use. A model loaded from a slow external drive takes minutes, so load time is reported separately from card time.

### Memory safety

18. Memory pressure is read from the OS: the kernel pressure level and swap on macOS, PSI on Linux. Before each step the harness checks headroom and refuses the step when swap in use exceeds 6 GB or has grown more than 2 GB since the card started; the card then stops with `memory_pressure`.
19. **One watchdog, one set of thresholds** — this spec owns them; [runtime.md](runtime.md) and [security.md](security.md) link here. It polls every 2 s on every path that runs cards (`run`, `queue`, the daemon) and escalates through levels, each adding actions:

    | Level | Raised by | Actions (cumulative) |
    | --- | --- | --- |
    | **elevated** | kernel warning, or swap grown 0.5 GB since the run started, or used memory ≥ 0.85 | suspend speculative decoding at the next launch (falling back to plain decoding to reclaim KV headroom), stop new worktrees, shorten keep-alive (to 5 minutes), shed masked-observation caches |
    | **high** | kernel warning for 3 consecutive samples, or swap grown 1 GB, or used memory ≥ 0.90 | also throttle parallel cards to one, trim KV and prompt caches (erase the server's slots) and language-server symbol caches, and force the masking of older observations at the next step ([context.md](context.md)) |
    | **critical** | kernel critical, or swap grown 2 GB, or swap in use ≥ 6 GB, or used memory ≥ 0.94 | also pause: no new steps until pressure falls, state persisted to the ledger first (keep-alive 60 s — evicting mid-card forces a full reload) |
    | **emergency** | kernel critical for 3 consecutive samples, or swap grown 3 GB | also unload the models |

    Swap growth is measured from the run's own start, so stale swap from before the run is not its doing. It escalates on the first sample that warrants it and de-escalates only after consecutive calmer samples, so it does not flap. Every action a level lists is either acted on by the queue and the runner or removed from the list; today `stopNewWorktrees` and `shortenKeepAlive` are declared and never acted on, and the 0.90 stage's parallel-card, language-server and forced-masking actions do not exist (`watchdog.ts:43-54`; `memory.ts:20-56` classifies 0.85, 0.90 and 0.94 separately from the levels) (NEW-models-2).
    **Precedence over Smart Swap** (*amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap), the later ruling*): the watchdog comes first, its higher levels before its lower ones, then holds (`ModelHold`), then Smart Swap's policy (rule 20e). At `elevated` and above, the watchdog's keep-alive overrides a visiting model's minimum dwell and idle hold (rule 20e, C3), and prefetch (C10) is cancelled and not started. Smart Swap never overrides a watchdog action, and nothing preempts a step mid-step.

### Scheduling

20. The user declares the hours the machine is theirs, `[machine] reserved_hours`; the machine is also **reserved** while a person has pressed **reserve now** on the dashboard or run it from the CLI, until they release it ([runtime.md](runtime.md), [surface.md](surface.md)). The **overnight window** is the complement of `reserved_hours`, optionally narrowed by `[machine] overnight_hours`, and never includes a reserve-now period. In the overnight window the harness works the backlog, and while it is idle in the overnight window it keeps the next card's model loaded and its prompt cache warm. Model swaps are batched by project to preserve caches, and planning runs in scheduled blocks on tiers where the Planner and Worker cannot be co-loaded. The daemon and `overnight` apply this ([runtime.md](runtime.md)).
20b. **The overnight benchmark is scheduled here.** The overnight tier of the benchmark ([measurement.md](measurement.md) NEW-measurement-5, rule 37) runs only in the overnight window, and never while the machine is reserved — inside `reserved_hours` (not even when the person is idle: [runtime.md](runtime.md) item 17's idle exception is for queue rounds only) or during a reserve-now — nor while a card is running: it takes the runner lease ([runtime.md](runtime.md)) only when no card holds it, and while it holds the lease no card starts. By default the night's backlog goes first and the benchmark takes the rest of the window; the person may put the benchmark first when scheduling it. It stops cleanly at the window's end — at the current card's end, or at the window's end if that comes first, keeping every completed card and run — and resumes the next night from the card where it stopped, in the same block order; if the harness build, the context version or a model's qualification changed in between, the interrupted run is discarded and restarted, because a run mixing two builds is not comparable ([measurement.md](measurement.md) rule 5). It runs in **counterbalanced blocks** ([measurement.md](measurement.md) rule 37): all of one combination's cards for a run, then the next combination's, the order reversed on the second run — so the residency scheduler (rule 20a) swaps models **once per block**, never per card, while every card is still run by every combination and the comparison stays paired by card. **Benchmark blocks bypass Smart Swap's C1–C10** (rule 20e; *amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap)*): a block's swap happens at its start whatever `decide()` would choose, and no tour, threshold, aging cap or prefetch reorders or interrupts a block, because a comparison needs its order fixed; the watchdog still applies (rule 19).
20a. **One scheduler owns model residency.** Every caller that needs a model — the queue, the PM's chat, the dashboard, the Researcher, the Reviewer, a retry — asks one scheduler, through the runner lease ([runtime.md](runtime.md)), and never loads a model itself:
    - **Adapters are keyed by weights, not by role.** Roles served by the same weights share one adapter, loaded once with the largest context any of them needs; a context-size change never reloads the same weights behind the scheduler's back (Ollama reloads on every `num_ctx` change, invisibly to the swap count).
    - **Work waits in per-role queues** (plans, questions, reviews, research, chat) and a queue drains whenever its model is resident. Swaps are never made in the order questions arrive. **When to swap, and to what, is one pure function, `decide()` (rule 20e)**, which replaces the fixed plan order this rule first gave (*amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap), the later ruling*). That order — a Worker pass, then the Researcher for every unexplained struggle (one load), then the Planner and Seshat for plans, answers and reflection after the retries, then the Worker's retries: four loads where asking per question cost ten — is what `decide()`'s tours produce on that demand, not a rule of its own. The Reviewer's place is a tour's (rule 20e, C2 and C6); what the Reviewer does is [review-git.md](review-git.md)'s.
    - **Two large models are never resident at once** (rule 22): a load of a second large model is always refused, whatever the headroom shows; before any other load the scheduler checks what is resident plus what it would load against the measured headroom, admits a small model beside a large one only under rule 20g's admission (*amended by DEC-45*: headroom replaces usable memory), and refuses (queueing the work) when it does not fit or when a footprint is unknown. A question asked during an escalated retry waits for its model's step rather than loading the Worker behind the running session (~13.7 GB + ~12 GB on a 24 GB host is the out-of-memory path).
    - On a machine where everything fits (the 128 GB node), every model is resident and every queue drains as work arrives, with no code path changed.
    - Fair share between people and projects, interactive-first ordering, aging and per-slot leases are [runtime.md](runtime.md)'s (NEW-runtime-6); the scheduler here supplies residency, the per-role queues and the qualified capacity (rule 10a).
20c. **Smart Swap: every swap is measured, predicted and, when slow, flagged** (NEW-models-14). On the 24 GB reference host one large model is resident at a time, and the Worker (13 GB) loads from a USB drive in about five minutes, so a swap to Seshat and back can cost ten. The scheduler (rule 20a) therefore:
    - **Loads when it says so, and times it.** Making weights resident loads them then (the adapter's `load`), not on the first request, so the scheduler measures the load it ordered. A server that was already serving the weights is adopted, not loaded, and nothing is recorded for it.
    - **Records every load and unload on the ledger** (`model/loaded`, `model/unloaded`, and `model/first_token` for the first reply after a load), structural fields only: the weights, the queues they serve, the volume the weights file is on (`internal` or `external`: a file on another device than the home directory and the root is external), its bytes, whether the OS file cache was `cold` or `warm`, the unload, load and first-token milliseconds, and for a load its `engine` and `loadMode` (rule 20h; *amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap)*). **Warm** (*amended by DEC-45*: this rule is now the prediction made before a load; the recorded state is measured, rule 20d) means the same weights were unloaded less than 15 minutes ago and the other weights loaded since then fit in the file cache beside them (cache capacity is taken as usable memory, rule 8); anything else, including weights never unloaded before, is **cold**.
    - **Predicts each load** per weights, volume and cold/warm (the volume is judged by device: a weights file on the same device as the system or home directory is internal, any other external — never by a path prefix): the median and p90 of the last 20 recorded loads once there are at least three. Before that it states an estimate: 5 s of startup plus the file's bytes at the volume's read rate — measured as the median rate of the cold loads recorded on that volume, any weights, and until one exists the stated defaults of 2 GB/s internal and 40 MB/s external (about 5.4 minutes for the Worker from the USB drive); a warm load reads at 4 GB/s. The estimate is labelled as one.
    - **Flags a slow load** (`model/slow_load`): with at least three recorded loads, a load past 1.5 × the p90; with fewer, a cold load over 120 s or a warm load past 1.5 × its estimate. The flag names the likely causes — the weights on an external volume, memory pressure (kernel level warning or worse at the load's start or end), swap in use (1 GB or more at the load's end), a cold file cache — and the fix for each: copy the weights to internal storage; free memory; pre-warm the model overnight. It reaches a person through the notifier as a low-priority `slow_load` notice, deduplicated per weights, within the day's notice budget; the dashboard's view of swap costs is B4.1.
    - **The policy that uses these numbers** is rules 20d–20k ([DEC-45](../DECISIONS.md#dec-45--smart-swap), *Smart Swap*): the whole team of roles gets the most accepted work per hour on one memory-bound machine by swapping only when it pays in round-trip cost, keeping people answered, using memory to its safe limit, and helping a person choose models, engines, placement and combinations from measured facts. **D** below marks a design value of ours, set before any measurement and changed only by the replay admission of [measurement.md](measurement.md) rule 16a; every D value and the load mode are calibrated on the first nights the owner permits model loads ([measurement.md](measurement.md) rule 16d).
20d. **Smart Swap's cost model: what a swap costs, in round trips** (NEW-models-14). Every threshold of the policy derives from measured cost, so moving the weights to faster storage re-tunes the policy without a code change.
    - **C_pair(r)** is the round trip that serving role r costs the resident role, in both directions: the resident's unload and r's load, then r's unload and the resident's reload; the first-token time above steady state after each load (the median `model/first_token` after a load, less the median first-token time of warm requests on the same weights); for every live session on either side (Seshat's thread, a card mid-attempt, each of the N slots), min(K, R), where K is the measured time to restore its saved slot and R the time to re-prefill its prompt at the measured prefill speed; and the idle slot-seconds the swap leaves, × N parallel slots ([runtime.md](runtime.md) RUN-35).
    - **Load time L** is kept per (weights, volume, engine, load mode, cold or warm), from the ledger (rule 20c). **Decisions use the p90**, so the policy errs toward fewer swaps; **predicted waits use the median**. After three consecutive loads above the p90, the baseline is re-taken from those loads onward, because the drive or the placement changed. With no history, the estimate is a 256 MB sequential read probe of the volume, plus the drive's spin-up when it had spun down, shown as ±50%; it replaces rule 20c's stated default read rates wherever a probe can run.
    - **Cold or warm is measured, never assumed.** Before a load, a small trusted helper reads the file's page-cache residency (`mincore`); where it cannot run, the load is classified after the fact by its effective read rate against the volume's cold rate. The page cache's capacity is physical memory − wired − anonymous, so after any large swap on 24 GB the other model is almost never warm. Rule 20c's 15-minute rule stays only as the prediction made before a load, with that capacity.
    - **Work W(r)** is the sum of the predicted service times of r's queued requests: prefill tokens at the measured prefill speed plus decode tokens at the measured decode speed, per engine. Prefill dominates: the owner measured about 80% of a 47 s turn as prefill. Before a benchmark, decode speed is estimated as efficiency × the host's memory bandwidth ÷ the bytes read per token (the active bytes, for a mixture of experts), with an efficiency per engine calibrated on the host: about 0.6 for llama.cpp and 0.85 for MLX, as measured here (this replaces MD-N13-3's single 0.8). Escalated retries count in the Planner's W, because they run on the Planner's weights.
    - **θ, the swap-overhead ratio**, is swap time ÷ wall time over a rolling hour, recorded and shown; **θ_max = 0.2** (D).
20e. **The policy is one pure function, `decide(snapshot, now) → action`** (NEW-models-14). It is called at every step boundary and shared by the live scheduler and the simulator (rule 20j). The snapshot holds the resident set, the queues with their ages and predicted service, the holds, the costs of rule 20d, the memory measures of rule 20g, presence and the plan; the action is one of keep, swap (to named weights, with the tour), unload, prefetch or wait. It reads nothing outside the snapshot and writes nothing: the residency scheduler (rule 20a) applies the action, and `residency.ts`'s real-time pump and static order rank are refactored behind it. Nothing ever preempts a step mid-step. **Precedence** — one order, highest first; when two rules disagree the higher one decides, and every request a decision delays carries its predicted start:
    1. **the watchdog** (rule 19), at every level;
    2. **holds**;
    3. **C5**, the Worker's floor of (1 − θ_max) of each rolling hour while its queue is non-empty;
    4. **interactive requests** (a person waiting): when serving the full answer would break C5, the person gets rule 20f's quick path — a deterministic answer from the ledger, or the quick model when headroom admits it — and is shown the full answer's predicted start;
    5. **C7**, the storm cap, which applies to non-interactive swaps only and is counted in round trips;
    6. **C4**, the non-interactive aging caps;
    7. **C3**, the idle hold, which ends as soon as another queue has work;
    8. **C1**, the threshold.
    - **C1. Exhaustive service with a threshold.** The resident model serves while its queue has work; while a queue run's pass is under way, the Worker's remaining cards in that pass count as its queued work, so other roles batch toward their threshold or cap instead of taking one swap each (a research or escalated card running alone clears it) (lead ruling, DEC-42). Another role r is loaded only when (a) the resident queue is empty, (b) W(r) ≥ C_pair(r) ÷ θ_max, or (c) one of r's requests has reached its aging cap (C4). **Hysteresis:** (b) must still hold at the next step boundary.
    - **C2. Tours.** When the Worker must yield, one absence serves every queue past 50% of its cap (D): the shared weights first (Seshat, the Planner and escalations, one scheduling unit, MD-N9-1), then the Reviewer, then the Researcher. A horizon optimiser orders the tour: it enumerates the orders of the next H visits (H = 4, D; at most 4! = 24 orders) and takes the one with the least predicted total time that meets every cap, using a MIP solver only when the space grows; when no order meets every cap, the precedence above decides and the predicted waits are stated. Where several models are resident, the one evicted is the one whose next use in the plan is farthest (Belady), least recently used only when there is no plan. The next role is predicted from each card's state (verify → the Reviewer; blocked → Seshat or the Planner; a research card → the Researcher) and the plan.
    - **C3. Rent or buy.** A visiting model's idle hold and its minimum dwell both equal C_pair, the round trip its next request would otherwise cost. The idle hold ends as soon as another queue has work (the precedence above). The watchdog overrides both (rule 19).
    - **C4. One aging mechanism.** Each request class has a cap: **interactive** (a person waiting on Seshat) 2 minutes; **Planner** 30, **Reviewer** 45 and **Researcher** 60 minutes (all D); **Worker steps** [runtime.md](runtime.md)'s `max_wait_s`. It unifies RUN-34's `max_wait_s` and these caps; there is no second aging rule. **Feasibility:** a cap below C_pair cannot be met; it is flagged on the model page, and the person sees the predicted wait instead. **When θ exceeds θ_max**, the non-interactive caps stretch by θ ÷ θ_max (never the interactive one) and the placement notice is raised (rule 20k).
    - **C5. The Worker's guarantee.** While its queue is non-empty, the Worker is resident for at least (1 − θ_max) of each rolling hour, so a chatty conversation cannot starve the cards; a request that would break it is answered as rule 20f says.
    - **C6. Presence-aware reviews.** While a person is present — inside `reserved_hours`, during a reserve-now, or with a dashboard session active in the last 10 minutes (D) — reviews of finished cards rank first after interactive requests, because they block acceptance and the human is the rate limiter. In the overnight window, reviews batch into one tour whose predicted end (the median) comes before the reserved hours start.
    - **C7. The swap-storm cap:** at most max(1, ⌊θ_max × 3600 ÷ C_pair⌋) **round trips** in a rolling hour — never fewer than one, so on a slow drive where one round trip exceeds the Worker's absence budget the other roles are still served once an hour (lead ruling, DEC-42), counting non-interactive swaps only (it matters on a fast SSD, where C_pair is small). A **round trip** is one visit: the swap away from the resident model and the swap back to it (or to the next resident, when a tour continues), counted once, at the swap away, and costed as one C_pair. Past the cap no non-interactive swap is decided, only the watchdog unloads, and requests wait with their predicted start; an interactive request is ranked above C7 and bounded by C5 instead.
    - **C8. Parallel slots** ([runtime.md](runtime.md) RUN-35): the Worker's holding cost is multiplied by its N running slots. A swap waits at a **drain barrier**: once it is decided, no new step is admitted on any slot, and the swap happens when every slot has reached its step boundary. The slot saves of rule 20i cover all N slots.
    - **C9. Overlap:** while a model loads, the CPU-side work of queued cards runs (tests, gates, context assembly, the repo map, language servers), so a load never idles the machine.
    - **C10. Prefetch:** the successor's weights are warmed into the page cache only from free memory minus a margin (2 GB, D), and never while the watchdog is above `normal`; a pre-warmed cache never counts in the watchdog's used ratio.

    The policy's version (`smart-swap/1`) and every parameter above form one recorded object, `SwapPolicyParams`, carried in every evidence bundle and `RunProfile` ([measurement.md](measurement.md) rule 9a). Every event Smart Swap adds — `measure/calibration`, the load-mode A/B record, the θ record, the copy record — is registered in the kernel's payload registry as structural only (MD-N14-40a).
20f. **Seshat while the Worker runs** (NEW-models-14). A person who writes to Seshat during a card would otherwise wait out a round trip of minutes. They are answered in this order:
    - **(a) Deterministic answers, with no model,** from the ledger and the board: status, where the cards stop, what waits on the person, and every predicted wait.
    - **(b) A quick answer,** only when measured headroom (rule 20g) admits a small model a person has named as the quick answerer (a setting of the Planner role, not a fifth role: rule 24). It is labelled *quick answer*, is informational only, is given no tools, and **may never create or change cards, plans, proposals or decisions**, because it is not qualified for the Planner's work (rule 27a).
    - **(c) The full answer,** queued under the interactive cap (C4) with its predicted wait in words (*I'll answer in about 4 minutes: the Worker is finishing a step, and switching takes about 3*) and a hold for the thread. The thread's KV slot is saved on swap-out and restored on return (rule 20i).
20g. **Memory: space-aware co-residence** (NEW-models-14).
    - **Headroom** is the lower of two measures, both taken at each admission. **GPU:** `iogpu.wired_limit` − the Metal in-use system memory (ioreg `AGXAccelerator` `PerformanceStatistics`, which counts every process, the owner's included) − 1 GiB − the peak compute buffer. **System:** total − (wired + anonymous + compressor-occupied) − about 3 GB for macOS − the peak of the harness, the language servers and tests. The owner measured the GPU as the binding limit here: Metal timed out while macOS showed 88% free.
    - **Our servers** are measured by their `phys_footprint`, because their memory-mapped weights can hide as file-backed.
    - **Admission:** a load is admitted only if its footprint is at or below the headroom **and** the projected used ratio stays at or below **0.80** (5 points under the watchdog's `elevated`) on **both** the GPU measure and the system measure, and swap is not growing.
    - **Cumulative feasibility:** every transition a decision implies — each unload, load and restore of a tour, not only its end state — is checked against the sum of what would be resident at that moment: weights + KV + engine state (compute buffers) + prompt cache ([Latency-Aware Orchestration for Multi-Agent LLM Workflows, arXiv 2609.03335](https://arxiv.org/html/2609.03335): cumulative feasibility checking; DEC-45). A tour with any infeasible transition is not chosen.
    - **The owner's own processes** (such as a Hermes server on 8080, or Ollama) are read by pid and never unloaded; a refusal names them (*Hermes on 8080 holds 9 GB*). For a model Ollama keeps alive, the scheduler waits for the expiry `ollama ps` shows rather than refusing.
    - **No two large models** (rule 22): a model is *large* when its footprint (weights, KV at its context and KV type, and compute buffer) is at least a quarter of the GPU wired limit (D; 5 GB on the reference host). A second large model is **always refused**, whatever the headroom shows; only a small model (footprint below a quarter of the GPU wired limit) goes through admission to sit beside a large one. `CO_RESIDENT_MIN_BYTES` is derived from the measured footprints, not fixed at 32 GB.
    - **A calibrated GPU ceiling:** when a co-residence fails with a Metal command-buffer timeout, its combined GPU footprint is recorded as this host's ceiling, and any later co-residence at or above it is refused, naming both models and the ceiling. **The reference host's ceiling is pre-seeded from recorded evidence:** known-bad, an 11.8 GB target beside a 3.85 GB draft model (15.65 GB combined) gave a Metal timeout on the base M4; known-good, the Worker at a 16K context (about 14.5 GB footprint); and a dense 27B's weights were stable at 11.9 GB and exhausted swap at 13.7 GB. **Until calibration** (the calibration nights, [measurement.md](measurement.md) rule 16d) any combined GPU footprint above the known-good maximum plus **0.5 GB** (D; 15.0 GB here) is refused, naming the seed it passed; a calibrated ceiling then replaces the seed.
20h. **Load mechanics, chosen by measurement** (NEW-models-14).
    - **The load mode** per volume and engine — mmap, `--no-mmap`, or a sequential pre-read then mmap — is chosen by an A/B recorded on the ledger, of at least three loads per mode; until one is recorded, mmap. It matters on USB: on 2026-09-26 the drive read the Worker's 13.6 GB sequentially in 130 s (105 MB/s), while llama-server's mmap load from it took about 300 s (about 43 MB/s effective), so page-fault reads cost more than half the load, and a pre-read or `--no-mmap` should roughly halve it even without a copy.
    - `--mlock` is never passed (it crashes on macOS), and no direct I/O is used.
    - `--fit`'s silent context shrink is detected and refused (MD-M4-1).
    - The prompt cache (`--cache-ram`) is sized from the headroom, never llama-server's 8 GiB default.
    - A drive that has spun down or been disconnected is detected before a load (the file present, a small timed read), so the prediction includes the spin-up, or the load is refused and the work stays queued, saying why.
    - A model served through Ollama whose served quantisation or weights hash differs from the file is flagged as requantised (Ollama silently requantises an IQ3_XXS file); llama-server is preferred where exact weights matter.
20i. **KV slots and prefix state: the first latency lever** (NEW-models-14). The owner measured time to first token fall from 27.66 s to 0.88 s by caching a static prefix. Live sessions (Seshat's thread, a card mid-attempt, all N slots) and each role's stable prefix (system prompt, repo map, dossier) are saved per model through llama-server's slot save and restore (`--slot-save-path`; `POST /slots/<id>?action=save|restore`) when their weights leave, and restored on return when K < R; before a slot's first save, K is estimated from the slot's size at the volume's read rate. Restoring **a card's live slot mid-attempt** counts as able to change the card's output until an equivalence check passes on a calibration night ([measurement.md](measurement.md) rules 16a and 16d); until then that card re-prefills on return. They are **caches, never evidence**: each file is keyed by (weights hash, engine build, context, KV type, template), and one whose key differs is never restored; no decision reads them; and a slot file whose prompt text a `ledger/erased` event covers is deleted (the spine: erasure).
20j. **The closed-loop replay simulator** (NEW-models-14). It runs the real `decide()` under a virtual clock, with fake adapters whose load and first-token delays are sampled from the recorded distributions with a seed, and a fake memory probe. It is closed-loop: a card's completion generates its review demand; escalations follow failures as recorded; Seshat's arrivals replay as think-times after the previous answer, not as wall-clock stamps; reserved hours and presence replay from the ledger. It reports θ; wait p50, p90 and maximum per class; accepted cards per hour; the maximum age; and swaps per hour. A parameter or policy change is adopted only by [measurement.md](measurement.md) rule 16a's scheduling row. Until real loads are recorded, it runs on fixture histories with this host's measured load times.
20k. **Placement, and choosing by time per card** (NEW-models-14; built in B4.1). The largest single gain is where the weights sit: every role's weights on the reference host are on the USB drive, where a round trip cost about ten minutes. The model section of Configuration ([dashboard.md](dashboard.md) §2.16) offers **copy to internal storage**, chosen as a knapsack: a copy's value is swaps per day × (L_external − L_internal) ÷ GB, and at least 20 GB of internal space is kept free for swap files and worktrees. Only a person's click copies; the copy is hash-verified, the registry points to it, and the original stays; the registry prefers an internal copy with the same hash. The page shows a combination's **time per card** as E[attempts] × compute + E[swaps] × C_pair, with E[swaps] from a closed-loop replay (rule 20j) of the person's last N cards' demand under that combination (median and p90, labelled an estimate while N < 20: a weaker Worker means more retries, reviews and swaps), and rule 4c recommends by it. *Measured 2026-09-26:* with the owner's approval the Worker's weights were copied to internal storage, hash identical and the USB original kept; the internal SSD reads about 3.4 GB/s, so the Worker's weights read in about 4 s, and a load from it is expected to be dominated by server start-up and Metal buffer setup (to be measured on the first permitted load). The registry and `SEKHEMET_MODELS_DIR` still point at the USB drive until a person repoints them.
20l. **Two projects on one machine** (NEW-models-17; FINDINGS REL-07). Each repository has its own runner lease, so residency must be guarded across them: before any process loads or unloads weights it holds a machine-wide model lease, `<user dir>/model.lock`, taken by exclusive open with the holder's pid and process start time, exactly as the runner lease is ([runtime](runtime.md) item 3). While another process holds it, a process attaches to the engine already serving a matching profile (rule 15), or else waits and says which project holds which model. A second `serve` takes the next free port and prints it; `daemon status --all` lists each project's server and port ([runtime](runtime.md) items 5a and 23). *Read with [DEC-57](../DECISIONS.md#dec-57--a-server-is-a-workspace-with-many-projects), the later ruling:* a server is a workspace of many projects, and its runner lease is the workspace's, shared by its projects in turn ([runtime](runtime.md) items 2 and 4b). So this rule governs two or more servers — workspaces — on one machine, and *project* in it and in NEW-models-17 means a workspace's server. The lease itself is unchanged.

### Roles and the registry

21. The harness consults a model in four roles: **Worker** (executes cards), **Planner** (plans, decomposes and answers questions about the board; the PM persona Seshat speaks with the Planner's weights), **Reviewer** (reads a passing diff against its specification, from a different model family than the Worker), and **Researcher** (answers questions with cited sources; it may also run a short `probe` against an installed dependency in the claim gate's sandbox, and in the plan's one Researcher load it answers the research packet's questions as well as the brief's deep question, [design-stage](design-stage.md) DS-N9-13, -16, -17). `vision` is a capability a model may hold, not a role. There is one role enumeration in code.
22. Roles are routing decisions, not agents or personas; the harness never simulates a conversation between them ([DEC-05](../DECISIONS.md#dec-05): agents never role-play ceremonies with each other; reports for people come from the one PM persona). One model may hold several roles, and on small machines usually does. **No two large models are resident at once**, decided by footprint against the measured headroom (rule 20g); `CO_RESIDENT_MIN_BYTES` is derived from measured footprints, not fixed (*amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap), the later ruling, which replaced "roles never co-reside below 32 GB"*). A second large model is always refused; only small models (a quick answerer, a draft model, an embedder, each below a quarter of the GPU wired limit) go through admission, and may sit beside a large one when it admits them.
23. A role whose model is absent degrades to a named fallback, never a failure: no Reviewer means the diff reaches the person unreviewed and the card says so; no Researcher means questions are answered from the repository alone.
24. A fifth role is added only when an existing one cannot be qualified for the work.
25. **The registry** is the harness's memory of what works on this machine: per model its identity, family, quant, size, context window, engine, template checksum, sampling, reasoning support, measured tool arm (with per-arm measurements), script capability, throughput per context bucket, qualification record and history, speculative decision and roles. It is keyed by host fingerprint, written atomically with a merge that never drops another writer's entry, and never written by tests.
26. **One construction path.** Every command that needs a model (`run`, `queue`, `bake-off`, `plan`, the PM) obtains it from the roster, which applies the registry, the tier cap and the engine decision; there is one `ModelProfile` record per model build.
26a. **The Team server's engines, one per role** (NEW-models-15; FINDINGS INS-01, severity 4). On the Team server the harness image runs no engine of its own: the compose file defines one engine service per filled role's weights (roles served by the same weights share one, MD-N9-1, so the Planning model and Seshat share a service), each started with exactly that profile's `launchArgs()`. The engine services share the harness service's network namespace and mount the models volume at the same path, so `--host 127.0.0.1`, the profile's port and the `/props` model path hold unchanged and server identity (rule 15, MD-M4-1) accepts them. The image contains every program the harness spawns on Linux — git, bubblewrap and socat ([DEC-50](../DECISIONS.md#dec-50--linux-gets-the-proxy-route-and-a-cards-named-ports-through-relays-in-c2)) — and every third-party image is pinned by digest. At start the server checks that each filled role's engine answers and matches its profile, adopts it without loading or unloading weights through it, and names on Configuration › Models and in `doctor` any role with no engine, a refused engine, or engines whose summed footprint exceeds the measured headroom (rule 20g): with one service per role, every filled role is resident at once, which rule 22 allows only on a host that fits them all. INSTALL names the GPU variant and the memory each role's service needs. **As built (C3):** the services are `engine-coding`, `engine-planning` and `engine-research`, one per filled shipped role (Review is unfilled, so it has none; a person who fills it adds a service the same way); each runs llama.cpp's server image and its `command` is exactly the shipped profile's `launchArgs()` (`teamEngines()`, `apps/harness/src/team_engines.ts`) with the weights at `/models/<file>` and the host-sized values (the prompt-cache flags and the Research window) computed for a 64 GB host, the Team tier this topology needs. The harness service owns the network namespace, the engines join it (`network_mode: "service:sekhemet"`), and both mount the models folder at `/models`. Each engine's health check is its own port's `/health`, since the image's default checks 8080. Images are pinned by digest: llama.cpp's `server-cuda-b10818` (the first published container build at or above the set's floor b10809; b10809 itself has no image), with `server-vulkan-b10818` and `server-b10818` (CPU) as the alternatives INSTALL names; oauth2-proxy v7.15.5; and the harness image's base, `node:24-bookworm-slim`. At start `checkTeamEngines()` reads each engine's `/health` and `/props` only — never a load, an unload or a request for a reply — and refuses one whose model path, window or MTP state differs from its profile (MD-M4-1); it sums the services' footprints (`footprintBytes()`) against the measured headroom and names each, or says that the headroom was not measured.

### Qualification

27. A model is qualified, not chosen by reputation. The qualification suite uses the harness's own tool schemas and deterministic scoring (no model judge) and measures schema validity, tool selection, arguments, multi-step recovery after an injected error, and refusal of an out-of-scope request. A model qualifies as Worker at a set pass rate on this internal suite — a bar not comparable to public leaderboards, set with multi-turn scores below single-turn in mind. It is measured at the sampling the role runs at (the model card's, e.g. temperature 0.6, top_p 0.95, top_k 20, min_p 0 for the Worker), never greedy unless the role runs greedy, and each case is sampled `QUALIFICATION_SAMPLES` = 5 times, fixed before any result: a check's score is its pass rate over every sample, the bar applies to that point rate, and its exact (Clopper–Pearson) 95% interval is recorded beside it. The sampling is part of the combination (MD-N8-1). An unqualified or invalidated model is not used as Worker without a recorded override. A request that fails, or a reply that is not a response (no tool-call list), fails that case with its reason and the check goes on, so the model is always scored; only replies that report their usage enter its speed.
27a. **Qualification is per combination.** What is qualified is the tuple **(engine, model build, host fingerprint, settings)** — settings meaning the context size, KV type, speculative decoding, prefix caching, parallel slots and chat template. A model assigned to a role on a host is refused until that exact combination has passed, and the suite includes, besides speed, **tool-call validity, a multi-step tool conversation and a recall check** (a fact stated once early in a long context, asked for later), because tool calls are the Worker's only interface and a speed-only qualification would pass a configuration that corrupts them. A change to any element of the tuple — a new engine build, a new template, MTP switched on, a new context version ([context.md](context.md) rule 27) — invalidates the qualification. **A qualification is for one role** (rule 4d, MD-N10-3), and its context version is **that role's own prompt version**: its templates, copy modules, tool schemas and budget policy, so another role's prompt change leaves it valid (live-test F24, [context.md](context.md) CX-N6-4). `sekhemet qualify --models <m> --role <role>` records it; the Coding model's is the default. **Qualifications are kept per version** (live-test F23, CX-N6-1): the registry is shared by every build on the host, so a build looks up only its own version's record, a newer build's version invalidates nothing an older build is running on, and an upgrade still requires re-qualification because the new version has none. *Amended by NEW-models-21 (C3-3):* the settings also include every per-role value a person sets that can change what the model emits — the sampling (temperature, top-p, top-k, min-p, and now the repeat and presence penalties), the reasoning level and its thinking cap, flash attention and the tool arm — so a change to any of them marks the role **Needs verifying** and the role is refused until this combination passes (MD-N21-3). A value that changes only speed or the harness's loop — the seed, GPU layers, the load mode, the working method, the evidence gate and the step budget — is not an element; the benchmark measures those. A value no person set adds no element, so every record made before keeps its key.
28. **Tool arm.** Each model's tool interface is measured across three arms — A (`arm_a_flat`: native, flat tool calls, optionally grammar-constrained per model), B (`arm_b_json`: calls written as JSON in the reply, read by the tolerant parser) and C (`arm_c_sketch`: the tool chosen in natural language, with constraints only on the terminal payload) — and the registry pins the winner once it has at least `MIN_ARM_TRIALS` trials and beats the others by the register's pre-set bar (5 points of tool-call validity, R4). Grammar constraints help on terminal payloads (paths, identifiers, flags) and hurt on reasoning and high-level selection (the "format tax", 15–30% on small models), so hard schema constraints are never a default ([DEC-22](../DECISIONS.md#dec-22--rejected-techniques)); a model gets them only when its measurement says so. Until a model is measured, arm A without constraints is used and the evidence says the arm was not measured.
29. **Quantisation is measured, not assumed.** No public source measures IQ3 against Q4 on agentic coding, and INT4 has raised tool-name hallucination up to 2.5× at unchanged final scores; so every run records tool-call format errors and tool-name errors per step, not only pass/fail.

### Per-repo bake-off

30. `sekhemet bake-off` runs candidate models under the real harness on tasks from the repository's own history: closed issues with their fixing commits become fail-to-pass tasks (a task is kept only if reverting the fix makes its test fail), and recent commits become reconstruction tasks. Every result carries its full settings (model, quant, tool arm, step budget, working context, engine, date), taken from the child run's evidence, not reconstructed afterwards. The results are written as a matrix by hardware tier with full settings, `MODEL_MATRIX.md` (`packages/eval/src/report.ts:133-200`), which the dashboard's Registry shows.
30a. **Who changes a role's model, and on what evidence** (the lead's ruling on the owner's product pass, 2026-09-24):
    - **The bake-off applies only to the recorded baseline and the shipped defaults.** It never gates a person's own assignment: any model that has passed rule 27a's qualification on this host for that role may be assigned.
    - **A person, for their own use:** such a model may be assigned to a role on the strength of the quick benchmark ([measurement.md](measurement.md) NEW-measurement-5) or with no benchmark at all. It is their machine. Every card's evidence names the model it ran with (M4), so no result is unattributable.
    - **The recorded baseline and the shipped defaults:** changing the recorded **baseline `RunProfile`** ([measurement.md](measurement.md) rule 9a) or a **shipped default** for a role requires a recorded **bake-off** on that host — the frozen suite for the Worker, the role's full evaluation set for the Planner, the Reviewer and the Researcher, paired under [measurement.md](measurement.md)'s statistics; the overnight benchmark tier runs exactly this. Published numbers are upper bounds, never inputs; model churn in the baseline that nobody measured would silently change every comparison against it.
    - **The shipped defaults need no bake-off at first run**: they are assigned by qualification alone (MD-N4-4).
    - In every case the previous assignment stays restorable with one command (`sekhemet models restore <role>`).

### Card class and the competence model

31. `cardClass = "<kind>:<ext>"`. `kind` is the card's stored kind, one of seven, closed: `spike`, `interface`, `implement`, `data`, `rule`, `review`, `research` ([kernel.md](kernel.md) rule 6, [DEC-26](../DECISIONS.md#dec-26--one-vocabulary-for-the-kind-of-card-and-the-run)) — not the SPIDR axis a story was split on (`split`) and not what the card does to existing code (`change`). `ext` is the primary file extension of the declared scope, or `none`. It is knowable before the card runs and coarse enough to fill; tool sets key on `kind` alone, and budgets, routes and exemplars on the whole class. It is defined once, in the kernel; today `cardKind()` derives the kind from the title on every read (`card_class.ts:93-102`), which NEW-kernel-9 replaces with the stored field.
32. Every card outcome writes a competence row: class, files touched, difficulty, model, arm, step budget and steps used, stop reason, gate failures, tokens and wall-clock — and, as three separate fields, the routing **prediction**, the **decision** taken and the **outcome**, so a row can say whether an escalation or a budget was necessary. An attempt a person built (`builtBy.kind = person`, [kernel.md](kernel.md) rule 22) writes no competence row and never counts in pass rate by model, so routing never learns from people's work. Budgets and routes change from these rows only through the inlet rules in [measurement.md](measurement.md). Public outcome data may seed only the **task-difficulty** axis as a prior; the model × arm axis comes only from this machine's ledger, because public data has no tool-arm dimension and its pass rates are dominated by the scaffold that produced them (16.7% versus 47.9% on the same instances under two harnesses). If routing ever needs more than a mean with a Wilson interval, a logistic regression over the row's columns is the tool, not a learned tabular model.

## 5. Changes for v1

### M4 — provenance: what produced a result

- **MD-M4-1** WHEN a server already listens on a managed port and its `/props` reports a different model path THE SYSTEM SHALL refuse to adopt it and say which model is loaded; WHEN the model matches but the context size or MTP state differs from the profile, it SHALL refuse the same way.
- **MD-M4-2** WHEN a card's evidence is compiled THE SYSTEM SHALL record the harness repository's commit and dirty flag and a hash of the built `dist` directories — never the target repository's HEAD as the harness commit.
- **MD-M4-3** WHEN a card's evidence is compiled THE SYSTEM SHALL record the running server's reported model, context, KV type, MTP state and build as read from `/props`.
- **MD-M4-4** WHEN a step completes THE SYSTEM SHALL record `finish_reason`, thinking tokens, answer tokens, cached and evaluated prompt tokens, tool-call format errors and unknown-tool-name errors, and, with speculative decoding on, drafted and accepted token counts.
- **MD-M4-5** WHEN a card's evidence is compiled THE SYSTEM SHALL record the seven-field reproducibility record — model, quantisation, chat-template checksum, prompt-set version, playbook version, tool-schema version and engine settings (the prompt-set and tool-schema versions are parts of the context version; the playbook version is the pack's guidance list, outside it, [context.md](context.md) rule 27) — so a card can be replayed and A/B-compared on exactly what produced it.

### M7 and M11 — MTP decided by measurement, on seconds per step

- **MD-M7-1** WHEN no speculative decision is recorded for this model, host fingerprint and thinking policy THE SYSTEM SHALL launch the Worker without `--spec-type draft-mtp`.
- **MD-M7-2** WHEN a recorded decision enables MTP for this host and policy THE SYSTEM SHALL launch with `--spec-type draft-mtp` and `--spec-draft-n-max 1 --spec-draft-p-min 0.0` (the model card's own sweep, which supersedes the earlier two-token figure; DEC-42); WHEN the thinking policy changes, the decision for the new policy SHALL apply.
- **MD-M11-1** WHEN the MTP A/B runs THE SYSTEM SHALL replay recorded Worker step prompts against one GGUF and one server build with MTP on and off, and record per step prefill seconds, decode seconds, total seconds, draft acceptance and the peak Metal working set, for each thinking policy.
- **MD-M11-2** WHEN the A/B's paired total seconds per step is not lower with MTP THE SYSTEM SHALL record `enabled: false` with the measured speed-up and reason.
- **MD-M11-3** WHEN the watchdog reaches `elevated` THE SYSTEM SHALL suspend MTP at the next launch whatever the recorded decision.

### NEW-models-1 — calibrate the reference host and correct its tier

*Justification:* the 24 GB reference host computes as tier S and calibration would shrink the Worker's window below what its prompts need.

- **MD-N1-1** WHEN a machine with 24 GB installed is classified THE SYSTEM SHALL place it in tier M.
- **MD-N1-2** WHEN calibration would set the Worker's working context below the p99 of its recorded prompt sizes plus the answer and thinking caps THE SYSTEM SHALL keep the larger window and say why.
- **MD-N1-3** WHEN `sekhemet calibrate` completes THE SYSTEM SHALL write the machine profile keyed by the hardware fingerprint, and the next run on the same host SHALL read it rather than re-measure.

### NEW-models-2 — floors and the watchdog on every path

*Justification:* the throughput floor never refuses anything, and the watchdog guards `queue` but not `run`.

- **MD-N2-1** WHEN the Worker's measured throughput is below the overnight floor THE SYSTEM SHALL refuse to start a card with a message naming the measured and required prefill and decode rates.
- **MD-N2-2** WHEN `sekhemet run` executes a card THE SYSTEM SHALL run the memory watchdog for the card's duration, and a `critical` level SHALL pause new steps.
- **MD-N2-3** WHEN `sekhemet run` starts a card with a Worker whose measured throughput is below the overnight floor THE SYSTEM SHALL refuse it as the queue does.
- **MD-N2-4** WHEN the watchdog reaches `high` THE SYSTEM SHALL run at most one card at a time, trim the language servers' symbol caches and mask older observations at the next step; WHEN it reaches `elevated`, it SHALL start no new worktree and shorten keep-alive.
- **MD-N2-5** WHEN the watchdog's action list is walked THE SYSTEM SHALL find each action handled by the queue or the runner (a test fails for an action with no handler).

### NEW-models-3 — reserved hours, the overnight window and swap batching

*Justification:* the design's scheduling is half-unreachable (`isUserTime`, `nextWorkWindow`); it is wired in, and only its unreached exports are cut (DEC-25 R30, §8 Q1).

- **MD-N3-1** WHEN the machine is reserved (`[machine] reserved_hours`, or a person's reserve-now, rule 20) THE SYSTEM SHALL NOT start a backlog card unattended, unless the card is marked urgent.
- **MD-N3-2** WHEN the queue holds cards from two projects THE SYSTEM SHALL run each project's cards together before swapping models, unless a dependency forces the order.
- **MD-N3-3** WHEN the machine is in the overnight window and idle with cards queued THE SYSTEM SHALL keep the next card's model loaded and SHALL NOT unload it between cards.
- **MD-N3-4** WHEN an overnight benchmark is due and the machine is reserved — inside `[machine] reserved_hours`, outside `[machine] overnight_hours` when that is set, or during a person's reserve-now — or a card holds the runner lease THE SYSTEM SHALL NOT start it, SHALL show it as *Queued* with when it will start, and SHALL start it at the first moment of the overnight window with the lease free; WHILE it holds the lease THE SYSTEM SHALL start no card; WHEN a person reserves the machine now during a run THE SYSTEM SHALL stop the run as at the window's end (MD-N3-5).
- **MD-N3-5** WHEN the overnight window ends during an overnight benchmark THE SYSTEM SHALL stop at the current card's end or at the window's end, whichever comes first, keep every completed card and run, and record where it stopped; WHEN the next window opens THE SYSTEM SHALL resume from that card in the same block order, and WHEN the harness build, the context version or a model's qualification changed in between it SHALL discard the interrupted run and restart it, saying why.

### NEW-models-4 — one profile, one role enum, one construction path, a live registry

*Justification:* three role vocabularies, sampling hard-coded in five places, three construction paths with different settings, and qualification that gates nothing.

- **MD-N4-1** WHEN the source is searched THE SYSTEM SHALL define one role type (`worker`, `planner`, `reviewer`, `researcher`) and one capability flag `vision`, and no other role enumeration.
- **MD-N4-2** WHEN a registry entry sets sampling, window or reasoning for a model THE SYSTEM SHALL use those values in the request, overriding the factory default (a test changes the registry and observes the request).
- **MD-N4-2a** WHEN a model's chat template cannot turn reasoning off (known from its GGUF architecture at `models add`, e.g. gpt-oss, whose floor is low) THE SYSTEM SHALL record that and its lowest level in the registry, resolve a request for no reasoning to that level, and add its thinking allowance to the request's max_tokens; and WHEN the server reports thinking on a reply to a request resolved to off THE SYSTEM SHALL record it — from the server's own report only, apart from the model's `reasoning` entry — so the next such request's max_tokens includes it; `models add` SHALL NOT override a reasoning entry the owner set (`supported: false`, a floor). A model whose architecture is not read (pulled through Ollama, where no GGUF header is read; an entry registered before this rule gets its floor from its recorded architecture, F30) has no floor: its first request for no reasoning may be cut off and fail, and it gets its allowance only from that learning (live-test F25; `reasoning_floor.spec.ts`). WHEN a registry entry records its GGUF architecture but no reasoning (an entry added before F25) THE SYSTEM SHALL derive that reasoning from the architecture when it reads the entry, and a recorded reasoning SHALL win (F30, `withArchitectureReasoning`, `reasoning_floor.spec.ts`).
- **MD-N4-3** WHEN `run`, `queue`, `bake-off`, `plan` or the PM needs a model, including by an Ollama tag THE SYSTEM SHALL obtain it from the roster.
- **MD-N4-4** WHEN the Worker model's qualification is missing, failed or invalidated THE SYSTEM SHALL refuse to run cards with it; WHEN its exact combination's newest qualification **failed** and a person recorded an override of that failure, THE SYSTEM SHALL run it, and the evidence SHALL say so. *(Narrowed from "missing, failed or invalidated" on 2026-09-25, as the owner intended: an override accepts a measured failure, so what was never measured, or was invalidated by a change, is qualified first; review of the override, low 5.)*
- **MD-N4-5** WHEN tests run THE SYSTEM SHALL write no file under the user's home `.sekhemet`, and a registry write SHALL preserve entries written by another process since it was read.
- **MD-N4-5a** WHEN two registry instances in one or several processes read and write the same registry file THE SYSTEM SHALL read the file again before each read or change when it has changed since this instance last read or wrote it, so no instance writes a stale copy of an entry over another's change (live-test F17: `qualify`'s own instance wrote over the chat template its adapter's instance had pinned).
- **MD-N4-6** WHEN a bake-off child finishes THE SYSTEM SHALL report the settings recorded in the child's evidence.
- **MD-N4-7** WHEN `sekhemet bake-off` runs in a repository with history THE SYSTEM SHALL build its tasks from that repository's closed issues and fixing commits (kept only if reverting the fix fails its test) and recent commits, and SHALL say when too few exist and it fell back to a fixture.
- **MD-N4-8** WHEN a model's reply carries reasoning THE SYSTEM SHALL strip it once, in the adapter, and every caller SHALL read JSON from a reply through one extraction helper (the integration review found `<think>` stripped in eight places and a greedy JSON regex in four).
- **MD-N4-9** WHEN the managed defaults are registered THE SYSTEM SHALL record each one's `family` (Worker and Planner `qwen`, Reviewer `gemma`, Researcher from its model card); WHEN a model of the Worker's family is assigned to the Reviewer role THE SYSTEM SHALL refuse the assignment naming both families, and WHEN no other family is qualified on the host THE SYSTEM SHALL record the Reviewer as unfilled.
- **MD-N4-10** WHEN the planner checks a card's INVEST *Small* bound THE SYSTEM SHALL read the resolved Worker's window from the registry and take the verdict from the context allocator's Zone 3 measurement at that Worker's prompt budget ([context.md](context.md) CX-N2-2); on the reference Worker (16,384) it SHALL refuse a card whose Zone 3 content exceeds 3,792 tokens, and no planner constant SHALL set the window or a second token limit.

### NEW-models-5 — tool-arm qualification

*Justification:* "which tool arm wins" blocks the product thesis and has never been measured for the Worker.

- **MD-N5-1** WHEN `sekhemet qualify` runs a model THE SYSTEM SHALL score arms A, B and C on the same tasks and record per-arm tool-call validity, pass rate and trials, and pin the winner only with at least `MIN_ARM_TRIALS` trials per arm and a lead of at least 5 points of tool-call validity whose interval excludes zero ([measurement.md](measurement.md) statistics).
- **MD-N5-2** WHEN a card runs with an unmeasured arm THE SYSTEM SHALL record `toolArm` with `measured: false` in the evidence.

### NEW-models-6 — competence rows that can improve routing

*Justification:* a row that records only the outcome cannot say whether an escalation or a budget was necessary.

- **MD-N6-1** WHEN a card finishes THE SYSTEM SHALL write a competence row with separate `prediction`, `decision` and `outcome` fields and the card's gate failures.
- **MD-N6-2** WHEN an attempt's `builtBy.kind` is `person` THE SYSTEM SHALL write no competence row for it and SHALL exclude it from pass rate by model.

### NEW-models-7 — weights that a new user can obtain

*Justification:* a local-first harness whose defaults cannot be obtained does not run for anyone but its author.

*C3 (2026-10-04):* every filled role of the shipped set now has a verified source (rule 8a): the Coding model, the Planning model and the Research model are fetchable by `sekhemet models fetch` and **Download…**, and the Review role, unfilled, offers nothing and says why. MD-N7-5 is added by C3.

- **MD-N7-1** WHEN a default model's file is missing THE SYSTEM SHALL say so and name the explicit ways to download it (the Configuration page's **Download…** and `sekhemet models fetch <model>`); WHEN a person runs `sekhemet models fetch <model>` THE SYSTEM SHALL download from the registered source through the same implementation as the page (MD-N12-6) and verify the published SHA-256 before the file is used, and SHALL delete a file whose hash differs; WHEN `[network] mode` is `offline` it SHALL refuse, naming the setting.
- **MD-N7-2** WHEN a weights file's hash differs from the registered one THE SYSTEM SHALL report `doctor` red for that model.
- **MD-N7-3** WHEN the shipped source is searched THE SYSTEM SHALL contain no absolute model path, external-volume path or user-specific directory.
- **MD-N7-4** WHEN no person has run the download command THE SYSTEM SHALL NOT download any weights (a test runs `doctor`, `run` and `queue` with a missing model and observes no network request for weights).
- **MD-N7-5** WHEN a shipped row records a source THE SYSTEM SHALL have taken its SHA-256, size and licence from a verified lookup (rule 4), and a test SHALL fail when a filled shipped role has no source, or a role without a verified source is given one.

### NEW-models-8 — engines as adapters, qualified per combination

*Justification:* on a team server the engine is a throughput choice and on a laptop a memory choice, so no engine is universal; and a configuration can pass a speed check while corrupting tool calls (vLLM #47194, prefix caching with MTP) — the Worker's only interface ([DESIGN_RESEARCH_TEAM_SERVER.md](../../research/DESIGN_RESEARCH_TEAM_SERVER.md)).

- **MD-N8-1** WHEN a model is assigned to a role on a host THE SYSTEM SHALL refuse to use it until that (engine, model build, host fingerprint, settings) combination has passed qualification, which includes tool-call validity, a multi-step tool conversation and a recall check as well as speed.
- **MD-N8-1a** WHEN qualification records a combination THE SYSTEM SHALL first pin the chat template the running server reports in the registry the combination is read from, so the template it measured is the one pinned, and a later run with the same weights and launch keeps the qualification (live-test F17: every newly qualified generic model was invalidated by its first queue run).
- **MD-N8-2** WHEN speculative decoding (MTP or a draft model) is enabled THE SYSTEM SHALL have qualified that exact combination with prefix caching on, and SHALL disable it, recording why, if the qualification's tool-call checks fail.
- **MD-N8-3** WHEN the host profile is multi-user THE SYSTEM SHALL read the engine's parallel-slot or batch capacity from its qualification and SHALL NOT assume one request at a time.
- **MD-N8-4** WHEN any element of the qualified combination changes (engine build, template, speculative decoding, context size, KV type, slots, context version) THE SYSTEM SHALL mark the qualification invalidated with the changed element as the reason.
- **MD-N8-5** WHEN a draft model is configured for speculative decoding THE SYSTEM SHALL measure and decide it by the same A/B as MTP (MD-M11-1, MD-M11-2), keyed by the draft model as well.

*The lead's rulings on reading these criteria (2026-09-25):*
- **Context version** in the combination is the role's own prompt version: its prompt templates, copy modules, literals, tool schemas and budget policy, not playbook rules, which are per project and card, and not another role's prompts ([context.md](context.md) rule 27, CX-N6-4; `rolePromptVersion(role)`, the Coding model's `workerContextVersion()`). Revised by C1 after live-tests F23 and F24: a record under another version is not "changed" for the build that made it; each build reads its own version's.
- **The elements** (*amended by NEW-models-21, C3-3: four more when a person sets them — the repeat and presence penalties, the reasoning level and cap, flash attention and the tool arm — each absent, and so keying as before, until set*) are all ten, and the role: engine and build, model build, host fingerprint, context size, KV type, speculative decoding, prefix caching, parallel slots, chat template, context version and (for a role other than the Coding model, so the Coding model's records keep their keys) the role. A change to any one invalidates, whether or not MD-N8-4's list names it.
- **"The tool-call checks fail"** (MD-N8-2) means any of schema validity, multi-turn recovery, the multi-step conversation or recall below the bar of 0.8.
- **"Qualified"** requires the pass rate and every tool-call check at the bar, everywhere a qualification is read (the Worker's refusal, `onboard`, the candidates' qualification).
- **An Ollama model** is named by its tag, with the engine's defaults for what the harness does not set.

### NEW-models-9 — one scheduler owns residency

*Justification:* the integration review measured ten evictions where four were needed (4–12 minutes a run), an escalated retry that could load the Worker beside a 12 GB model on a 24 GB host, three adapters on the same weights reloading on every `num_ctx` change, and a dashboard path that loads models with no footprint check (C1–C4; suggestions 1 and 10; target scheduler; ruling DEC-25.R20).

- **MD-N9-1** WHEN two roles are served by the same weights THE SYSTEM SHALL construct one adapter for them with the largest context either needs, and a request from either SHALL NOT reload the model.

### NEW-models-14 — Smart Swap

*Justification:* on the 24 GB reference host a swap costs minutes (the Worker loads from a USB drive in about five), an earlier review measured ten evictions where four were needed (NEW-models-9), and today no load's cost is recorded where a scheduler, a person or a later measurement could read it: `ThroughputMeter.loads()` (MS-T7-1) keeps load times in memory for one run and never on the ledger. The owner asked for swap cost to be measured, predicted and flagged (rule 20c), and then for the switching itself to be smart, delegating its details ([DEC-45](../DECISIONS.md#dec-45--smart-swap)). **Workstream:** the engine in B4.0a — the record, prediction and slow-load flag (MD-N14-1–6, built), then the policy (MD-N14-7–40, part 3); placement and the model section of Configuration in B4.1 (MD-N14-41–42).

- **MD-N14-1** WHEN the scheduler makes weights resident whose adapter can load on request THE SYSTEM SHALL load them then, time the load, and record `model/loaded` with the weights, the queues they serve, the volume (`internal` or `external`), the file's bytes, the cache state (`cold` or `warm`), the `engine`, the `loadMode` (`mmap`, `no_mmap` or `preread_mmap`, rule 20h; recorded since B4.0a part 3 when the adapter names its engine, the load mode for llama.cpp only), the load milliseconds and the prediction it made (median, p90 and whether measured or estimated); WHEN the server was already serving them THE SYSTEM SHALL record no load.
- **MD-N14-2** WHEN the scheduler unloads weights whose load it recorded (an eviction, a release, releasing everything) THE SYSTEM SHALL record `model/unloaded` with the weights, the queues, the volume, the bytes, the unload milliseconds and whether the unload was confirmed; WHEN the first reply after a recorded load arrives THE SYSTEM SHALL record `model/first_token` with the milliseconds from that request's start to its first token (to the reply when it does not stream).
- **MD-N14-2a** WHEN the scheduler unloads weights (an eviction, a release, releasing everything) THE SYSTEM SHALL ask the adapter to confirm the unload — for a managed llama-server, polled within a bound (default 5 s) until the process it stopped has exited and nothing listens on its port — and record `confirmed` from that answer; WHEN an unload is not confirmed THE SYSTEM SHALL keep counting its footprint as resident memory in every admission, and never evict or reload it as though gone, until a later look confirms it (live-test F3: every `model/unloaded` read `confirmed: false`, because only an eviction asked, and the managed adapter answered before looking; `unload_confirmation.spec.ts`).
- **MD-N14-2b** WHEN the first reply after a recorded load streams THE SYSTEM SHALL record its first token's milliseconds as `firstTokenMs`; WHEN it does not stream THE SYSTEM SHALL record no `firstTokenMs` and the reply's milliseconds as `replyMs`, and SHALL take steady-state first tokens from streamed replies only, so C_pair's first-token excess is never a whole reply's time (live-test F14).
- **MD-N14-3** (*amended by [DEC-45](../DECISIONS.md#dec-45--smart-swap)*: this is now the prediction made before a load; the recorded state is measured, MD-N14-10) WHEN a load's cache state is decided THE SYSTEM SHALL call it `warm` only when the same weights were unloaded less than 15 minutes before and the bytes of the other weights loaded since, plus these weights, fit in usable memory, and `cold` otherwise, including weights with no recorded unload; every recorded field SHALL be structural (the kernel's payload registry refuses a payload that is not).
- **MD-N14-4** WHEN a load is predicted and at least three loads of the same weights, volume and cache state are recorded THE SYSTEM SHALL predict the median and p90 of the last 20 of them, labelled measured; WHEN fewer are recorded it SHALL predict 5 s plus the bytes at the volume's read rate — the median effective rate of the cold loads recorded on that volume, else 2 GB/s internal and 40 MB/s external — or at 4 GB/s for a warm load, labelled an estimate; the history SHALL be read back from the ledger, so a new process predicts from every load recorded before it.
- **MD-N14-5** WHEN a recorded load took longer than 1.5 × its prediction's p90 with at least three samples, or, with fewer, a cold load took longer than 120 s or a warm load longer than 1.5 × its estimate THE SYSTEM SHALL record `model/slow_load` with the load, the bound it passed, its causes among `external_volume`, `memory_pressure` (kernel level warning or worse at the load's start or end), `swap_in_use` (1 GB or more at its end) and `cold_cache`, and the fix for each (`copy_to_internal`, `free_memory`, `prewarm_overnight`); WHEN a notifier runs THE SYSTEM SHALL turn it into one low-priority `slow_load` notice naming the causes and fixes, deduplicated per weights and counted in the day's notice budget.
- **MD-N14-6** WHEN a weights' load fails for a reason other than memory (the file is missing, the server exits) THE SYSTEM SHALL reject the work queued for it with that error rather than hold it queued, and SHALL NOT mark the weights resident.

**The policy** ([DEC-45](../DECISIONS.md#dec-45--smart-swap); rules 20d–20k). *Workstream:* MD-N14-7–40 are the engine, B4.0a part 3; MD-N14-41–42 are B4.1, with the page ([dashboard.md](dashboard.md) DB-NM14-1–9). Every criterion below is tested **without a model**: a fake clock, fake adapters with scripted load, unload, first-token and restore times, a fake memory probe (GPU wired limit, Metal in-use memory, wired, anonymous, compressor, swap, process footprints) and real SQLite ledgers.

*Amended by DEC-45, the later ruling, which wins over each:* rule 3's co-residence sentence and rule 22 (no two large models, by footprint); rule 4c's tie-break (floors, then time per card including swaps, then footprint; no weighted score); rule 19 (the watchdog's precedence); rule 20a (the fixed plan order replaced by `decide()`; headroom replaces usable memory) and with it MD-N9-2's "the order the residency plan gives" and MD-N9-3's "usable memory"; rule 20b (benchmark blocks bypass C1–C10); MD-N13-3's single efficiency of 0.8 (per engine); MD-N14-3's cold/warm rule (now the prediction before a load; the recorded state is measured) and MD-N14-4's default read rates (replaced by a probe where one can run); [runtime.md](runtime.md) item 4 and RUN-34 (interactive replies first within a resident visit only; one aging mechanism); [review-git.md](review-git.md) §2.3 item 2 and RG-P8-3 (the Reviewer loads when C2's tours and C6 bring it, not once after the retries).

*The cost model (rule 20d)*
- **MD-N14-7** WHEN C_pair(r) is computed THE SYSTEM SHALL sum the resident's unload, r's load, r's unload and the resident's reload (each at its p90), the first-token time above steady state after each of the two loads, min(K, R) for every live session of either side, and the idle slot-seconds × N; a test with scripted values observes the exact sum, and a session whose restore is slower than its re-prefill contributes its re-prefill time.
- **MD-N14-8** WHEN a swap is decided THE SYSTEM SHALL use each load's p90, and WHEN a wait is predicted it SHALL use the median; WHEN three consecutive recorded loads of the same weights, volume, engine, load mode and cache state exceed the p90 THE SYSTEM SHALL re-take the prediction from those loads onward (a test records ten loads at 60 s, then three at 300 s, and observes the next prediction's median at 300 s).
- **MD-N14-8a** WHEN a wait is predicted THE SYSTEM SHALL price the load of the request's own weights whatever their state (live-test F10); WHEN the Worker is at home with cards still to run and the request is not interactive and under C1's threshold THE SYSTEM SHALL lay its start at the backlog's end (the remaining cards × the measured step time, when the caller knows it) or its aging cap, whichever comes first, and WHEN the backlog's length is unknown SHALL report the wait as a bound, at most the cap (`atMost`), never a smaller number it cannot support (live-test F11).
- **MD-N14-9** WHEN a load is predicted with no recorded history for its weights and volume and a probe can run THE SYSTEM SHALL estimate it from a 256 MB sequential read of the volume, plus the spin-up when the drive had spun down, labelled an estimate of ±50%; WHEN no probe can run it SHALL fall back to MD-N14-4's stated rates.
- **MD-N14-10** WHEN a load's cache state is recorded THE SYSTEM SHALL take it from the file's page-cache residency read before the load, or, where that cannot be read, from the load's effective read rate against the volume's recorded cold rate, and SHALL NOT record a state it did not measure; WHEN the state is predicted before a load THE SYSTEM SHALL take the page cache's capacity as physical memory − wired − anonymous (a test: after a scripted 13 GB swap on a 24 GB probe, the other 12 GB weights are predicted cold).
- **MD-N14-11** WHEN a role's queued work W is computed THE SYSTEM SHALL sum each request's prefill tokens at the measured prefill speed and decode tokens at the measured decode speed of its engine, and, with no measured speed, decode speed as the engine's efficiency (llama.cpp 0.6, MLX 0.85 until calibrated on the host) × the host's bandwidth ÷ the bytes read per token (active bytes for a mixture of experts); an escalated retry SHALL count in the Planner's W.
- **MD-N14-12** WHEN a rolling hour is observed THE SYSTEM SHALL compute θ as swap time ÷ wall time over it and record it with the policy's parameters (a test with 12 minutes of scripted swaps in an hour reads θ = 0.2).

*`decide()` and C1–C10 (rule 20e)*
- **MD-N14-13** WHEN residency is decided THE SYSTEM SHALL call one pure function `decide(snapshot, now)`, at every step boundary, from both the live scheduler and the simulator; given the same snapshot and time it SHALL return the same action and perform no I/O (a test calls it twice on a frozen snapshot with every probe replaced by one that throws), and a search test SHALL find no other code choosing which weights to load or evict, except the watchdog (rule 19), which may also evict.
- **MD-N14-14** WHEN two of its rules disagree THE SYSTEM SHALL act by the higher in rule 20e's precedence — the watchdog (every level), holds, C5, interactive requests, C7, C4, C3, C1 — and SHALL give every request it delays its predicted start; WHEN serving an interactive request's full answer would break C5 THE SYSTEM SHALL give the person rule 20f's quick path (a deterministic answer from the ledger, or the quick model when headroom admits it) and the full answer's predicted start; WHEN the watchdog is at `elevated` or above THE SYSTEM SHALL let its keep-alive override a visiting model's minimum dwell and idle hold and SHALL start no prefetch; and it SHALL never interrupt a step to swap (a test scripts a swap decision mid-step and observes it applied at the boundary).
- **MD-N14-15** WHEN the resident model's queue has work THE SYSTEM SHALL load another role r only when W(r) ≥ C_pair(r) ÷ θ_max at two consecutive step boundaries or one of r's requests has reached its aging cap; WHEN the resident queue is empty and r has work THE SYSTEM SHALL load r, subject to C3's dwell and C7's cap (a test: W(r) crosses the threshold at one boundary and falls back at the next, and no swap happens).
- **MD-N14-16** WHEN the Worker yields THE SYSTEM SHALL serve, in the same absence, every queue past 50% of its cap, the shared weights first (Seshat, the Planner and escalations), then the Reviewer, then the Researcher, before reloading the Worker (a test with a Planner question at 60% and a review at 55% of their caps observes one Worker absence and one Worker reload).
- **MD-N14-17** WHEN a tour is ordered THE SYSTEM SHALL choose, among the orders of the next H = 4 visits, the one with the least predicted total time that meets every cap, and WHEN no order meets every cap SHALL let rule 20e's precedence decide and state each request's predicted wait; WHEN a model must be evicted from several resident THE SYSTEM SHALL evict the one whose next use in the plan is farthest, and SHALL fall back to least recently used only when there is no plan (a test with a plan whose next Researcher use is last evicts the Researcher, not the least recently used model).
- **MD-N14-18** WHEN a visiting model has been loaded THE SYSTEM SHALL keep it resident at least C_pair after its load (its minimum dwell) and at least C_pair after its last request (its idle hold), unless the watchdog orders otherwise, and SHALL end the idle hold as soon as another queue has work (a scripted C_pair of 600 s keeps it 600 s with no work; an `elevated` sample at 300 s ends the hold; a request arriving for another role at 200 s ends the idle hold).
- **MD-N14-19** WHEN a request waits THE SYSTEM SHALL age it by its class's cap — interactive 120 s, Planner 30, Reviewer 45, Researcher 60 minutes, Worker steps `max_wait_s` — through one mechanism shared with [runtime.md](runtime.md) RUN-34, and a request at its cap SHALL be served at the next step boundary unless a higher rule of rule 20e's precedence forbids it, and otherwise SHALL be shown its predicted start (a search test finds one aging implementation).
- **MD-N14-20** WHEN a class's cap is below C_pair THE SYSTEM SHALL flag the cap as infeasible on the model page and give the person the predicted wait instead; WHEN θ over the rolling hour exceeds θ_max THE SYSTEM SHALL stretch the Planner, Reviewer and Researcher caps by θ ÷ θ_max, SHALL NOT stretch the interactive cap, and SHALL raise the placement notice (rule 20k).
- **MD-N14-21** WHILE the Worker's queue is non-empty THE SYSTEM SHALL keep the Worker resident for at least (1 − θ_max) of every rolling hour (a test with a scripted C_pair of 300 s sends a Seshat question every 3 minutes for two hours and observes the Worker resident at least 48 minutes of each hour, every question answered by rule 20f).
- **MD-N14-22** WHILE a person is present (inside `reserved_hours`, during a reserve-now, or with a dashboard session active in the last 10 minutes) THE SYSTEM SHALL rank reviews of finished cards first after interactive requests; WHEN reviews are due in the overnight window THE SYSTEM SHALL batch them into one tour whose median predicted end is before the reserved hours start.
- **MD-N14-23** WHEN max(1, ⌊θ_max × 3600 ÷ C_pair⌋) round trips (rule 20e, C7: a swap away and the swap back, counted once) of non-interactive swaps have happened in the rolling hour THE SYSTEM SHALL decide no further non-interactive swap in that hour except a watchdog unload, and each waiting request SHALL carry its predicted start; an interactive request SHALL be bounded by C5, not by this cap.
- **MD-N14-24** WHEN a swap is decided while N slots run THE SYSTEM SHALL admit no new step on any slot and SHALL swap only once every slot has reached its step boundary, saving all N slots (rule 20i); the Worker's holding cost in C_pair SHALL be multiplied by N (a test with two slots, one finishing its step 40 s after the other, observes the unload after the second).
- **MD-N14-25** WHILE a model loads THE SYSTEM SHALL run the CPU-side work of queued cards (tests, gates, context assembly, the repo map, language servers) (a test with a scripted 60 s load observes a queued card's gate run inside it).
- **MD-N14-26** WHEN the successor's weights are prefetched THE SYSTEM SHALL do so only while free memory minus 2 GB exceeds their bytes and the watchdog is `normal`, and SHALL NOT count the prefetched cache in the watchdog's used ratio.

*Seshat while the Worker runs (rule 20f)*
- **MD-N14-27** WHEN a person asks Seshat for status, where the cards stop, what waits on them, or a predicted wait while the Worker is resident THE SYSTEM SHALL answer from the ledger and the board and SHALL send no model request (the fake adapter records none).
- **MD-N14-28** WHEN a quick answerer is named and measured headroom admits it THE SYSTEM SHALL answer with it, labelled *quick answer*, with no tools; WHEN a quick answer's text proposes or asks to change a card, plan, proposal or decision THE SYSTEM SHALL record none of them; WHEN headroom does not admit it THE SYSTEM SHALL NOT load it.

*Memory (rule 20g)*
- **MD-N14-30** WHEN a load is considered THE SYSTEM SHALL compute headroom as the lower of the GPU measure (`iogpu.wired_limit` − Metal in-use system memory − 1 GiB − the peak compute buffer) and the system measure (total − wired − anonymous − compressor-occupied − 3 GB − the peak of the harness, language servers and tests), both read at that admission, and SHALL measure its own servers by `phys_footprint` (a test with a probe whose GPU measure is the lower observes the GPU measure used).
- **MD-N14-31** WHEN a load is considered THE SYSTEM SHALL admit it only when its footprint is at or below the headroom (MD-N14-30) **and** the projected used ratio is at or below 0.80 on both the GPU measure and the system measure, and swap did not grow between the last two samples; otherwise it SHALL refuse the load and keep the work queued, naming the measure that refused it (a test whose GPU measure projects 0.82 while the system measure projects 0.60 observes a refusal naming the GPU measure).
- **MD-N14-31a** WHEN a decision implies a sequence of transitions (unloads, loads, restores of a tour) THE SYSTEM SHALL check every transition, not only the end state, against weights + KV + engine state + prompt cache resident at that moment, and SHALL choose no tour with an infeasible transition (a test with a tour whose end state fits but whose second load would sit beside the first model's unreleased KV observes the tour rejected).
- **MD-N14-32** WHEN memory is held by a process the harness did not start (a server on a port it does not manage, Ollama) THE SYSTEM SHALL read its footprint by pid, SHALL never unload it, and SHALL name it and its size in any refusal (*Hermes on 8080 holds 9 GB*); WHEN Ollama keeps a model alive THE SYSTEM SHALL wait for the expiry `ollama ps` reports rather than refuse.
- **MD-N14-33** WHEN a second large model (footprint at least a quarter of the GPU wired limit) would be resident beside a large one THE SYSTEM SHALL always refuse it, whatever the headroom shows; WHEN a small model (footprint below a quarter) would be resident beside a large one THE SYSTEM SHALL admit it only under MD-N14-31; it SHALL derive `CO_RESIDENT_MIN_BYTES` from the measured footprints rather than a constant, and WHEN a co-residence ends in a Metal command-buffer timeout SHALL record its combined GPU footprint as the host's ceiling and refuse any later co-residence at or above it, naming both models (a test replays the recorded case: an 11.8 GB target and a 3.85 GB draft model).
- **MD-N14-33a** WHEN no calibrated ceiling is recorded for the reference host THE SYSTEM SHALL use the ceiling pre-seeded from the recorded evidence (known-bad 15.65 GB, a Metal timeout; known-good the Worker at a 16K context, about 14.5 GB; a dense 27B's weights stable at 11.9 GB and swap-exhausted at 13.7 GB) and SHALL refuse any combined GPU footprint above the known-good maximum plus 0.5 GB (D), naming the seed (a test with a 14.8 GB combination admits it and one at 15.2 GB refuses it); WHEN a calibration night records a ceiling THE SYSTEM SHALL use that instead.

*Load mechanics (rule 20h)*
- **MD-N14-34** WHEN a load-mode A/B is run on a volume THE SYSTEM SHALL alternate the modes (mmap, `--no-mmap`, pre-read then mmap) on the same weights, at least three loads per mode (an A/B with fewer SHALL decide nothing), record each load on the ledger with its mode, and use the mode with the lowest median load plus first-token time for that volume and engine; WHEN no A/B is recorded it SHALL use mmap.
- **MD-N14-34a** WHEN a load-mode A/B runs THE SYSTEM SHALL time only each unload, record `confirmed` from the adapter's own check, record a first token only when the request streamed (else the reply time, MD-N14-2b), and record the cache state the modes were compared in (`cold`, `warm` or `mixed`, from each load's measured read rate); `loadModeFor` SHALL take only A/Bs that compared cold loads; a calibration night SHALL run it for each llama.cpp model it loads ([measurement.md](measurement.md) MS-NM14-3a) (live-test F13).
- **MD-N14-35** WHEN a server is launched THE SYSTEM SHALL pass no `--mlock` and no direct-I/O flag, SHALL set `--cache-ram` from the headroom (never leave the 8 GiB default), and SHALL refuse a server whose served context is smaller than requested (MD-M4-1); WHEN the weights' drive is disconnected before a load THE SYSTEM SHALL refuse it and keep the work queued, saying why, and WHEN it has spun down the prediction SHALL include the spin-up; WHEN Ollama serves a quantisation or weights hash that differs from the file THE SYSTEM SHALL flag the model as requantised.

*KV slots and prefix state (rule 20i)*
- **MD-N14-36** WHEN weights with live sessions or a role's stable prefix leave THE SYSTEM SHALL save each slot when K < R, keyed by (weights hash, engine build, context, KV type, template), taking K before a slot's first save as the slot's size at the volume's read rate, and WHEN they return SHALL restore only a file whose key matches (a test changes the template between save and return and observes a re-prefill, not a restore); WHILE no equivalence check has passed on a calibration night THE SYSTEM SHALL re-prefill, not restore, a card's live slot mid-attempt ([measurement.md](measurement.md) rule 16a).
- **MD-N14-37** WHEN a `ledger/erased` event covers prompt text a saved slot holds THE SYSTEM SHALL delete that slot file; and `decide()` SHALL read no slot file (a search test).
- **MD-N14-37a** WHEN the slot directory's files exceed its cap (`SEKHEMET_SLOT_CACHE_MAX_GB`, default 8 GiB) THE SYSTEM SHALL delete slot files oldest-saved first until they fit, at every save and in the supervisor's start-up pass, and SHALL never delete a file whose save is still being written; a slot a running engine holds (one saved for its return by a process still alive) SHALL be deleted only when the unheld files cannot bring the directory under its cap, oldest held first (F31, C5).

*The simulator (rule 20j)*
- **MD-N14-38** WHEN the simulator replays a recorded history with a seed THE SYSTEM SHALL run the real `decide()` under a virtual clock with fake adapters and a fake memory probe, and two runs with the same seed SHALL report identical θ, waits (p50, p90, maximum per class), accepted cards per hour, maximum age and swaps per hour.
- **MD-N14-38a** WHEN a replay's day is built from the ledger THE SYSTEM SHALL include, beside the cards, a person's chat with Seshat as sessions (each turn a think-time after the previous answer), research requests at the time each was asked for its recorded time, and presence, at their recorded times; and the simulator SHALL queue research on a `researcher` queue served as its class, refusing a day with research and no researcher weights (live-test F15).
- **MD-N14-39** WHEN the simulator replays THE SYSTEM SHALL generate each finished card's review demand from its completion, escalations from failures as recorded, Seshat's arrivals as think-times after the previous answer, and reserved hours and presence from the ledger (a test where the policy delays a card by an hour observes its review demand delayed by the same hour).

*Recording (rule 20e)*
- **MD-N14-40** WHEN a card's evidence or a `RunProfile` is written THE SYSTEM SHALL record the swap-policy version and every parameter of `SwapPolicyParams`; WHEN an overnight benchmark block runs THE SYSTEM SHALL swap once at the block's start and SHALL NOT apply C1–C10 inside it (rule 20b).
- **MD-N14-40a** WHEN Smart Swap adds an event type THE SYSTEM SHALL register it in the kernel's payload registry with structural fields only, so the registry refuses a payload that is not: at least `measure/calibration` ([measurement.md](measurement.md) MS-NM14-3), the load-mode A/B record (MD-N14-34), the θ record (MD-N14-12) and the copy record ([dashboard.md](dashboard.md) DB-NM14-8); a test appends each with a free-text field and observes the refusal.

*Placement and choosing (rule 20k; B4.1)*
- **MD-N14-41** WHEN placement is advised THE SYSTEM SHALL rank copies to internal storage by swaps per day × (L_external − L_internal) ÷ GB, choose them as a knapsack that keeps at least 20 GB of internal space free, copy only on a person's click, verify the copy's hash before the registry points to it, and keep the original; WHEN an internal copy with the same hash exists THE SYSTEM SHALL prefer it.
- **MD-N14-41a** WHEN a managed model (the Worker, the Planner, the Researcher) is launched, or `doctor` checks its weights, THE SYSTEM SHALL use the registry's preferred recorded copy of its model id that is readable on this host, and its shipped file name under the models directory only when none is (live-test F1: the Planner stored as `Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf` could not run; `plug_and_play_weights.spec.ts`).
- **MD-N14-42** WHEN combinations are recommended THE SYSTEM SHALL apply each role's quality floor, then order by the least time per card including swaps (E[attempts] × compute + E[swaps] × C_pair, with E[swaps] from a closed-loop replay of the person's last N cards under that combination, labelled an estimate while N < 20), then by the smaller footprint, and SHALL compute no weighted combined score (a search test).

*Decided in C3-3 (DEC-56), where the spec was silent:*
- **The values**, in five groups as the page's tabs (dashboard NEW-dashboard-27): **Basics** — context; **Sampling** — temperature, top-p, top-k, min-p, repeat penalty, presence penalty, seed; **Reasoning** — thinking policy (`off`, `surgical`, `all`), level (`off` to `high`), thinking cap, and the floor (read-only: the template's lowest level, a fact of the model, MD-N4-2a); **Engine** — KV type, flash attention, GPU layers, slots, MTP (`auto`: on only when measured faster and qualified, rule 13; or `off`), load mode (`auto`: the recorded A/B, rule 20h; `mmap`; `no_mmap`); **Harness** — tool arm (`auto`: the measured arm, rule 28; or an arm), working method (`baseline`, `strict`), evidence gate (`off`, `on`), step budget.
- **Grades and sources.** A value nobody set resolves, in order: a measurement on this host (the MTP decision for this thinking policy, the measured tool arm) → *Measured*; the registry's recorded model-card values, the family's published defaults, the template's floor → *From its makers*; this host's tier capping the context → *Estimated*; the harness's own value → *Default*. A person's value is *Set by* that person, with the date. **Reset** removes the person's value, so the value returns to its grade.
- **Presets** (Basics; D values, tuned by G3): *Fast* — reasoning off, thinking policy off, MTP `auto`; *Balanced* — every preset value Reset; *Careful* — reasoning `medium` with a 4,096-token cap, thinking policy `surgical`, evidence gate on, method `strict`. The working method, evidence gate and step budget are recorded and shown; the queue reads them in a later workstream (§4).
- **The export format** is one JSON object, `{ format: "sekhemet-role-settings/1", model, role, values }`, holding only a person's values.

- **MD-3** WHEN swap in use exceeds 6 GB, or has grown 2 GB since the card started THE SYSTEM SHALL refuse the next step and stop the card with `memory_pressure`.
- **MD-4** WHEN the watchdog sees pressure rise THE SYSTEM SHALL escalate on the first such sample and de-escalate only after the configured number of calmer samples.
- **MD-5** WHEN a role's model is absent THE SYSTEM SHALL use its named fallback and say so on the card.
- **MD-6** WHEN the Worker weights are missing from the models directory THE SYSTEM SHALL report `doctor` red before any other check is reported green.
- **MD-7** WHEN a request carries a token callback THE SYSTEM SHALL deliver each streamed delta to it and still return the full reply and its usage.
- **MD-8** WHEN a server answers `/health` as loading THE SYSTEM SHALL report the model as loading, not dead.
- **MD-9** WHEN the Planner is asked for a plan THE SYSTEM SHALL send the planning sampling (temperature 0.7, top_p 0.8) and `min_p` 0; for code, temperature 0.2 and top_p 0.9.

## 7. Later

- **Cloud models per role** — after v1, optional and per role, never as a silent fallback. - **The vLLM adapter is built with the Team setup** ([DEC-35](../DECISIONS.md#dec-35--one-product-two-setups-solo-and-team)), not before: the owner approved vLLM as the optional multi-user engine ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O8), qualified per combination with MTP off until its prefix-caching fix lands and is re-qualified (rule 13). SGLang stays *proposed*. Rule 14 keeps the adapter boundary so adding one changes no other code. Per-tenant token quotas beyond fair share, Kubernetes deployment and autoscaling are out: a team server is one machine in v1.
- **The ceiling run** — the frozen suite once with a frontier model as Worker, only after local v1 meets the Definition of Done ([DEC-07](../DECISIONS.md#dec-07)); measurement only.
- **Replacing the Worker's weights.** The project's research rates Cyber-Tiel "not recommended" and names Tiel-Coder-35B-A3B-MTP as a same-size guardrailed drop-in; the owner kept Cyber-Tiel (DEC-04). A swap is a new decision with its own suite run.
- **A multi-machine inference pool**, and a local verifier model ranking passing samples (only if it beats gate-only selection at equal wall-clock, and only with an anchor set calibrating it — a learned scorer drifts without one, arXiv:2608.12564).
- **Rejected:** KV-cache eviction by random scoring (arXiv:2609.03430) — its gains are batch-128 datacentre gains, its failure mode (a fact stated once, never restated) is a tool loop's normal case, and it needs a forked engine; a learned tabular predictor for competence (LimiX-2) — a second resident model and an unreadable router; local LoRA or RL on the repository's history — too little data, too much forgetting.
- **Initialising difficulty and routing from public data** (SWE-bench annotations) — [measurement.md](measurement.md) says what may and may not be imported.
