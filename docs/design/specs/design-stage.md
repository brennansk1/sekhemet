# The design stage, new projects, and research

## 1. Purpose

Before a request has cards it has a shape, and deciding that shape is what a good project manager is for. This subsystem decides **how much** conversation a request deserves — usually none — holds that conversation the way a professional PM would, and, before any card is written, **looks for what already exists**: legally usable libraries and repositories, and the literature when the work is an algorithm. It serves the non-developer ("tell it what you want"), the beginner (a brief is what a professional writes first), and the spine: research is a role with no privileges of its own, and nothing it finds is trusted without a gate. It also serves the person who **inherits** a project someone else started and did not finish: before planning anything, it finds out what the repository claims and what actually runs (§2.10, [DEC-43](../DECISIONS.md#dec-43--take-over-a-project)). The backlog it hands on is [planner-pm.md](planner-pm.md)'s.

## 2. Behaviour

### 2.1 Proportion: most work needs almost none of this

1. **Proportion is the default behaviour, not an escape hatch**, and the small case is the common one. The failure to design against is not an under-planned calculator; it is a person who wanted a calculator and got interviewed about success metrics. *You don't need a consultation to build a calculator.*

| The request | The design stage is |
| --- | --- |
| "Add a `--json` flag" (a small change to an existing project) | Nothing. It is a card. |
| "Build me a calculator" | One sentence saying what is about to be built, then it starts. No brief, no question. |
| "A CLI that syncs my notes to S3" | At most two questions, each about something hard to change later, each with the default that will be used. No brief: the answers are assumptions on the cards. |
| "A multi-tenant billing service" | The six things in §2.3, a real conversation, a brief, and a question about whether it is two projects. |

2. The level is chosen **before any model is loaded**, in this order: **a brief** when being wrong is expensive (money, identity or personal data at stake); **questions** when the request names an external contract hard to change once code depends on it (sync conflict rules, storage credentials, the database, the calling protocol); **one sentence** for a new project or a change large enough to restate; **nothing** for a small change to an existing project. It errs toward less.
3. The rules only *decide* the level. The Planner role's model *phrases* what is said, classifies risk (the rules are its fallback), and writes the brief's prose (NEW-design-stage-1).

### 2.2 Propose and proceed, rather than ask and wait

1. **The default move is a statement, not a question:** what is about to be built, then doing it — *"A calculator — TypeScript, Vitest, the four operations, a CLI. Starting now."* The person can redirect in the next breath.
2. **Ask only when the answer is both uncertain and expensive to get wrong** (the data model, the deploy target, the public interface, anything a second person will build on). The test is "what does being wrong cost", not "am I certain".
3. **One question at a time**, the one that most changes the backlog; then decide whether a second is still worth asking. Never a list — except the one batch of up to five that opens a take-over (§2.10 step 5), an exception [DEC-43](../DECISIONS.md#dec-43--take-over-a-project) makes for a take-over only. **A question whose answers produce the same cards is not asked**, nor one the playbook, the brief or an earlier answer already settles ([planner-pm §2.10](planner-pm.md#210-questions-and-decisions)).
4. **"Just build it" is always a complete answer, and so is silence.** Every blank takes its default, recorded as an assumption, and work starts. Collaboration is offered, never required, and never re-offered after it is declined.
5. **Nothing is blocked on the conversation.** An unanswered question stays open on the board as a decision with its default ([planner-pm §2.10](planner-pm.md#210-questions-and-decisions)).
6. It is a conversation, not a form: no step is announced, and the words "requirements", "phase" and "let me gather" never appear in what the product says.
7. **The stack is detected, not assumed.** A request that names a language or runtime ("a Python script that renames photos") is planned in it; one that names none gets TypeScript on Node with Vitest, the stack the harness verifies best, stated as an assumption.
8. **Quality words are constraints, not work.** "Fast", "secure", "scalable", "reliable", "easy to use" leave the spec that is decomposed and become constraints with a stated default (for example *secure*: secrets only from the environment, every input validated where it enters). Request phrasing ("build me", "I want") is dropped from what is built.
9. **Every default is an assumption on every card** — in the dossier the Worker reads, and logged on the epic — and its outcome is recorded when a later card keeps or contradicts it.

### 2.3 What it produces: the brief, and the project documents

For the brief level only, a **project brief** is written. Its sections:

| Section | Why it earns its place |
| --- | --- |
| **Problem** | Who it is for, what they are trying to do, **what they do today instead** (the baseline to beat). |
| **Outcome** | What is different when it works, stated so it could be checked. |
| **Non-goals** | What it deliberately does not do; lets the planner refuse scope later without re-asking. |
| **Constraints** | Stack, deploy target, appetite, depth profile (§2.8), anything fixed; the quality constraints with their defaults. |
| **Prior art** | What exists, with licences and links, and how it is usually built (§2.5). |
| **Riskiest assumption** | The thing most likely to make it not work. It becomes the card right after the contract ([planner-pm §2.2](planner-pm.md#22-slicing)). |
| **The first slice** | The thinnest path through the whole backbone that produces something real. |
| **Definition of done** | The gates, agreed here rather than discovered at the first Verify. |
| **Invariants** | Architectural rules in the form the architecture gate enforces (`` `src/db/` does not import `src/cli.ts` ``). Omitted when there are none. |

Problem, Outcome and Non-goals are written from what the person said, and say *"not stated — assumed: …"* where they said nothing; they are never a fixed template. The **backbone** is the activities a user performs, in order; the first slice is narrow and complete through all of them, not one part finished properly.

**Where the project's documents live** ([DEC-30](../DECISIONS.md#dec-30--project-documents-follow-professional-conventions), under owner decision O12). The ledger is canonical for the brief, the requirements ([planner-pm §2.15](planner-pm.md)) and the decision records (spine rule 2). On every accepted change to them, Sekhemet **exports** them as Markdown where a professional team expects them, **adapting to the layout the repository already has rather than imposing one**, and commits every generated document through the Accept path on the integration branch, so it is reviewed like code:

| Document | Where | Format |
| --- | --- | --- |
| The brief | `docs/product/brief.md` | The sections above |
| The requirements | `docs/product/requirements.md` | One `### REQ-7 — title` heading per requirement; under it a line with `version`, `kano`, `must`, `slice`, `status` (proven, passing with strength unmet, planned, unplanned, suspect or cut) and `dependsOn`; its EARS criteria; the ids of the tests that prove it (generated) |
| Architecture decisions | `docs/decisions/NNNN-title.md` (MADR's default location), or the repository's existing ADR folder — `docs/adr/` or `doc/architecture/decisions/` — when one exists, numbered after its highest record | MADR 4.0: context and problem, drivers, options, outcome, consequences, confirmation; front matter `status`, `date` and `decision-makers` (display names resolved at export time) |
| The changelog | `CHANGELOG.md` at the root | Keep a Changelog, written from accepted cards and released slices; a new version's section is added above the earlier ones, which are never rewritten (the release itself is [planner-pm §2.15.8](planner-pm.md) and [review-git §2.6.7](review-git.md)) |
| Release notes, per slice, for people | `docs/product/releases/<version>.md` | Written from the slice's proven requirements in the brief's words ([planner-pm §2.15.8](planner-pm.md)) |
| Documentation for the project's users | The repository's existing documentation folder, else `docs/` | Organised by the Diátaxis framework: tutorials, how-to guides, reference and explanation |
| Documents a person attached for Seshat | `docs/product/inputs/<YYYY-MM-DD>-<name>` (the product folder `[docs] product` names), numbered when the path is taken | As the person sent them, byte for byte, with no generated header, so an export never rewrites them; committed by plumbing on the integration branch when a message or paste is longer than 8,000 characters or the composer attaches one ([planner-pm](planner-pm.md) §2.8 item 18, NEW-planner-pm-10) |

**`README.md` and `CONTRIBUTING.md` are the person's**: Sekhemet proposes changes to them as PM proposals and never writes them. Each generated file starts with *Generated by Sekhemet from ledger seq N; edit through Seshat or by pull request*. Files → ledger is **by proposal only**: when a merged commit changes a generated document, it is parsed, diffed against the ledger, and each difference becomes a PM proposal (the same path as a Jira CSV import, [integrations](integrations.md)); nothing changes in the ledger until a person applies one, and an applied requirement edit is a `requirement/revised` with its impact ([planner-pm §2.15](planner-pm.md)). `--no-names` writes role labels instead of people's names. **A document the person wrote themselves is never overwritten**: a file at that path without the generated header is imported as proposals instead (a person's `CHANGELOG.md` is only extended, as above). Only `config.toml`, `gates.toml` and these exported documents are meant to be tracked from Sekhemet's files ([security](security.md) owns the `.gitignore` block). Today the brief is written once to `.sekhemet/brief.md` and never updated (`wave2.ts:230-235`; NEW-design-stage-3).

### 2.4 A project that does not exist yet

1. **Card zero is the ecosystem's own generator**, never a model and never a template library of ours: `npm init` with `tsc --init` and Vitest for TypeScript, `uv init` for Python, `cargo new` for Rust, `pnpm create vite` for a web front end. Gates are derived from what it produced; the generator and its version are recorded in the brief so the scaffold is reproducible. The static layer (typecheck, lint, build) works from the first file.
2. **Card one is a failing test.** Its acceptance criterion is that the test exists, runs, and fails for the stated reason — at an assertion, not at an import ([gates](gates.md)) — verified by executing it. From card two every card has a functional gate.
3. **The ambiguous hour belongs to the conversation.** For genuinely novel architecture Seshat says *"talk it through with me, then I'll cut the cards"* rather than making a confident autonomous attempt.
4. A non-developer starts all of this with one sentence to Seshat ([planner-pm §2.9](planner-pm.md#29-starting-a-project-by-conversation)); `sekhemet init` on an empty directory offers the same path instead of stopping at "add typecheck, lint and test scripts".

### 2.5 Reuse before rebuild

The most expensive thing an agent does on a new project is write what a maintained, legally usable package already does. Whenever the design stage says anything at all (every level except *nothing*), planning looks first.

1. **What is searched.** For each *capability* the request needs, the planning model writes one to three short capability queries ("subscription billing", "payment provider SDK", "email sending") through its adapter, seeing the capability and the language only; the keyword extractor is the deterministic fallback when no Planning model is assigned, its server is not on this machine, its answer is unusable, or a live measurement has not yet admitted that model (DS-S8-3 as the owner amended it on 2026-09-28: `sekhemet research --reuse-eval --planner <model>`). The package registry takes every query; GitHub, whose unauthenticated search allows ten requests a minute, takes the first only, and so does a Python project's registry search, which is a GitHub search. Sources: the package registry of the project's ecosystem — **npm** for JavaScript and TypeScript, **PyPI** for Python — and **GitHub repositories** in that language; **the literature** (arXiv, OpenAlex) only when the need is an algorithm (ranking, matching, scheduling, compression, detection, similarity, forecasting). PyPI has no search API, so Python candidates are names found on GitHub, each verified against the PyPI JSON API (names proposed by the model are not built: see the departures under P7).
2. **Only short queries leave the machine** — never the spec, the code or a whole clause. A need with no keyword left after filtering is not searched.
3. **Filters, applied before anyone sees a result:**
   - *Relevance:* a candidate holds at least two of a query's words (every word of a one-word query) in its name, description or keywords, after Porter stemming, a hyphenated word also read joined ("e-mail" is "email") and a stem of four letters or more also matching the words it begins ("pars" finds "parser"); the queries are the need's own keywords and the capability queries. Relevant candidates are ranked by BM25 over the three fields in SQLite FTS5 (`node:sqlite`; a dense index is rejected, [DECISIONS](../DECISIONS.md)), the name weighted most, with a popularity prior: relevance scaled to the best candidate's plus half the popularity on a log scale against the most popular one's. Words that say what kind of thing is built ("CLI", "service", "handles") are dropped from the keyword query.
   - *Somebody uses it:* at least 1,000 weekly downloads (npm) or 20 GitHub stars. An unknown count is not a pass.
   - *Maintained:* archived repositories and ones untouched for two years are not recommended. In research mode the release date is deps.dev's for the version found ([DEC-44](../DECISIONS.md#dec-44--what-to-reuse-for-the-rest-of-phase-b)), and the registry's without it.
   - *Advisories:* a usable, maintained package whose version found has advisories on deps.dev is not recommended; it is named with the advisory ids. Without deps.dev (not allowed, unreachable), Prior art says the dates, licences and advisories were not checked there, and why.
   - *Licence,* by one SPDX-based classifier shared with the licence gate ([gates](gates.md)): permissive licences are recommended; weak copyleft (LGPL, MPL, EPL) is flagged; strong copyleft (GPL, AGPL) is named under exclusions so the choice is visible; code with no licence is dropped without comment; a licence the classifier cannot read is excluded and named. An `AND` expression is usable only if every part is; an `OR` if any part is. In research mode the licence is every SPDX expression deps.dev found for the version, joined with `AND` (the registry's own string when deps.dev names none).
   - *Correct silence:* when nothing passes — or the need is something no one would depend on a library for, like a calculator's arithmetic — nothing is recommended, and that is said.
4. **Candidates are worth checking, not guaranteed.** People hear *"may already cover this"*, never *"already does this"*. Before the Worker is told to depend on one, the Researcher has read its README (and, for a brief-level project, its API surface).
5. **A source that could not be reached is "not searched", never "nothing found."** The difference between "nobody has built this" and "I did not look" is the whole value of looking.
6. **Where results go.** Seshat says the best candidate per capability in one line; the brief's Prior art lists everything found with licences and links; **each card's dossier** carries what exists for the need it builds, linked by the need's id (not by matching words in its title), with the instruction to depend on it or say with `note` why none fits. **The Worker never searches**: it stays offline in its sandbox, and the choice reaches it as part of its card.
7. **For a brief-level project**, when the Researcher is configured and memory allows, one deep question — *how is this usually built, and what goes wrong* — runs before planning, and its cited answer goes into Prior art. When it cannot run, Prior art says so.

### 2.6 Network policy

1. **Research is opt-in and logged** ([SPINE](../SPINE.md#locked-for-v1): offline by default). The survey and every research fetch run only when `config.toml [network] research = "yes"` — the user's answer to the first-project question (§2.6.2), which a project may turn off for itself (`research = "no"` in its `config.toml`, or its research switch) — and never for a host in `fetch_deny`; `research` is independent of `mode`, which governs card commands and stays `offline` by default ([surface](surface.md) item 24). `--offline` and `SEKHEMET_OFFLINE=1` turn research off too.
2. **Asked once, on the first new project** (owner decision [O16](../../reference/OPEN_QUESTIONS.md#owner-decisions), decided 2026-09-25 by [DEC-33](../DECISIONS.md#dec-33)). The first time a new project is planned on this machine with research off, Seshat asks once: *may it search public package registries and GitHub with short keywords (never your spec or code) to avoid building what already exists?* The question names what a yes changes and lists the hosts research would reach: a yes enables only the harness's own research requests, through the one network policy ([surface](surface.md) item 24), and opens nothing for a card's sandboxed commands ([security](security.md) item 29a). **Nothing leaves the machine before the answer**, and the default if unanswered is no. The answer is recorded in the user's `config.toml`, so a yes turns research on for that project and every later one without asking again; a project may still turn it off for itself (a project file may only narrow). When off, planning says *"I did not look for existing packages: research is off"*.
3. Every query and its result set is an event in the log, and every fetch goes through the one polite path (robots respected, per-domain rate limits, private and local addresses never fetched). What may be fetched is [surface](surface.md)'s one network schema: `[network] mode` (`offline`, `allowlist`, `open`), **`fetch_allow`** (domains the Researcher may read; enforced today as the allowlist, `polite.ts:344-402`, under the old key `allow`) and **`fetch_deny`** (domains never fetched, whatever `fetch_allow` or `mode` says). **With `research = "yes"`, research may reach the effective `fetch_allow`'s hosts when that list is non-empty, otherwise any public host, minus `fetch_deny`**, whatever `mode` says — so a yes never widens a list the person wrote ([surface](surface.md) item 24, [security](security.md) item 29a). **The user's `config.toml` is authoritative**; a project's `config.toml` may only add domains to `fetch_deny`, narrow `fetch_allow` and set `research = "no"`, never widen `mode`, `fetch_allow` or `research` ([security](security.md) item 28). There is no second network path ([security](security.md)).

### 2.7 Research: a role with no privileges of its own

1. Research is a registry role and a card type, not a second harness. Fetching uses the one egress path; claim execution is a gate; model selection is the router; remembering uses the event log and the research cache. **Needing a second sandbox, scheduler, cache or permission model is evidence something does not belong here.**
2. **Lookup order:** the repository and its installed dependencies at the installed version (types, READMEs, source); local documentation and `llms.txt` per dependency version; the research cache; the live web — only when the earlier tiers miss and the project allows network. **The research cache** stores each page as extracted text with its URL, fetch date and content hash, indexed lexically; the same bytes under a second URL (a mirror, a redirect target, a versioned alias) resolve to the first URL that carried them, so the corpus holds one copy and one citation (`polite.ts:286-301`). **Each entry's lifetime follows what was cached, not its file type** (`ResearchCache.ttlFor`, `polite.ts:241-258`): a page at a pinned commit SHA or a `pinned:` key never goes stale by class, search result sets and package registry metadata last 1 day, papers, `llms.txt` and documentation sitemaps 30 days, official documentation 90 days, issue threads, forums, blogs and anything unclassified 14 days — every lifetime capped at the cache's 7-day default (`polite.ts:225, 280`), so in v1 no entry is served fresh after 7 days; only fresh entries are served. **Pages are read through Crawl4AI** when it is installed — a warm headless-browser sidecar started from a private virtual environment (`research/crawl4ai.ts`, `SEKHEMET_CRAWL4AI_HOME`, port 11235 by default, bound to loopback; `SEKHEMET_CRAWL4AI=off` turns it off), which renders JavaScript and returns the page as Markdown; Apache-2.0, its required credit carried with its output ([PROVENANCE](../../reference/PROVENANCE.md) rule 4) — and otherwise through the built-in polite fetcher, without rendered pages. Either way the read passes the same robots gate, rate limits and cache (`web.ts:245`, `polite.ts:386`).
3. **Deep research** (a card labelled `research`, or `sekhemet research`): restate the question as a brief (what counts as an answer, what is out of scope); decompose into sub-questions, each with a budget; gather with sub-researchers in isolated contexts that return findings with citations, never raw pages; a sub-question **closes** when it has independent sources of sufficient tier, and one still open is re-dispatched with different queries; stop on coverage of the sub-questions, not a step count; verify; synthesise. **Effort** is `quick`, `standard` or `exhaustive`, and sets the number of sub-questions, the pages read per sub-question and the verification depth; `exhaustive` runs overnight (NEW-design-stage-4; `research/effort.ts`).
4. **Verification.** Claims are typed: *executable* (an API exists, has this signature, behaves this way at this version) — run as a gate in the gate host's sandbox with **no network and no repository write access** (claim scripts are untrusted input), or recorded as *documented, not reproduced* with the reason; an executable claim whose run fails is struck from the report, with the failing run attached as evidence; *citational* — checked against text actually read, matched by URL or by normalised title, through one reference checker against the fetch ledger; *contested* — both positions reported with source tiers and dates, never silently flattened; *temporal* — dated by the newest source. Every claim carries its confidence and the check it survived. **The claim gate is a functional-layer gate declared in `gates.toml` and hash-pinned** like any other ([gates](gates.md)): it fails the card when an executable claim has neither a reproduction nor a recorded reason it could not be reproduced. It is not a rule the pipeline enforces on itself — a gate that lives in prose is a gate the model can reason around.
5. **Revision is gated, never self-graded.** Every draft carries a grounded risk vector measured outside the generated text: citations that point at nothing read (`badCitations`), open sub-questions (coverage), executable claims that did not reproduce, and grounding confidence from the source ledger. In deep mode one critique pass may propose a revision; it is **accepted only when no component worsens and at least one improves** (`acceptRevision`), otherwise the prior draft stands, and the pass stops when no candidate lowers the risk. Citation and coverage terms are recomputed per candidate (model-free); claims are re-run only for the sentences a revision touched. There is **no separate citation-repair pass**: a research report reaches Review when every executable claim has a verdict and no revision can lower its risk. Contested claims are reported with both positions, their source tiers and dates, and which is better supported and why (`adjudicate`, `renderDisagreements`) — never flattened into one confident sentence.
6. **What the Worker sees** is a research note: a short, cited summary with the excerpts the task needs, at a fixed budget, outside the byte-stable prompt prefix. Fetched text is always wrapped as untrusted; instructions inside it are inert. Package names found on the web are never installed without the supply-chain gate. No credentials are sent.
7. **Reproducibility.** Every query, fetch (with content hash), plan, and model and prompt version is recorded, so a run can be re-derived against its cache.
8. **Retrieval is lexical** (BM25 over heading-sized chunks, deduplicated by content hash rather than URL, weighted toward primary sources). A dense index is rejected on this machine's terms: its resident memory is what the Worker needs, the corpora are hundreds of chunks, and questions name exact identifiers ([DEC-22](../DECISIONS.md#dec-22--rejected-techniques)).
9. **The hardware envelope.** On the 24 GB reference host roles do not co-reside; the Researcher is one registry entry used for both gathering (a tool loop) and synthesis, qualified by the bake-off, not chosen by reputation. Quality comes from more passes, better retrieval and executable checks, not a larger model.
10. **Tools.** The Researcher has `search`, `fetch`, `docs`, `scholar`, `paper`, `repo`, `deps` and the project's MCP tools. Repository reading is first-class and deterministic, built on `git` and `gh`: a dependency's own source at the installed version; a repository's tree and any file at any ref; code search in a repository and across GitHub; releases and CHANGELOG entries **diffed between the installed and the proposed version**; issues and pull requests including closed ones; blame for a line range; a shallow clone into the cache when a question needs more than a few files. Results at a commit SHA never go stale by class; in v1 they are held within the cache's 7-day cap like every entry (rule 2), and the indefinite lifetime arrives with the full expiry table (§7). **The Worker's read-only research tools** are `docs`, `git_history`, `dependencies`, `ask` and `recall` (`packages/loop/src/tool_catalog.ts`), specified in [worker-loop](worker-loop.md); it never has `search` or `fetch`.
11. **Search** takes 1–6 terms per query, prefers primary sources (official docs, source repositories, standards, papers) over aggregators, and treats recency as a parameter ("the current way" versus "always true"). The web-search provider is one the person configures — a self-hosted **SearXNG** (no API keys, no query logging to a third party; AGPL-3.0, so it runs as a separate service and is never embedded, [PROVENANCE](../../reference/PROVENANCE.md)), or a Brave or Tavily key the person supplies (optional, used only when `research = "yes"`; allowed because a person may prefer a hosted search over a self-hosted one, and the provider sees the queries, which the Integrations card says); papers, page reads and GitHub work without one.

### 2.8 How deep to build: coverage does not rely on the interview

Models find about a third of the requirements people leave unsaid, and almost none of the "style" ones ([research](../../research/PROJECT_DONE_AND_DEPTH.md), ReqElicitGym). So the requirement graph ([planner-pm §2.15](planner-pm.md)) is filled from four sources, and the conversation is only one of them:

1. **The conversation** — clarifying questions (they beat open probing), each asked only when its answer changes the cards, one at a time, with a proposed default.
2. **A depth profile**, proposed from the request and confirmed with the person: *prototype*, *internal tool*, *production* or *regulated*. The profile selects which rows of a quality checklist built on ISO/IEC 25010:2023 are must-haves — functional suitability, performance, compatibility, interaction capability (including accessibility), reliability (error handling, persistence, recovery), security, maintainability, flexibility, safety — and turns each must-have row into a requirement with a test or a project-gate invariant. A calculator is a *prototype* and gets no questions; a payments service is *production* or *regulated* and gets a short conversation. The profile also sets the default appetite, **the test-strength rule a requirement must meet to count as proven** ([gates](gates.md)), and **which tests a person approves** — none for *prototype* and *internal tool*, the example tables of must-haves for *production*, every acceptance-test file and mutation waiver for *regulated* ([planner-pm §2.17](planner-pm.md)). **The *regulated* profile claims no compliance**: it selects stricter checks and more human approval, and nothing Sekhemet says or exports states that a project meets any standard or regulation — a compliance pack or any compliance claim is out of v1 ([SPINE](../SPINE.md#locked-for-v1)).
3. **Comparable products.** The Researcher finds comparable open-source projects and products (the same search as the reuse survey, §2.5) and lists their features. A feature most comparables share becomes a *must-be* candidate; a rarer one a *performance* or *attractive* candidate. Every candidate carries its sources; a feature with none — one the model imagined — is a proposal only, never a requirement, until a person accepts it.
4. **A walkthrough.** The story map is walked once from each user's point of view (Elicitron-style), and each step where the user would be stuck becomes a candidate requirement.

The person sees the candidates grouped by Kano class with must-be first, accepts, edits or rejects them, and can move the line between slices. Nothing the model proposed enters the graph without that acceptance. Each accepted requirement gets a stable id and version 1; every later accepted edit bumps the version and marks downstream links suspect ([planner-pm §2.15](planner-pm.md)).

### 2.9 A stakeholder starts a project

How a person who is not an engineer — a Stakeholder in the Team setup, or anyone on their own machine — starts a project with Seshat ([DEC-35](../DECISIONS.md#dec-35--one-product-two-setups-solo-and-team), [DEC-36](../DECISIONS.md#dec-36--the-ai-is-a-teammate-that-proposes-people-decide); [teams](teams.md) item 21). It is §2.1–2.8 seen from their side; nothing here changes the proportion rules.

1. **The conversation and the draft are the stakeholder's.** Others see them only once sent for approval.
2. **Research consent is asked once**, on the first new project, and the answer holds for later ones (owner decision O16, [DEC-33](../DECISIONS.md#dec-33); [security](security.md) NEW-security-8).
3. **The Type is proposed with its reason** — Prototype, Internal tool, Production or Regulated, the depth profile of §2.8 in [DEC-31](../DECISIONS.md#dec-31)'s words (*Production: people outside your team will sign in and pay*) — and the stakeholder can change it.
4. **At most two questions** (§2.2), each with its default; every unanswered one is recorded as an assumption.
5. **Candidates by priority.** The candidates of §2.8 are listed under *Must have*, *Should have* and *Could have*, each with *Accept* and *Remove*, and a **release line** the stakeholder drags to decide what the first release holds. Nothing enters the plan without that acceptance (§2.8). The on-screen words keep §2.2.6's rule in what Seshat says: candidates are named, and no step is announced. On the start page (§2.11) the draft's list may be titled *Requirements*, as the approved Start mockup titles it (DEC-51; before it, never a "requirements" heading anywhere — the later ruling wins).
6. **Review plan** shows, before anything exists:
   - the brief as *Problem*, *Outcome*, *Users*, *Not in scope*, *Constraints*, *Prior art*, *Riskiest assumption* and *Done means* (§2.3's Problem, Outcome, Non-goals, Constraints, Prior art, Riskiest assumption and Definition of done, with *Users* drawn from Problem's "who it is for");
   - the releases, each with its forecast as a range, 50% and 85% ([planner-pm](planner-pm.md) §2.6 item 3), or *Not enough history yet*;
   - the assumptions;
   - what approval creates: the project, its epics and issues, the brief and card zero, counted.
7. **Approval.** In the Team setup the stakeholder, or a Member who leads no project, presses **Send for approval** and names as the approver a person who may create a project — an Admin, or a person who leads a project in the workspace ([teams](teams.md) items 6 and 21; [DEC-57](../DECISIONS.md#dec-57--a-server-is-a-workspace-with-many-projects), the later ruling; *a Member or Admin* before it); the approver can approve, ask a question in the thread, or edit the plan. In Solo the button is **Create project**. **Nothing is created before approval** — no project, issue, brief or card zero ([teams](teams.md) TEAM-20; [planner-pm](planner-pm.md) §2.9). The issues the approved plan creates are assigned to the approver by default (the stored `owner`; *Assignee* on screen, DEC-52), and the assignee can be changed ([teams](teams.md) item 21, TEAM-42).

### 2.10 Taking over a project

A repository someone started and did not finish — a colleague's prototype, an abandoned side project, a half-delivered contract, a codebase another coding agent left half-built — is taken over, not started ([DEC-43](../DECISIONS.md#dec-43--take-over-a-project)). **Take over a project** sits beside **Start a project** on the empty board ([dashboard](dashboard.md) item 10), and in a workspace of many projects *New project* offers it as **Add an existing repository**, for a path the person names (§2.11 item 6; [DEC-57](../DECISIONS.md#dec-57--a-server-is-a-workspace-with-many-projects)). Seshat's `take_over_project` tool starts it from a conversation, and the first run offers it for a repository with history ([surface](surface.md) items 9–12). A take-over includes onboarding and adds what onboarding does not: finding out what is true, then deciding with the person what to do next. The professional move on an inherited codebase is to find out what runs before believing what is written, to pin today's behaviour before changing it, and never to rewrite. Six steps, in this order; each step's result is an event, so a take-over replays.

1. **Trust first.**
   - **Nothing from the repository runs before workspace trust** ([security](security.md) S9, items 38–40): no install, build, test, language server, hook or script. Steps 1 and 2 only read files and git objects.
   - **The repository's own agent configuration is inert**: `.claude/`, `.cursor/`, `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.envrc` and git hooks (`.githooks/`, `.husky/`, `.pre-commit-config.yaml`, anything under `.git/hooks/`). Sekhemet never runs it, and its text is untrusted content ([security](security.md) items 38a, 42) until a person approves it, file by file, by SHA-256. The approval is stored as workspace trust is (item 39): in the user directory, keyed by the repository's real path and each file's SHA-256, never in the repository; a ledger event records it for audit only. In the Team setup only an Admin may trust a repository ([teams](teams.md)). An approved file's commands and gotchas may then enter the draft playbook; its prose never becomes an instruction to a role.
   - **The full history is scanned for secrets, offline**: with gitleaks when it is installed, otherwise with a bundled offline rule set ([security](security.md) item 34c). A finding names the commit, the path and the rule, never the secret, and asks the person to rotate it. Sekhemet never rewrites history on its own initiative.
   - **No submodule is cloned or initialised recursively.** Each is listed with its path and URL as a finding; a person may initialise one after trust.
   - Trust is asked once, showing exactly what would run: the install, build and test commands of step 3, each confined.
2. **Recon without a model.** Deterministic readers only; no model is loaded.
   - Manifests and lockfiles: the dependencies and their versions; each one's age from registry metadata when research is allowed (§2.6), otherwise *not checked: offline*; known vulnerabilities from an offline database (osv-scanner's, [gates](gates.md)) when one is present, otherwise *not checked*.
   - Scripts, CI workflows and the gates they would become ([surface](surface.md) item 9b); workspaces (9d).
   - The ranked repo map ([context](context.md)).
   - Git history: the last commits and their dates; branches not merged into the default branch, with their last commit; churn hotspots (files by the number of commits that changed them).
   - README, docs, ADRs, TODO and FIXME comments with their locations, the connected tracker's open issues ([integrations](integrations.md)), and transcripts a previous agent left, if present — all read as untrusted text.
3. **Prove what works by running it.** After trust, everything runs confined.
   - Install with lifecycle scripts off (`--ignore-scripts` for npm, pnpm and yarn), reaching only what the network policy allows, or offline from the local store. An ecosystem that cannot install without running package code (a Python source distribution's build) runs that step confined like any repository code.
   - Build and run the test suite confined with **no network, twice**. This is onboarding's baseline ([surface](surface.md) item 9c; [gates](gates.md) rule 15a, NEW-gates-7), recorded once and reused by every later card.
   - Every result is recorded: what built, which tests passed, failed or flaked, with the command and exit code.
   - **"Could not build" is a first-class finding** with its reason — a missing system tool, a secret, a service, a network need, a broken lockfile — and never a stall. The take-over continues on what could be read, and the repair becomes a *stabilise* card.
   - **Half-done work is detected deterministically**: stubs and "not implemented" bodies (`throw new Error("not implemented")`, `NotImplementedError`, `todo!()`, `unimplemented!()`); skipped and todo tests (`it.skip`, `it.todo`, `xit`, `@pytest.mark.skip`, `#[ignore]`); routes or UI controls with no handler; imports of modules that do not exist; a schema with no migration that creates it. Each is a finding with its file and line.
4. **A brief as found.** Seshat (the Planner role) drafts the brief of §2.3 as the project stands: what it **claims** — README, docs, ADRs, issues, commit messages — set against the **evidence** of steps 2 and 3. Each claim carries one label:
   - **proven** — only when it cites an executed result from step 3: a test that passed in both runs, or a build that succeeded. A model's reading of the code never makes a claim proven (spine rule 1);
   - **claimed, unproven** — nothing executed confirms or contradicts it;
   - **contradicted** — an executed result or a step-3 finding says otherwise (a failing test, a stub, a missing module).

   Every claim cites file:line, test ids or commits. All repository text enters the prompt as untrusted content ([security](security.md) item 42). The brief as found seeds the brief and the requirement graph ([planner-pm](planner-pm.md) §2.9 item 4, §2.15) once the person approves the plan.
5. **One PM conversation.** Seshat asks **one batch of up to five** questions at the start, ranked by how much each answer changes the plan and by whether this person can answer it. Each is a decision request ([planner-pm §2.10](planner-pm.md#210-questions-and-decisions)) with the `safe_default` policy and a **default that cites a finding** (*"The README says it exports PDF, but no code does. Default: leave PDF out of the first release."*). The topics are the goal and the users, what "done enough" means, what must not change (an API others call, a data format, a deployment), and what to cut. It is proportional — a small leftover gets one question or none — and in plain words a non-developer can answer. **When the person approves the take-over plan, every question still unanswered takes its default**, recorded on the ledger (`decision/default_applied`); no timer and no deadline decide anything. This batch is an exception, for a take-over only, to §2.2.3's one question at a time, to [planner-pm](planner-pm.md) PM-P2-3's two open questions per pass and to the reversal recorded in planner-pm §9 — [DEC-43](../DECISIONS.md#dec-43--take-over-a-project) is the later ruling: an inherited project has no request to restate, so the person's context is needed once, together, before a plan exists. Every other rule holds: each question has its default, and nothing waits on an answer.
6. **A backlog with evidence, then approval.**
   - **Three tiers.** *Stabilise*: a broken build and failing tests — each a `fix` card, or a `characterize` card where the right behaviour is unknown ([planner-pm §2.16](planner-pm.md)). A broken build's `fix` card has the build command failing on the base as its red check ([gates](gates.md) rule 6b, planner-pm §2.16 item 1). A secret to rotate is not a card for the Worker: it is a task for a person — a decision request, or a card assigned to a person — because rotating it happens at the provider, outside the repository. *Finish*: the half-built features of step 3 that the person keeps. *Defer*: the rest, named and not planned.
   - **Inherited issues are reconciled against the code** — already done, duplicate, stale or valid — as proposals ([integrations](integrations.md) item 18a, NEW-integrations-4).
   - **Every card links its evidence**: the finding, test id, file:line or commit that made it.
   - **Characterize before change; no rewrite.** A card whose scope has no test that executes it on the base gets a `characterize` card first ([planner-pm §2.16](planner-pm.md) item 2), and a rewrite of a part whose tests pass is never proposed.
   - **The person approves the plan** (*Review plan* and approval as in §2.9 items 6–7); nothing is created before. Then normal work proceeds. The requirement graph is seeded from the brief as found ([planner-pm §2.15](planner-pm.md#215-when-a-project-is-done--computed-never-claimed)): each **proven** claim becomes a requirement whose links to the baseline's tests are **proposed**, unconfirmed until a person confirms them (`trace/confirmed`), and whose status is computed by planner-pm §2.15.5 like any other — *passing, strength unmet* until the tests' strength is measured; the claimed-unproven ones become candidates the person accepts or cuts (planner-pm §2.15).

## 5. Changes for v1

### P2 — Start a project by conversation (design side)
*Non-developers cannot start a project; there is no card zero.*

- **DS-P2-1** WHEN a new project's stack is TypeScript THE SYSTEM SHALL make card zero run the ecosystem generator (npm init, `tsc --init`, Vitest), record the generator and its version in the brief, and derive the gates from its output.
- **DS-P2-2** WHEN a new project's stack is Python THE SYSTEM SHALL make card zero run `uv init` and derive the gates from its output.
- **DS-P2-3** WHEN card zero is done THE SYSTEM SHALL make card one a test whose gate passes only when the test runs and fails at an assertion for its stated reason.
- **DS-P2-4** WHEN `sekhemet init` runs in an empty directory THE SYSTEM SHALL offer to start a project by conversation instead of printing only "No gates found".
- **DS-P2-5** WHEN the five greenfield specs (calculator, Python photo renamer, notes-to-S3 sync CLI, billing service, recipe site with sign-up) are started by a scripted non-developer conversation THE SYSTEM SHALL reach green gates after card one on each, with no shell command in the transcript.
- **DS-P2-6** WHEN a person opens *Review plan* THE SYSTEM SHALL show the brief under Problem, Outcome, Users, Not in scope, Constraints, Prior art, Riskiest assumption and Done means, each release with a 50% and 85% forecast or *Not enough history yet*, the assumptions, and the count of what approval creates, and SHALL have created nothing.
- **DS-P2-7** WHEN candidates are shown for a new project THE SYSTEM SHALL group them as Must have, Should have and Could have with *Accept* and *Remove* on each and a movable release line, SHALL propose the Type with its reason, and SHALL ask at most two questions, recording each unanswered one as an assumption. (Send for approval in the Team setup is [teams](teams.md) TEAM-20.)

### P14 — Depth and coverage: profile, checklist, comparables, walkthrough

Today the design stage produces a brief from the conversation alone; depth is whatever the model thought of ([research](../../research/PROJECT_DONE_AND_DEPTH.md)).

- **DS-P14-1** WHEN a new project or feature brief is started THE SYSTEM SHALL propose a depth profile (prototype, internal tool, production, regulated) with its reason, and SHALL record the person's choice.
- **DS-P14-2** WHEN a depth profile is chosen THE SYSTEM SHALL add a requirement for every quality-checklist row that profile marks must-have, each with an acceptance criterion or a project-gate invariant; a *prototype* SHALL add none.
- **DS-P14-3** WHEN a depth profile is chosen THE SYSTEM SHALL record with it the test-strength rule and the test-approval level it selects (§2.8.2), and every later card of the project SHALL use them.
- **DS-P14-4** WHEN the *regulated* profile is proposed or chosen THE SYSTEM SHALL say that it selects stricter checks and claims no compliance, and no brief, requirement, release note or exported document SHALL state that the project complies with a standard or regulation.
- **DS-P14-5** WHEN research is allowed and the request names a kind of product THE SYSTEM SHALL list comparable projects or products with their sources, and SHALL propose each feature found in at least half of them as a *must-be* candidate citing those sources.
- **DS-P14-6** WHEN a candidate requirement has no source other than a model THE SYSTEM SHALL label it a proposal and SHALL not add it to the requirement graph until a person accepts it.
- **DS-P14-7** WHEN the story map exists THE SYSTEM SHALL walk it once per named user role and SHALL record each step with no supporting requirement as a candidate.
- **DS-P14-8** WHEN the design stage asks a question THE SYSTEM SHALL ask it only if at least two of its answers produce different cards, and SHALL offer a default.
- **DS-P14-9** WHEN research is not allowed THE SYSTEM SHALL say that comparables were not searched, and SHALL not present the checklist and conversation as complete coverage.
- **DS-P14-10** WHEN a person accepts a candidate requirement THE SYSTEM SHALL give it a stable id and version 1, and SHALL never reuse the id.

### NEW-design-stage-1 — Design-stage judgement
*Keyword risk detection misfires both ways, the billing service is asked nothing, the brief is a form letter, and the stack is forced (domain08 §1). No COVERAGE id covers the conversation's quality; P2 covers only the tool.*

- **DS-N1-1** WHEN the request is "a CLI that shows my laptop charging status", "a static blog with author pages", "a password generator CLI" or "a health check endpoint" THE SYSTEM SHALL NOT choose the brief level.
- **DS-N1-2** WHEN the request is "a recipe website where people can sign up and save favourites" THE SYSTEM SHALL choose the brief level with an identity riskiest assumption.
- **DS-N1-3** WHEN the request is "build me a calculator" THE SYSTEM SHALL ask no question and say one sentence naming the four operations.
- **DS-N1-4** WHEN the level is brief THE SYSTEM SHALL ask first the one question that most changes the backlog, with its default, and planning SHALL proceed on that default while it is open; one question is the first, not the cap — WHEN a further question still changes the cards THE SYSTEM SHALL ask it after the first, one at a time, with never more than two open per planning pass ([planner-pm §2.10.1](planner-pm.md#210-questions-and-decisions)).
- **DS-N1-5** WHEN the request is "a Python script that renames photos" THE SYSTEM SHALL plan it in Python and SHALL NOT assume TypeScript.
- **DS-N1-6** WHEN a spec reads "…scale to many users. A retried charge must never charge a customer twice." THE SYSTEM SHALL keep the second sentence in the spec that is decomposed, as a hard invariant.
- **DS-N1-7** WHEN any design-stage text is shown to a person THE SYSTEM SHALL contain none of the words "requirements", "phase" or "let me gather".
- **DS-N1-8** WHEN a brief is written and the person gave no non-goals THE SYSTEM SHALL write "Not stated — assumed:" with the assumed non-goals rather than a template sentence.

### NEW-design-stage-3 — Project documents in the repository, generated from the ledger
*The brief is a one-off file under tooling state, there is no requirements or decision document, and a team cannot review requirements in a pull request or keep its reasoning if it leaves ([DESIGN_RESEARCH_TEAMS_DATA_CHANGE](../../research/DESIGN_RESEARCH_TEAMS_DATA_CHANGE.md) decision 14; DS-T1…T3).*

- **DS-N3-1** WHEN the brief, a requirement or a decision record is accepted or revised THE SYSTEM SHALL regenerate `docs/product/brief.md`, `docs/product/requirements.md` (each requirement with its EARS criteria, Kano class, slice and status) and the decision records as `docs/decisions/NNNN-title.md` (MADR 4.0), each headed with the ledger `seq` it was generated from, and commit them through the Accept path on the integration branch.
- **DS-N3-2** WHEN a merged commit changes a generated project document THE SYSTEM SHALL parse it, diff it against the ledger, and create one PM proposal per difference; it SHALL NOT change the ledger until a person applies a proposal.
- **DS-N3-3** WHEN documents are exported with `--no-names` THE SYSTEM SHALL write role labels instead of people's names.
- **DS-N3-4** WHEN the product or decisions folder is configured to another path THE SYSTEM SHALL export there and nowhere else.
- **DS-N3-5** WHEN a file already exists at an export path without the generated header THE SYSTEM SHALL leave it unchanged and offer its content as proposals.
- **DS-N3-6** WHEN the repository already has an ADR folder (`docs/adr/` or `doc/architecture/decisions/`) and no decisions folder is configured THE SYSTEM SHALL write each new decision record there, numbered after the highest existing record, and SHALL create no `docs/decisions/`.
- **DS-N3-7** WHEN an export would change `README.md` or `CONTRIBUTING.md` THE SYSTEM SHALL offer the change as a PM proposal and SHALL NOT write either file.
- **DS-N3-8** WHEN a release is proposed for a slice THE SYSTEM SHALL propose a section for its version at the top of `CHANGELOG.md` in the Keep a Changelog format, from the slice's accepted cards, and `docs/product/releases/<version>.md` from its proven requirements, both committed through the Accept path before the tag; every earlier section of `CHANGELOG.md` SHALL stay byte-identical.
- **DS-N3-9** WHEN Sekhemet generates documentation for a project's users THE SYSTEM SHALL file each page as one of tutorial, how-to guide, reference or explanation (Diátaxis), in the repository's existing documentation folder when one exists.

### P7 — Reuse survey by capability, with one SPDX licence classifier
*Live, the survey recommends wrong packages, rejects MIT-0 (nodemailer), and offers npm to Python projects.*

- **DS-P7-1** WHEN the licence string is `MIT-0`, `Zlib`, `BlueOak-1.0.0`, `BSL-1.0`, `MIT AND Apache-2.0`, `Apache 2.0` or `BSD-3-Clause` THE SYSTEM SHALL classify it permissive in both the survey and the licence gate.
- **DS-P7-2** WHEN the licence is `LGPL-3.0-or-later` or `MPL-2.0` THE SYSTEM SHALL classify it weak copyleft and flag it; WHEN it is `GPL-3.0-only` or `AGPL-3.0` THE SYSTEM SHALL exclude and name it; WHEN it is absent THE SYSTEM SHALL drop the candidate silently.
- **DS-P7-3** WHEN the survey and licence-gate tests run THE SYSTEM SHALL compute every `usable` verdict with the production classifier, never from a fixture value.
- **DS-P7-4** WHEN a candidate's weekly download count is missing or zero and it has fewer than 20 stars THE SYSTEM SHALL NOT recommend it.
- **DS-P7-5** WHEN the project is Python THE SYSTEM SHALL search PyPI (by verified name) and GitHub in Python, and SHALL NOT query npm.
- **DS-P7-6** WHEN the need is "a calculator" THE SYSTEM SHALL recommend no package and say that none is needed.
- **DS-P7-7** WHEN the labelled set of about 40 needs is run THE SYSTEM SHALL record precision@1 and the correct-silence rate, and both SHALL be no lower than the pre-change baseline recorded on the same set.
- **DS-P7-8** WHEN a planning model rephrases card titles THE SYSTEM SHALL still attach each need's findings to the card built for that need.
- **DS-P7-9** WHEN Seshat's `find_library` or the Researcher's `find_library` returns candidates THE SYSTEM SHALL have applied the same relevance, popularity, maintenance and licence filters as the survey, and SHALL judge GitHub results with the same classifier whichever search path found them.
- **DS-P7-10** WHEN the level is brief, the Researcher is configured and no card is running THE SYSTEM SHALL write one cited deep answer to Prior art; otherwise Prior art SHALL say the deep question did not run and why.
- **DS-P7-11** WHEN candidates are relevant to a need THE SYSTEM SHALL order them by BM25 over their names, descriptions and keywords in SQLite FTS5, with a popularity prior, not by the registry's order. *(Compliance C3: REUSE_SURVEY_2026-09, domain08 §6.)*
- **DS-P7-12** WHEN a Planning model on this machine is assigned and admitted (DS-S8-3) THE SYSTEM SHALL search each need by one to three capability queries it writes from the capability and the language alone; WHEN none is, it is not admitted, or its answer is unusable, THE SYSTEM SHALL search by the need's keywords. *(Compliance C3; admission added by the owner's ruling of 2026-09-28.)*
- **DS-P7-13** WHEN research is allowed and the person's yes names `api.deps.dev` THE SYSTEM SHALL take each candidate's release date, licences and advisories from deps.dev for the version found, SHALL NOT recommend a version with advisories and SHALL name it; otherwise it SHALL keep the registry's facts and say in Prior art that deps.dev was not checked and why. *(Compliance C3: DEC-44.)*
- **Departures from REUSE_SURVEY_2026-09 and the review, with reasons** (compliance C3): deps.dev is asked about packages only, not GitHub repositories (GitHub's own licence and push date already feed the filters) and its OpenSSF Scorecard and dependents are not used (the survey's floors are downloads and stars; Scorecard stays in §7). A stem of four letters or more also matches the words it begins, because Porter keeps "parser" and "server" apart from "parse" and "serve": this rule was added after the first offline run, in which BM25 without it scored 15 of 34 and lost YAML and WebSocket, so it is fitted to that run in part. The popularity prior's weight, 0.5, was fixed before the offline measurement and is not tuned to it. GitHub, and a Python project's registry search, take the first capability query only (ten unauthenticated searches a minute). Python names proposed by the model (§2.5 item 1's first reading) are not built: every name still comes from GitHub and is verified on PyPI. The review's "the Researcher reads the README before the Worker is told to depend on it" is unchanged (§8 question 2).

### S8 — `plan` honours offline mode and the research setting, and logs its queries
*The local-first promise.*

- **DS-S8-1** WHEN `config.toml [network] research` is not `yes`, or the project's research switch is off, or `--offline`/`SEKHEMET_OFFLINE=1` is set, THE SYSTEM SHALL make zero network requests during `sekhemet plan` and say that it did not look; WHEN `research = "yes"`, `mode = "offline"` and `fetch_allow` is empty THE SYSTEM SHALL let research fetch a public host not in `fetch_deny` while every card command still has no route out.
- **DS-S8-2** WHEN research is off and the first new project on this machine is planned THE SYSTEM SHALL ask once whether to enable it, naming each host a yes would allow, make no network request before the answer, take no as the default, and record the answer in the user's `config.toml` (O16's default).
- **DS-S8-6** WHEN a person answered yes on an earlier project THE SYSTEM SHALL NOT ask again on a later new project, and its survey SHALL run; WHEN a project's own configuration turns research off THE SYSTEM SHALL make no research request for that project.
- **DS-S8-8** WHEN a person answers yes to the research question THE SYSTEM SHALL record the hosts it named as `[network] research_hosts`, and SHALL send research to a host of `RESEARCH_HOSTS` only when the yes covers it (a yes recorded without a list covers the hosts the question named before `pypi.org`); WHEN a new project is planned with a terminal and a research host is uncovered and not declined THE SYSTEM SHALL ask once, naming only the uncovered hosts, and record the union (a no in `research_hosts_declined`); until then it SHALL NOT reach an uncovered host and SHALL say which hosts await a yes. *(Lead ruling, review of B4.5.)*
- **DS-S8-7** WHEN `research = "yes"` and the effective `fetch_allow` is non-empty THE SYSTEM SHALL fetch for research only from its hosts (and their subdomains) not in `fetch_deny`, and SHALL refuse and log a fetch to any other host, whatever `mode` says ([security](security.md) SEC-52b, [surface](surface.md) SUR-48c).
- **DS-S8-3** WHEN the survey sends a query THE SYSTEM SHALL append a `research/query` event with the source, the query text, the result names and who wrote the query (`origin`), and the query SHALL contain no word that is not in the need's keyword set, except the search's language qualifier (`language:python`, `language:rust`, `language:go`) for a project in that language, or SHALL be a capability query the Planning model wrote from the capability and the language alone, cut to at most four plain words; a registry lookup by a name the search returned (PyPI's, deps.dev's) is a query too, and SHALL be recorded with that name. - **DS-S8-4** WHEN a need has no keyword left after filtering THE SYSTEM SHALL NOT send a query for it.
- **DS-S8-5** WHEN the papers source errors THE SYSTEM SHALL report literature as "not searched (unreachable)", never as "nothing found".

### NEW-design-stage-2 — Research that can be verified and does not park wrongly
*The claim gate cannot pass, citation checks differ by pipeline, memory leaks across repositories, and research quality is unmeasured (domain08 §2, §6.7). Not in COVERAGE.*

- **DS-N2-1** WHEN a research answer contains an executable claim that was not run THE SYSTEM SHALL record it as "documented, not reproduced" with the reason and let the card reach Review.
- **DS-N2-2** WHEN an executable claim has neither a reproduction nor a recorded reason THE SYSTEM SHALL fail the claim gate, which SHALL be declared in `gates.toml` and covered by the gate contract's hash.
- **DS-N2-3** WHEN a claim script runs THE SYSTEM SHALL run it in the gate host's sandbox with no network and no write access to the repository.
- **DS-N2-4** WHEN any research pipeline checks citations THE SYSTEM SHALL check each against text actually fetched and recorded, matched by URL or by normalised title, and strike or flag a citation that points at nothing read.
- **DS-N2-5** WHEN a cached answer was recorded for another repository or another installed version of the package in question THE SYSTEM SHALL NOT reuse it.
- **DS-N2-6** WHEN a critique pass proposes a revision that raises `badCitations` or the count of unreproduced executable claims THE SYSTEM SHALL keep the prior draft; WHEN it lowers one component and raises none THE SYSTEM SHALL accept it; WHEN no candidate lowers any component THE SYSTEM SHALL stop.
- **DS-N2-7** WHEN every executable claim in a research report has a verdict and no candidate revision lowers its risk THE SYSTEM SHALL move the card toward Review, with no separate citation-repair pass.
- **DS-N2-8** WHEN two sources disagree on a claim THE SYSTEM SHALL report both positions with their source tiers and dates and name the better-supported one with its reason.
- **DS-N2-9** WHEN the research golden set (25 software questions with checkable answers: API signatures at pinned versions, licences, release dates) runs THE SYSTEM SHALL record accuracy and citation precision per pipeline, versioned with the set's hash; WHEN one pipeline's accuracy is lower than another's by a difference an exact paired test on the set rejects at 0.05 THE SYSTEM SHALL route research questions to the better pipeline by default and mark the other "not recommended" in `doctor` (removing its code is a workstream decision, not system behaviour).

### NEW-design-stage-6 — Take over a project
*A person with a half-built repository has no path: onboarding assumes a maintained team repository, runs language servers before trust, and nothing finds out what the project claims against what runs ([DEC-43](../DECISIONS.md#dec-43--take-over-a-project), owner-approved 2026-09-25). Trust, recon and the as-built inventory (DS-TO-1 to DS-TO-8; *could not build* recorded as a finding only) are built with the first run in B4.1, after B4.0b, whose onboarding baseline (NEW-gates-7) DS-TO-6 writes; the brief as found, the conversation, the backlog and the reconciliation of inherited issues (DS-TO-9 to DS-TO-16) with starting a project in B4.4.*

- **DS-TO-1** WHEN a repository is taken over and no person has trusted it THE SYSTEM SHALL run no install, build, test, language server, hook or script from it, and SHALL only read its files and git objects.
- **DS-TO-2** WHEN a taken-over repository contains `.claude/`, `.cursor/`, `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.envrc` or git hooks THE SYSTEM SHALL execute none of them, SHALL pass their text to a prompt only as untrusted content, and SHALL let a file's commands into the draft playbook only after a person approves that file's SHA-256 ([security](security.md) SEC-54).
- **DS-TO-3** WHEN a repository is taken over THE SYSTEM SHALL scan every commit of its history for secrets with gitleaks when it is installed and the bundled offline rule set otherwise, SHALL make no network request for the scan, SHALL record which scanner ran and each finding's commit, path and rule, SHALL record *history not scanned* with the reason whenever git or the scanner could not read the history, and SHALL NOT record or show the secret ([security](security.md) SEC-55). *Scope (the lead's ruling under DEC-42 on [security](security.md) item 21, B4.1):* a repository whose only preflight finding is `core.hooksPath` (Husky) SHALL be scanned, its git run with hooks forced off (`core.hooksPath=/dev/null` on the command level); any other preflight finding SHALL still refuse the scan with *history not scanned* and the reason.
- **DS-TO-4** WHEN a taken-over repository declares submodules THE SYSTEM SHALL clone or initialise none of them, and SHALL list each with its path and URL.
- **DS-TO-5** WHEN recon runs THE SYSTEM SHALL load no model, and SHALL record the manifests and lockfiles, the scripts and CI steps, the ranked repo map, the last commits, the unmerged branches with their last commit, the churn hotspots, the TODO and FIXME locations, and the docs, issues and agent transcripts it found; WHEN research is off THE SYSTEM SHALL record dependency age as *not checked: offline*, and WHEN no offline vulnerability database is present, known vulnerabilities as *not checked*.
- **DS-TO-6** WHEN a taken-over repository is trusted THE SYSTEM SHALL install its dependencies with lifecycle scripts off, then build it and run its test suite twice, confined and with no network, SHALL record each command with its exit code and each test's result, and SHALL record the two runs as the onboarding baseline that later cards' gates read ([gates](gates.md) GT-BF-2, [surface](surface.md) SUR-38).
- **DS-TO-7** WHEN the install or the build fails during a take-over THE SYSTEM SHALL record *could not build* with its reason as a finding, and SHALL continue with the remaining steps.
- **DS-TO-8** WHEN a fixture repository holding a stub that throws "not implemented", an `it.skip` and an `it.todo` test, a route with no handler, an import of a missing module and a schema with no migration is taken over THE SYSTEM SHALL report each as a half-done finding with its file and line.
- **DS-TO-9** WHEN the brief as found labels a claim *proven* THE SYSTEM SHALL cite an executed result — a test that passed in both baseline runs or a build that succeeded — and SHALL record that result's link to the claim as proposed, never confirmed; WHEN a claim cites no executed result THE SYSTEM SHALL NOT label it *proven*; WHEN no executed result bears on a claim THE SYSTEM SHALL label it *claimed, unproven*; WHEN an executed result or a finding contradicts it THE SYSTEM SHALL label it *contradicted*; and every claim SHALL cite at least one file:line, test id or commit.
- **DS-TO-10** WHEN repository text — README, docs, issues, comments, commit messages, agent transcripts or agent configuration — enters a prompt during a take-over THE SYSTEM SHALL wrap it as untrusted content ([security](security.md) item 42).
- **DS-TO-11** WHEN the take-over conversation starts THE SYSTEM SHALL post its questions together as at most five decision requests, ranked by how much each answer changes the plan, each with the `safe_default` policy and a default that cites a finding id, and SHALL ask none whose answers produce the same plan; WHEN the inventory holds at most one failing test or half-done finding and no contradicted claim THE SYSTEM SHALL post at most one; WHEN the person approves the take-over plan THE SYSTEM SHALL record `decision/default_applied` for every one of those requests still unanswered and plan on its default; WHEN the plan is not approved THE SYSTEM SHALL apply no default, whatever time has passed; and no question SHALL contain the words "requirements", "phase" or "let me gather".
- **DS-TO-12** WHEN the take-over backlog is proposed THE SYSTEM SHALL place each card in *stabilise*, *finish* or *defer*, SHALL link each card to at least one finding, test id, file:line or commit, SHALL propose for each *could not build* finding (DS-TO-7) a *stabilise* `fix` card whose red check is the build command failing on the base ([gates](gates.md) rule 6b), SHALL propose each secret to rotate as a task for a person (a decision request or a card assigned to a person) and never as a card for the Worker, SHALL plan a `characterize` card before any card whose scope files no test executes on the base, and SHALL propose no card that rewrites a part whose tests pass.
- **DS-TO-13** WHEN inherited issues exist on the connected tracker THE SYSTEM SHALL propose each as already done, duplicate, stale or valid, citing its evidence, and SHALL change no issue until a person applies the proposal ([integrations](integrations.md) NEW-integrations-4).
- **DS-TO-14** WHEN the person approves the take-over plan THE SYSTEM SHALL create its cards and seed the requirement graph with each proven claim as a requirement whose links to the baseline's tests are proposed and unconfirmed until a person records `trace/confirmed`, with its status computed by [planner-pm](planner-pm.md) §2.15.5 (*passing, strength unmet* until the tests' strength is measured), and each claimed-unproven claim as a candidate for the person to accept or cut (planner-pm §2.15); WHEN the plan is not approved THE SYSTEM SHALL have created nothing.
- **DS-TO-15** WHEN the take-over fixtures (a half-built TypeScript app with failing tests, a repository that does not build, a Python project with stubs, a repository with a committed fake secret, a repository with inherited issues) are taken over by a scripted non-developer conversation THE SYSTEM SHALL bring at least one card on each to accepted, with no shell command in the transcript and no fixture file edited by hand (DEFINITION_OF_DONE §6.4).
- **DS-TO-16** WHEN the board has no cards THE SYSTEM SHALL offer **Take over a project** beside **Start a project**, and pressing it SHALL open Seshat with the take-over conversation ([dashboard](dashboard.md) item 10).

### NEW-design-stage-9 — Research like an engineer, at the version the project pins
*An engineer reads the documentation of the version they run, and only the part that answers the question; an agent given another version's page or a whole page does worse (arXiv 2604.09515: 42.6% of code executable without docs, 66.4% with; CodeRAG-Bench arXiv 2406.14497: distracting retrieval hurts). The Worker's `docs` tool and the Researcher's `read_docs` read a library's documentation home with no version, and Crawl4AI never received the question (§4, `web.ts:288`). Owner's approval of 2026-10-05 (scope B with Go and Rust; [DEC-59](../DECISIONS.md)). DS-N9-1 to -7 are item 1 of the scope (the installed-dependency adapters and the pins), DS-N9-8 to -14 items 2 and 3 and the Researcher's wiring, DS-N9-15 to -18 items 5 and 7, DS-N9-19 to -22 item 6 (DEC-59), and item 4 runs through all of them. The fix round of the review (2026-10-05) amended DS-N9-7, -10, -12, -15, -16, -19 and -20 and added DS-N9-23 to -25.*

- **DS-N9-1** WHEN the Worker's `docs` or `dependencies` tool, the Researcher's `deps_*` tools, the research packet or a probe asks about a dependency THE SYSTEM SHALL resolve it through one adapter per ecosystem — npm, Python, Go, Rust (`packages/loop/src/ecosystems/`) — each giving the declared dependencies, the version in use (the installed copy's, else the lockfile's pin) with both versions when they differ, the source root, the files to read in reading order, the package's static declarations, the API surface for a symbol and what a probe runs and reads; a name may carry an ecosystem prefix (`python:requests`, `go:cobra`, `rust:serde`); without one the first ecosystem with an installed copy answers, else the first with a pin. Everything is local and offline.
- **DS-N9-2** WHEN a Python dependency is read THE SYSTEM SHALL read the project's virtual environment (`.venv`, `venv` or `env` with a `pyvenv.cfg`): each distribution's `.dist-info` (METADATA for its name, version and description, RECORD for the files it owns, `top_level.txt` for its import names), the API surface read statically, stubs (`.pyi`) before sources; only when static reading finds nothing and the distribution ships compiled modules SHALL it run the standard library's `inspect` on it, through the sandbox with no network and no worktree write. Nothing is installed; no new library is used.
- **DS-N9-3** WHEN a Go dependency is read THE SYSTEM SHALL take the version from go.mod's `require` line, checked against go.sum, and the source from the module cache (`GOMODCACHE`, else `GOPATH/pkg/mod`) at the escaped `path@version`; the API surface is a static scan of exported declarations, and WHEN `go` is installed `go doc` adds its text, run confined with `GOPROXY=off`, `GOFLAGS=-mod=mod`, `GOTOOLCHAIN=local` in a scratch copy of go.mod and go.sum. WHEN `go` is not installed THE SYSTEM SHALL read the source alone; a missing tool is reported, never installed.
- **DS-N9-4** WHEN a Rust dependency is read THE SYSTEM SHALL take the version from Cargo.lock and the source from `$CARGO_HOME/registry/src/<index>/<name>-<version>` (any index directory), compiling and fetching nothing; WHEN Cargo.lock holds more than one version of the crate THE SYSTEM SHALL take the one the project's own packages depend on (their `dependencies` entry `name version`), else the one Cargo.toml's requirement selects, else the highest; the API surface is a static scan of `pub` items, the members of its types, the names `pub use` brings in, and `#[macro_export]` macros, which are exported at the crate root.
- **DS-N9-5** WHEN the Worker calls `dependencies` THE SYSTEM SHALL list the declared dependencies of every ecosystem (package.json, pyproject.toml and requirements.txt, go.mod, Cargo.toml) with the version in use, and WHEN it calls `docs` its second tier SHALL read a dependency's own files at that version in any ecosystem — npm's README and type declarations, a Python distribution's METADATA, stubs and sources, a Go module's README and sources, a Rust crate's README and `src/` — caching each answer under the installed version, so a package installed after a lookup is read rather than answered from the earlier miss.
- **DS-N9-6** WHEN a file of a dependency is read THE SYSTEM SHALL read it only inside the package's root: a path with a `..` element, an absolute path, a path outside the elements the package owns, or one whose real path leaves the root is refused; a walk follows no symlinked directory, and a symlinked file only when its target is inside the root.
- **DS-N9-7** WHEN a version is pinned THE SYSTEM SHALL read it from one reader of the project's lockfiles (`pinsOf`: pnpm-lock.yaml, package-lock.json, requirements.txt `==` lines, poetry.lock, uv.lock, Cargo.lock, go.mod's `require` lines checked against go.sum), which the adapters, the research notes and the air-gap kit share; a lockfile that cannot be read pins nothing and a truncated one only its complete entries; a dependency's version in use SHALL be one version — where the pins hold several and none is installed, the one DS-N9-4 selects for Rust and the highest otherwise — while `pinnedVersion` may list them all.
- **DS-N9-8** WHEN documentation for a dependency the project pins is read from the web THE SYSTEM SHALL resolve it at the pinned version: Rust `https://docs.rs/{crate}/{ver}/{crate_}/` (its `all.html` maps a symbol to its page); Go `https://pkg.go.dev/{module}@{ver}`; Python the project's Documentation URL (the installed distribution's METADATA, else PyPI's) when it is on `*.readthedocs.io`, rewritten from `/en/latest/` or `/en/stable/` to `/en/{ver}/`, then `/en/v{ver}/`; npm `https://unpkg.com/{name}@{ver}/llms.txt`, then its `README.md`; a versioned `llms.txt` at the versioned root before the origin's. A page for another or an unknown version SHALL be read only when fewer pages at the pinned version were read than asked for, labelled `[docs for X; project pins Y]`, and ranked after every page at the pinned version.
- **DS-N9-9** WHEN the resolver fetches THE SYSTEM SHALL send every request through the research's polite fetcher — `fetch_deny`, robots.txt for page reads, the host's pacing, the cache, and with `research = "yes"` the research policy with each request a `harness/egress` event — and SHALL tag what it read as untrusted; WHEN research is off or offline THE SYSTEM SHALL send nothing. Documentation hosts are not research hosts (`RESEARCH_HOSTS` is unchanged).
- **DS-N9-10** WHEN a page is read for a question THE SYSTEM SHALL pass the question to Crawl4AI's BM25 filter and to the plain reader's own ranking, SHALL cache the raw page once under `crawl:<url>` whatever the question, and SHALL extract at most five excerpts per read of the documentation, across all its pages, of heading-sized chunks of at most 1,200 characters (a paragraph longer than that is cut at its line ends, and a line longer than that at 1,200 characters, so every chunk stays verbatim), each `{url, anchor, heading, text, sha256, pageSha256}` (the chunk's and the raw page's SHA-256), deterministically and with no model: the same page and question give the same excerpts and hashes.
- **DS-N9-11** WHEN the Researcher is asked a question THE SYSTEM SHALL find the project's dependencies it names — by name in any ecosystem, a Go module path or its last element included — append their versions to the question as the project's pins, and record them as `pins` (`eco:name@version`) in `research/asked`'s payload.
- **DS-N9-12** WHEN the Worker's `docs` tool reaches its web tier (`workerWebDocs`) or the Researcher calls `read_docs` for a dependency the project pins THE SYSTEM SHALL read through the pinned resolver (DS-N9-8 to -10); a library the project does not pin is read from its known documentation home (`KNOWN_DOCS`) as before. WHEN the Worker names a URL, or a library the project does not pin and that has no known documentation home, THE SYSTEM SHALL send nothing and answer from the local tiers: the Worker chooses which documentation is read, never where a request goes (worker-loop rule 10, the `docs` tool). The Researcher's `read_docs` may still read a URL it names.
- **DS-N9-13** WHEN the Researcher works THE SYSTEM SHALL offer a `probe` tool that runs a short program against the installed dependency (DS-N9-17) and SHALL refuse a probe past the effort's budget — quick 2, standard 4, exhaustive 6 per question — before it runs; a probe that exits 0 adds its executable claim, with the program that ran as its reproduction, to the answer's claims report.
- **DS-N9-14** WHEN the Researcher reads a dependency (`deps_source`, `deps_grep`) THE SYSTEM SHALL read it in any ecosystem through the adapters (DS-N9-1 to -6), at the version in use, confined to the package.
- **DS-N9-15** WHEN a plan creates cards THE SYSTEM SHALL flag, without a model, each qualified reference (`a.b`, `a.b(`, `a::b`, `a.b.c`) in a card's spec and criteria whose head is an installed dependency, or an import alias the repository binds to one (TS/JS import specifiers, Python `import x as y` and `from x import y`, Rust `use`, a Go import path by its last element), and whose member is absent from that dependency's API surface at the installed version — a package, namespace or module head against the package's exports and the names its files declare at the top level, a named import of a type against that type's members, each only when the surface lists them; and a backticked package name — scoped, a Go module path, or named a package, library, crate or dependency in its sentence — that is not installed. The package's declarations are the adapter's own static declarations (DS-N9-1; npm's through the source index, gates GT-T2-3), so a Rust `#[macro_export]` macro is a declared name. A bare identifier is never flagged, nor a member the surface cannot list, nor a backticked name the repository itself declares (a workspace package, a path at its root, or a top-level declaration of its own TS/JS source). The repository map is a guard only: a card's identifiers expected in the project's own code are not checked, because a card names the new identifiers it will create and telling those from a mistake needs a model (Not yet, §6 row). At most 4 flags per card, recorded as `research/packet` {card, flagged, answeredLocally, askedResearcher, reused}.
- **DS-N9-16** WHEN a reference is flagged THE SYSTEM SHALL first answer it locally: the same member declared elsewhere in the package, then the nearest exported names and members by edit distance, at most 3, each with its signature, cited `deps:<eco>:<pkg>@<ver>/<file>:<line>` with the file's SHA-256 (for a package that is not installed, its pin or the installed packages with near names). THE SYSTEM SHALL ask the Researcher only when that finds nothing, research is allowed, a Researcher is configured and the runner lease is free, in the same model load as the brief's deep question — a plan whose brief asks no deep question loads no Researcher for its packet, and the plan asks at most 8 packet questions in all, the rest answered locally with the reason — with a question holding only the flagged identifier and `pkg@ver` and no other spec text (the one spec-derived word that may leave the machine, DS-N9-23); the Researcher answers it with the dependency tools (`deps_source`, `deps_grep`, `probe`, its probe reading the dependency roots and nothing else of the repository, DS-N9-17) and the web, never the tools that read the project (`module_api`, `git_history`), and its answer is not written to research memory.
- **DS-N9-17** WHEN a probe runs THE SYSTEM SHALL refuse, before it runs, a program over 30 lines or 2,000 characters or in a language other than the package's ecosystem's (`node` for npm, `python` for Python), and SHALL run any other through the claim gate's runner (`runProbe`, gates rule 27a): a fresh scratch directory the only writable root and the working directory, the dependency roots (the adapter's `runtime().readRoots`) readable and never writable, no network, 10 seconds and 512 MB; the output the model sees is the last 1,000 characters, wrapped untrusted. For a research card's question the repository is readable too; for a research packet question THE SYSTEM SHALL make the repository unreadable except its dependency roots (the sandbox's `hiddenReads`, security item 8c), since that Researcher also holds the web.
- **DS-N9-18** WHEN a probe exits 0 THE SYSTEM SHALL make it an executable claim whose `reproduce.code` is the exact program that ran, so the claim gate re-runs it unchanged, with the repository a read-only grant; a Go or Rust statement runs nothing and is recorded documented, not reproduced, with the reason `no probe runner for <eco> in this version`.
- **DS-N9-19** WHEN a flag's answer is grounded THE SYSTEM SHALL admit it as a research note, `research/note_admitted` {noteId = `rn_` + the first 16 hex of SHA-256(eco|pkg|ver|symbol), symbol, ecosystem, package, version, citation {kind `local` with `deps:<eco>:<pkg>@<ver>/<file>:<line>` and fileSha256, `web` with `url#anchor`, the chunk's sha256, pageSha256 and fetchedAt, or `probe`}, check {kind `citation`, or `probe` with the program's SHA-256, its language and exit 0}, at, answeredBy `local` or `researcher` with the model}, with the question (templated from the symbol and `pkg@ver`), an excerpt of at most 600 characters and the repository's real path in the event's private part. A note is admitted only model-free: a local citation whose cited line holds the symbol's missing name verbatim and whose file hash matches; a web citation whose excerpt holds it, whose chunk is cut from the cached page's bytes, and whose page documents that exact version by its URL (DS-N9-24) — a page for `latest`, another or an unknown version, a changelog, an issue or a blog admits nothing; or a probe that exited 0 at that `pkg@ver` whose own code, the harness's prelude, comments and strings left out, names it, and for which the harness's own existence check (DS-N9-25) exits 0 in the same sandbox. A Researcher answer without one goes to the dossier as plain research and is never a note.
- **DS-N9-20** WHEN a later card's packet flags the same eco, package, version and symbol THE SYSTEM SHALL reuse the note, asking no Researcher, after re-checking its source's hash (the local file, or the cached page and its chunk); a mismatch retires the note (`source_changed`) and the flag is answered afresh. A note whose private part was erased (`ledger/erased`) SHALL be retired with reason `erased` the first time a packet meets it, naming it as a gap on replay; it is never fed, and the flag is answered afresh and may admit a new note under the same id.
- **DS-N9-21** WHEN a plan or packet reads the notes THE SYSTEM SHALL retire, with a recorded `research/note_retired` {noteId, reason, cardId?} and its detail in the private part, a note whose `pkg@ver` is no longer the installed or pinned version (`lockfile`), and a note a card it fed has since failed on: a failed `gate/result` after the `research/note_fed` whose excerpt names the symbol's missing name with TS2339, TS2305 or TS2724, Python `AttributeError`, `ImportError` or `ModuleNotFoundError`, Go `undefined:`, or Rust E0425, E0599 or E0432 (`card_failed`). A failure that does not name it retires nothing. A retired note is never fed.
- **DS-N9-22** WHEN a flag is answered THE SYSTEM SHALL record it on the card as one `card/research` dossier entry of at most 400 characters with its source, tagged untrusted where the Worker reads it; a note's entry is followed by `research/note_fed` {noteId, cardId}. Notes are cited research data, never rules ([DEC-59](../DECISIONS.md) (b)).
- **DS-N9-23** WHEN a research packet question is put to the Researcher THE SYSTEM SHALL hold in it only the flagged identifier or package name — letters, digits and `_ $ . : / @ -`, at most 120 characters, no space, never a phrase — the package and the version, templated (`researchCopy.packetQuestion`, `packetPackageQuestion`), so the Researcher's searches may carry that identifier and nothing else of the spec; a flag whose identifier does not have that form is answered locally only. *(The owner's approval of 2026-10-05, research scope item 5, which sends a flagged identifier to the Researcher in the planning swap: the one exception to S8's rule that only keywords or an admitted model's capability queries leave the machine. Security's NEW-security-11 lists it.)*
- **DS-N9-24** WHEN a web citation is checked for a note THE SYSTEM SHALL accept its page only when the page's URL documents the note's exact version: `docs.rs/{crate}/{ver}/…`, `pkg.go.dev/{module}@{ver}…`, a Read the Docs `/{lang}/{ver}/` or `/{lang}/v{ver}/` path, or `unpkg.com/{name}@{ver}/…`.
- **DS-N9-25** WHEN a probe is checked for a note THE SYSTEM SHALL run, in the packet's probe sandbox (DS-N9-17), a program the harness writes from the note's subject alone — load the package (Node's `load`, Python's `importlib.import_module` of its import name) and read each part of the symbol in turn, a type's member through its prototype — that exits 0 only when every part resolves; the Researcher's program and its exit code alone admit nothing.

- **Crawl4AI's link scoring and adaptive crawl** (within a documentation site, stopping when the gathered pages answer the question rather than at a fixed depth). Crawl4AI itself reads pages in v1 (§2.7 rule 2), and the question reaches its BM25 filter (DS-N9-10). v1 reads the pages its sub-questions name and stops on coverage of the sub-questions (§2.7 rule 3); an adaptive crawl is admitted when the golden set shows it closes sub-questions a plain fetch leaves open.

- **Taking over a project** (§2.10, [DEC-43](../DECISIONS.md#dec-43--take-over-a-project)). Cited conservatively: a number appears only where it was checked in the source's own abstract.
  - *Trust first.* Check Point's disclosure of CVE-2025-59536 in Claude Code: hooks and MCP servers defined in a repository's `.claude/settings.json` and `.mcp.json` could run as soon as the tool started, in one case before the person could read the trust dialog. A cloned repository's agent configuration is attacker-controlled input, so it stays inert until a person approves it.
  - *Commands and gotchas only.* "Evaluating AGENTS.md" (arXiv 2602.11988): context files, whether generated by a model or written by developers, did not generally improve task success and raised inference cost by over 20%, and repository overviews did not help. So an approved agent file contributes commands and gotchas to the playbook, not overviews; the same reason as [surface](surface.md) item 9a.
  - *"Could not build" is a finding.* EnvBench (arXiv 2503.14443): on repositories it selected as hard to configure, the best approach it measured configured 6.69% of the Python ones and 29.47% of the JVM ones. That is not the failure rate of an ordinary repository, but it shows setup failing often enough that a take-over must not stall on it.
  - *Ask, once, with defaults.* HumanEvalComm (arXiv 2406.00215) measures whether code models ask clarifying questions when a problem is inconsistent, ambiguous or incomplete, and finds they often generate code instead of asking. ClarifyGPT (FSE 2024, doi 10.1145/3660810) asks only when a requirement is judged ambiguous. Hence one batch, each question with a default, none asked when its answers produce the same plan.
  - *A ranked map, not the whole tree.* Aider's repository map — a graph-ranked summary of the definitions that matter, sized to a token budget — is the pattern [context](context.md)'s ranked repo map follows; recon reads it rather than every file.
  - *Plan, then approval.* Kiro's spec-driven flow (requirements, then design, then tasks, each reviewed before the next) and GitHub Copilot Workspace's editable specification and plan before any code is written: the category's convention is that a person approves the plan before implementation, which step 6 keeps.
