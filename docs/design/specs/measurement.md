# Measurement and self-improvement

## 1. Purpose

Every claim Sekhemet makes about quality is unfalsifiable until it is measured on a fixed task set with the models it actually runs. Measurement is the admission test for every change the harness makes to itself, the way a model is qualified, and the only way to tell a feature that helps from one that merely exists. It applies the spine's first rule to the harness itself: **a change is admitted by a signal measured outside the generated text, never by argument**.

## 2. Behaviour

### The frozen suite

1. The frozen suite is a fixed set of 20–40 tasks, versioned in `fixtures/suite.json` (today four fixtures — chronicle 6, onyx 8, vanguard 8, basalt-canvas 8 — thirty tasks), each with a specification, a repository state and gates that decide pass or fail without a person. A task may be added, which bumps the version; no task is ever edited to make a result look better.
2. The **suite hash** covers everything that defines a task: the manifest, the fixture trees, the card specifications and the seed scripts that create them. A result is comparable only with results of the same hash.
3. A run copies each fixture into a fresh git repository, seeds it once, and runs every card through the real product path (`sekhemet run`). A passing card is accepted (squash-merged) before the next card starts, as in a real project. A card whose contract needs a module an earlier failed card never delivered is recorded as **blocked on that dependency** — unmeasured, not failed — because running it measures nothing.
4. One number comes out: **tasks passed**, reported as a pass rate with an exact (Clopper–Pearson) 95% interval, alongside its cost — wall-clock, tokens and cards that needed a repair rung — and the count of blocked cards. **Every failure is attributed to a named cause** in `SUITE_RUNS.md`. A change that does not move the number, or moves it down, is not an improvement however well it is argued.
4a. **Every role's tokens are on the ledger.** A cost in tokens counts every model that worked, never the Coding model alone. A card's step records its own usage (`card/step`, [kernel.md](kernel.md)); every other model request that goes through the one path to a model ([models.md](models.md) rule 20a, `ModelAccess`) — Seshat's answers, its read-in-parts pass, summaries and quick answers, the Planning model's plans and re-plans, the Review model's reviews and vision checks, the Research model's questions, the Coding model's requests outside a step — is recorded as one `model/usage` event: whose request it was (`worker`, `seshat`, `planner`, `reviewer`, `researcher`), what it was for (the request's `task`, else the role's own work: `code`, `answer`, `plan`, `review`, `research`), the model id, and the prompt, cached, thinking and answer tokens and the time; never the prompt or the reply. A request the caller records as a step (`recordedAsCardStep`) is not recorded again, a failed request records nothing, and a measurement run's requests ([models.md](models.md) rule 20b: `measurementRun`, a benchmark) are not the project's work and are not recorded. Insights' model use and the capstone's Sekhemet arm total the two records (NEW-measurement-6).
5. **A run describes itself.** It records the harness commit and dirty flag, a SHA-256 of every built `dist` directory, every `SEKHEMET_*` variable, the Worker server's `/props` and build, the host fingerprint, the suite hash, and the thinking policy and working method. It re-hashes `dist` before each card and aborts if the build changed mid-run.
6. **Trials are independent.** During a measured run, learned state is isolated (its own configuration directory, model registry and exemplar store); no playbook rule or exemplar learned from one card in the run reaches a later card; and each card's evidence records the rules and exemplars it saw. This is the measurement half of one rule. In **production** use, whether a lesson verified by execution (a gate that failed and then passed with it applied) may reach later cards of the same run **on probation**, before a person approves it, is decided: no probation, approval first ([O15](../../reference/OPEN_QUESTIONS.md#owner-decisions), [DEC-33](../DECISIONS.md#dec-33)); until the owner decides, **probation is off**: nothing learned during a run is applied before a person approves it (the owner's rule of 2026-09-18), and a verified lesson becomes a candidate for approval with its evidence ([context.md](context.md) rule 24f). Probation's criteria are MS-T8-15 here (T8) and [context.md](context.md) CX-N4-7 (NEW-context-4). In a **measurement run** — the frozen suite, a bake-off, the planning measure — no rule learned during the run is applied whatever O15 decides, so the run measures the harness, not what it learned from the test itself.
6a. **Only the Worker's work is measured as the Worker's.** An attempt a person built ([kernel.md](kernel.md) rule 22) never counts in a pass rate, a comparison, an inlet signal or the competence model; the frozen suite's comparison with live use would otherwise lose its meaning.
7. **The model stays resident** across the cards of a run; model load time is reported separately and never counted in a card's wall-clock.
8. **Reference solutions.** Each fixture card has a reference solution, validated against the frozen tests and hashed into the suite. A card can then run alone on a `main` holding its predecessors' reference work, which makes every card an independent, re-runnable trial. The "build the whole project" run, where each card builds on the Worker's own earlier cards, stays as a separate measure.
9. **One measurement path.** The suite runner lives in `packages/eval` as a tested module, and the bake-off, the rule gate, `m0` and every benchmark call it; each goes through the same card execution the product ships — same prompt, tools, thinking policy, working method, context window and tool arm, and the same roles and policies switched on (exploration, the Reviewer, the Researcher, escalated retries, the step cap) as the product ships them, so the benchmark measures what ships, not a harness with most features off. Any wrapper around a model adapter forwards every property, not only `generate`, and meters cached prompt tokens.

    **The suite measures the queue path** (the lead's ruling in B2.4). The product runs cards through `sekhemet queue`; `sekhemet run` is the Worker alone, without the queue's planning prelude, dependency deferral, learned rules, team note or manager. So the suite, the bake-off, the rule gate and `m0` all run cards through the queue with its **shipped defaults** — whatever `queue` does without experiment flags — and `--auto-accept` stands in for the person who accepts each card, so later cards build on earlier ones. *Confirmed under [DEC-42](../DECISIONS.md#dec-42--the-owner-delegates-the-outstanding-decisions-to-the-lead):* `--auto-accept` is bounded to measured runs — the queue refuses it unless the repository carries `.sekhemet/measurement.json`, which only the suite runner's fixture copies, M0's workspaces and the combination benchmark's card repositories are given (each marked with its own purpose: `frozen suite`, `m0`, `benchmark`), and each attempt's reproducibility record names it; it is not in the command line's help, and in a person's repository a person accepts each card (review M5, the human is the rate limiter). An arm is named only through the `RunProfile` (a settings file, the experiment switches), which the runner hands to the queue as one flag per setting; `--profile full` is an experiment arm, not a default, and a measured run refuses it. On this 24 GB host the shipped defaults run the Worker alone: the queue loads a second model only when a Planner is configured (`[models] planner`, used for repair plans, retries and the end-of-run reflection, swapped with the Worker, never co-resident with it: no two large models, [models.md](models.md) rule 22), when `SEKHEMET_RESEARCHER` names a Researcher (used only in a manager batch), or when a person writes to the PM during the run (the Worker is swapped out to answer). No configuration on this host names either; the residency scheduler is NEW-models-9's.

9a. **A run's settings are one recorded object.** Every run resolves its settings once — configuration, then flags — into one `RunProfile` (roles present, policies on, model roster, budgets, switches, and Smart Swap's policy version and parameters, `SwapPolicyParams`: [models.md](models.md) rule 20e, [DEC-45](../DECISIONS.md#dec-45--smart-swap)) that is written into the run's evidence. A named settings file (`--settings <file>`) is allowed, because the file itself is recorded; a flag that silently changes other flags (a `--profile benchmark` that turns on four others) is not ([surface.md](surface.md)).

### Statistics fit for 14–30 tasks

10. **Comparisons are paired.** Two settings are compared on the same cards, interleaved (A, B, A, B) with fixed seeds, and decided by an exact McNemar test on the cards where they disagree, or a Bayesian beta-binomial comparison; a sequential test (SPRT or a confidence sequence) may stop early. Runs are repeated; results report pass@k and pass^k. Adopting a new model for a role is such a comparison — a bake-off on the frozen suite on that host, the incumbent against the candidate ([models.md](models.md) rule 30a).
11. **Only large effects are claimed.** With 25–30 tasks a paired test has about 6–7% power to see a 10-point gain; about 155 paired tasks are needed at 20% disagreement (≈76 at 10%, ≈233 at 30%). So the 30-card suite claims only effects of **at least 20 points**, and every comparison states the smallest difference it could have detected. One trial at non-zero temperature is never a finding.
12. **When arms cannot be separated**, the default is the arm with the lower seconds per card, and the record says the pass rates were indistinguishable. This is how the thinking A/B (`off`, `surgical`, `all`, then the top two again) and the M2, M7/M11 and exemplar A/Bs are decided. It chooses among the arms of a setting that must take one value **before the baseline `RunProfile` is frozen** (B2.5), and it decides **every** such setting: the thinking policy, the working method (`baseline` or `strict`, [worker-loop.md](worker-loop.md) rule 26), the tool arm (M2), and the M7/M11 and exemplar arms. The **evidence-gated commit** ([worker-loop.md](worker-loop.md) rule 29a, ECLoop), also run inside B2.5, is not one of them: it is a new mechanism, not a choice among existing arms, so rule 12's faster-arm default never decides it — it is admitted by rule 16c against B2.5's other winning settings, and when the A/B is inconclusive it **stays off**, its default, unless rule 16c's cheaper ground is shown (its simpler ground cannot apply, since the arm adds a switch). Once the baseline exists, a change against it is a harness change and is admitted only by rule 16c, whose cost measure is named before the run (final check F10).
13. Only uncertain cards are re-run when narrowing an interval (SIFT-style slicing), and the re-runs are paired.

### The planning measure

14. The frozen suite ships hand-written cards, so it measures the Worker, the gates and the loop — never the Planner. The planning measure sits beside it and is never merged into it:
    - **Card validity.** Each fixture's specification is planned from scratch. Each generated card is scored on SPIDR shape, a declared scope of 1–3 files and at most 200 changed lines, and an acceptance test that fails at the seed, passes on the reference solution and kills mutants of the reference (fail-at-seed alone proves nothing, because `src/` ships empty). Beside these, each card reports the test-strength figures of [gates.md](gates.md) rule 32a: red at an assertion against the interface stub, stub-kill, the acceptance-test mutation score and the oracle cross-check disagreement rate.
    - **End to end.** The Worker builds from the Planner's cards, and the score is the share of the **hand-written, held-out** acceptance tests that pass on the final `main`.
    - **The first mutation threshold comes from here.** A project's first blocking acceptance-test mutation threshold is derived from at least one planning-measure run's per-card "mutants killed" and entered in the register with its date before any project uses it (rule 26).
15. Public project-building benchmarks that run locally (Commit0 lite, 16 libraries; ProjDevBench, 20 problems) are candidates for an external planning measure — *proposed*.

### Null baselines

16. A learned component is compared with the cheapest thing that could work, at equal budget, before it ships. The context pruner is measured against structure-preserving random line dropping at the same token budget; if it does not clear that baseline on the suite it is deleted with its register row.

### Admission: one rule for what the system learns

This section owns the rule ([DEC-28](../DECISIONS.md#dec-28--one-rule-for-admitting-what-the-system-learns)); [context.md](context.md), [planner-pm.md](planner-pm.md), [extensibility.md](extensibility.md), [worker-loop.md](worker-loop.md) and PM_CONTRACT point here and restate nothing.

16a. **The admission table.** What is learned is admitted, kept and retired by the rule for its kind, and **no admission rule relies on an effect the measurement cannot resolve**:

    | What is learned | Admitted by | Kept or retired by |
    | --- | --- | --- |
    | A **project playbook rule** (this repository's paths, kinds, error codes) | A person's approval | Paired credit on this project's own attempt records, with rotation (rule 16b). Tested only at fixed looks — after 20, 40 and 80 pairs — and retired automatically when a one-sided exact test on the discordant pairs shows harm at 0.05/3 at a look; never retired below 20 pairs. A person may retire a rule at any time |
    | An **execution-verified lesson** during a run | **Pending the owner ([O15](../../reference/OPEN_QUESTIONS.md#owner-decisions)).** Default until decided: nothing learned is applied before a person approves it. If the owner allows probation: production only, never in a measurement run (rule 6) | At the run's end, a candidate for a person's approval with its evidence |
    | A **harness change** (prompt, tool, budget policy, harness skill, context version) | A paired frozen-suite A/B that shows a gain at the suite's resolution (at least 20 points on 30 cards, one-sided exact test at 0.05; rule 16c) | **Inconclusive** (the usual case): adopted only if it is **simpler** — deterministically: it removes prompt tokens from the stable zone, a tool, a switch or code, and adds none — or **cheaper** on the one cost measure named before the run (median tokens per card), shown by a one-sided paired Wilcoxon signed-rank test at 0.05; and the paired pass-rate result is not a loss the suite can resolve. Recorded as "not established"; watched, and rolled back on the first paired loss a later run resolves |
    | A **scheduling parameter or policy** — Smart Swap's `SwapPolicyParams` and its D values, the policy itself, a load mode ([models.md](models.md) rules 20d–20j, [DEC-45](../DECISIONS.md#dec-45--smart-swap)) | A **paired closed-loop replay** ([models.md](models.md) rule 20j) of the change against the current parameters across **k ≥ 5 distinct recorded days**, on **one metric and direction registered before the run** (for example p90 interactive wait, or accepted cards per hour), paired by day and seed: a one-sided exact sign test on the per-day differences at 0.05, where a tie (a day with no difference) counts as not improved — with five days, every day must improve — **plus proof that the cards' outputs are unchanged**: the change alters only when requests are served, never what is sent — the same card from the same `RunProfile` sends a byte-identical first request with and without it (MS-M9-1's check), and it touches no sampling, context, prompt or qualified combination (rule 16d). A byte-identical first request is not enough for **restoring a card's live KV slot mid-attempt** ([models.md](models.md) rule 20i): a change that does so counts as able to change output until an equivalence check passes on a calibration night — the same request continued from the restored slot and from a full re-prefill produces identical tokens at temperature 0 with a fixed seed | Watched on real nights: the realised θ and waits per class are compared with the replay's prediction, and the change is rolled back when a paired replay over the next k ≥ 5 recorded days resolves a loss on the registered metric. A change that alters a request's content is a harness change (the row above), never this row |

    The frozen suite never admits a project rule: its fixtures cannot exercise a rule scoped to one repository's paths and error codes, so a suite score would measure nothing about it. The **context version** a harness change moves covers the harness only — prompt templates, the copy module, the tool catalog and its descriptions, budget policies ([context.md](context.md) rule 27); a project's approved rules and skills are project data, listed on each pack but outside the context version, so approving or retiring one never invalidates a model's qualification and never needs a suite A/B ([DEC-28](../DECISIONS.md#dec-28--one-rule-for-admitting-what-the-system-learns)). The six inlets of rule 17 map onto the table: playbook rules are the first row; exemplar and skill *mechanisms*, prompts, tools and budget *policies* are harness changes; an individual exemplar enters by its inlet's volume threshold and structural filter (rules 20, MS-T8-6) and never within a measurement run; budgets and routes recalibrated inside an admitted policy are measurements, bounded by rule 17's ≤ 15% and rule 20's volume threshold; synthesised tasks are measurement instruments, admitted by revert-and-fail; generated tests stay advisory until a person promotes them. A skill a person installs into their own project is their configuration, like a hand-written `playbook.toml` rule: approved by them once its own checks pass ([extensibility.md](extensibility.md) item 17a), never a harness change.
16b. **Rotation and paired credit** — the statistic for the first two rows:
    - **Comparable cards** are cards of the same project and the same card class (`kind:ext`, [models.md](models.md) rule 31) whose scope the rule matches on every declared condition ([context.md](context.md) rule 24b).
    - **Rotation.** Among the comparable cards a rule matches, in the order they start, the rule is in the prompt of one and withheld from the next, alternately; each attempt record lists the rules its prompt held ([worker-loop.md](worker-loop.md) rule 39), so "with" and "without" are read from the ledger, never inferred.
    - **A pair** is two consecutive comparable cards, one with the rule and one without. Only **first attempts** count — never a retry or an escalated pass — and person-built attempts never do (rule 6a). A pair's outcome is whether each first attempt passed its gates (stop reason `gate_passed`).
    - **Credit** is the number of *helpful* pairs (with it passed, without it failed) minus the number of *harmful* pairs (the reverse), counted over every pair since the rule came into force; pairs where both passed or both failed count for nothing. These are the rule's helpful and harmful counts; nothing else increments them. The credit is reported as it accrues, for the person and the diagnostics (rule 24); it retires nothing on its own.
    - **Fixed looks.** A rule is tested only when its pair count first reaches **20, 40 and 80**. At a look, with *n* discordant pairs of which *h* are harmful, a one-sided exact binomial test (a sign test, p = ½) of "no harm" is rejected when P(X ≥ *h*) ≤ **0.05/3** — the three looks share a 0.05 error rate (Bonferroni). Below 20 pairs the rule reports "insufficient data" and is never retired automatically; between looks, and after the look at 80, nothing is tested.
    - **Retirement.** When a look rejects "no harm" the rule is retired automatically, with its pairs and the test as the evidence, recorded as a `learn/rule` event with status retired. A person may retire a rule at any time. A retired rule returns only by a person's approval, starting a fresh count.
    - *Why fixed looks.* The earlier statistic — retire when the credit over a rolling last 10 pairs is below zero — retired a rule that lifts a class from 70% to 80% about 22% of the time at each evaluation, and evaluated after every pair, so a helpful rule was very likely retired within a few dozen pairs (confirmation review N3). Under the fixed looks (exact computation, pairs independent): a rule that lifts 70% to 80% is retired with probability about 0.001 over all three looks; a rule with no effect at 70%, about 0.02; a rule that lowers 80% to 70% is caught with probability about 0.23 by the look at 80, and one that lowers 80% to 60%, about 0.70. The looks catch rules that clearly hurt and keep rules that help; a small harm is left to a person, who sees the credit.
    - **Probation**, if the owner allows it ([O15](../../reference/OPEN_QUESTIONS.md#owner-decisions); off until then), uses the same rotation within one production run, with no minimum: a lesson is withdrawn as soon as its credit over the pairs completed in the run is below zero — a one-run safeguard, not an admission test — and one still on probation at the run's end goes to a person for approval with its pairs. With probation off, a verified lesson is recorded as a candidate at once and applies to no card before a person approves it.
16c. **Harness changes.** The A/B is paired and interleaved on the frozen suite (rules 10, 13, MS-T7-4), at least two paired runs per arm (rule 19), against the recorded baseline `RunProfile` (rule 9a). **Admitted** when a one-sided exact test rejects "no gain" at 0.05 with a difference of at least 20 points (rule 11). **Inconclusive** — neither a resolvable gain nor a resolvable loss — the change may still be adopted on one of two grounds, and only if the paired pass-rate result is not a loss the suite can resolve (a one-sided exact test does not reject "no loss" at 0.05):
    - **Simpler**, decided deterministically from the change itself, never by judgement: it removes at least one of — prompt tokens from the stable zone (Zones 1–2, counted with the Worker's tokenizer), a tool, a switch, lines of code — and adds none of them.
    - **Cheaper**, on **one** cost measure written into the A/B's record **before the run**: median tokens per card. The saving is shown by a one-sided paired Wilcoxon signed-rank test at 0.05 over the cards run in both arms; a lower median without the test is not "cheaper", and no second measure may be substituted after the run.

    `SUITE_RUNS.md` records the verdict as "not established — simpler" or "not established — cheaper", with the context version or harness commit it admits and **the smallest paired loss the run could have detected** at 80% power (as MS-M12-2 does for gains), so no one reads "not established" as "harmless". Otherwise the change is not adopted. An adopted change is watched and rolled back on the first paired loss a later run resolves (rule 18). The suite cannot see losses under about 20 points (rule 11); that is why the inconclusive case needs an independent reason — less to maintain, or a measured saving — and never admits a change on the absence of a loss alone ([DEC-28](../DECISIONS.md#dec-28--one-rule-for-admitting-what-the-system-learns), confirmation review N2).

    **The footprint, as computed** (the lead's ruling in B2.4). `sekhemet measure footprint` records one file per build, stamped with its commit and dirty flag; an admission compares two recorded files and never checks anything out. Its four counts: **stable-zone tokens** — the system prompt, static prefix and tool schemas of one fixed card's first Worker prompt, counted with the allocator's estimator and recorded as `estimated` until the Worker's tokenizer is available through [context.md](context.md) CX-N1-2's fallback rule; **tools** — the tool catalog's size; **switches** — the experiment switches (`SEKHEMET_THINKING`, `SEKHEMET_WORKER_METHOD`, `SEKHEMET_PRUNE`, `SEKHEMET_EVIDENCE_GATE`) plus the `RunProfile`'s flags (rule 9a); **lines of code** — non-blank lines of non-test TypeScript under `packages/*/src` and `apps/*/src`. `sekhemet measure admit` refuses a footprint without its commit.
16d. **Smart Swap: admission, calibration nights and placement** ([models.md](models.md) rules 20d–20k, NEW-models-14; [DEC-45](../DECISIONS.md#dec-45--smart-swap)).
    - **Admission** is the scheduling row of rule 16a. The replay runs the real `decide()` under a virtual clock on recorded days; "distinct days" means k ≥ 5 calendar days of recorded demand, never one day replayed with k seeds. The registered metric, its direction and the days are written into the A/B's record before the replay, as rule 16c's cost measure is. The proof that outputs are unchanged is part of the verdict, not a separate review.
    - **The calibration protocol.** [DEC-42](../DECISIONS.md#dec-42--the-owner-delegates-the-outstanding-decisions-to-the-lead)'s "unloaded after each run" **holds for measurement runs** — the frozen suite, a bake-off, an A/B, qualification — so each starts from a declared state. **Calibration nights**, when the owner permits model loads (DEC-42's host checks: swap under 4 GB and at least 60% of memory free, before each load), **run the policy as designed**: models stay resident, swap and prefetch as `decide()` chooses, and every load, unload and first token is recorded ([models.md](models.md) MD-N14-1–2). Before its first load a calibration night declares its protocol in one `measure/calibration` event: the policy version and parameters, the models, volumes and load modes it will try, the order of the load-mode A/B (at least three loads per mode), the probes it runs, and whether it runs the slot-restore equivalence check (rule 16a's scheduling row). It never runs during a suite or measurement run, and it unloads everything at its end. Every D value and each volume's load mode is then derived from the recorded loads and changed only through rule 16a's scheduling row. The first night loads are permitted, the baseline runs' loads (cold, one per run) feed the same distributions.
    - **The placement measurement.** A copy's gain is measured, not assumed: the same weights' cold loads are recorded per volume and load mode, and the gain is the median external load less the median internal one, each over at least three loads (MD-N14-4's minimum), shown as *measured*. Before three exist, the gain is predicted from the volumes' probed read rates and shown as an estimate. On the reference host, 2026-09-26: the USB drive read the Worker's 13.6 GB sequentially in 130 s (105 MB/s) against about 300 s for llama-server's mmap load from it, and the internal SSD read about 3.4 GB/s; so a load from internal storage is expected to be dominated by server start-up and Metal buffer setup, measured on the first permitted load.

### Self-improvement: one mechanism, six inlets

17. An objective signal becomes a bounded proposal; every proposal, whatever produced it, is admitted by the rule for its kind in the admission table (rule 16a) — a harness change by the frozen suite, a project rule by a person and then its paired credit — pinned by hash or commit when it takes effect, and watched afterwards. What varies between inlets is what they propose; how a proposal earns its place does not vary.

    | Inlet | Recorded signal | Proposes | Bound |
    | --- | --- | --- | --- |
    | Playbook rules | Repeated gate failures; send-back reasons | Add or retire a rule | One rule per retrospective |
    | Budgets and routes | Pass rate by card class, size, model, arm, steps | Adjust a class budget or a route | ≤ 15% per calibration cycle |
    | Skills | Recurring multi-step trajectories that passed | Package one as a skill with its own checks | One skill per proposal |
    | Exemplars | Accepted cards correlated with later pass rates | Index the top trajectories per class | Two per class |
    | Synthesised tasks | Fix commits and closed issues in this repository (C₋₁ fails, C₀ passes; paths scrubbed from the problem statement; dependencies installed in an ephemeral worktree per task) | A fail-to-pass regression task | Discarded if reverting the fix does not fail |
    | Generated tests | Mutants surviving the mutation gate | A test that kills the mutant | Advisory until a person promotes it; demoted to advisory again when the change it guards is rolled back |

    A seventh inlet must justify itself by the size of the signal it reads, not by the paper it comes from. Offline policy tuning (`sekhemet tune`: replaying recorded trajectories to choose when to stop an attempt; conservative, since a replayed policy can only stop earlier) feeds the budgets-and-routes inlet and proposes, never applies; a fresh repository with no history of its own starts from the machine's global tuning report, as a proposal through the same inlet. Every signal an inlet reads is tagged with its **source** (a gate transition, an attempt record, a person's action including an edit, a model's synthesis) and **how it was verified** (executed, approved by a person, or unverified); an unverified model synthesis never admits anything on its own.
18. **Guardrails.** (1) Every change is triggered by an objective, recorded signal; self-assessment is rejected. (2) Each inlet's bound holds; whole-system rewrites are blocked. (3) Every change is versioned or hash-pinned and rolled back automatically if the pass rate drops, compared **paired** — the same kind of cards with and without the change — never against whatever different cards ran before. (4) **Admission is grounded, never textual:** nothing durable is admitted unless a quantity measured outside the generated text strictly improves. For skills and generated tests the grounded signal is execution: a skill's own checks run in the gate host's sandbox as gates before the suite is even consulted.

    **Who rolls back** (the lead's ruling in B2.4). Rule 18 governs: an admitted change is rolled back only when a later **paired** suite run resolves a loss (MS-T8-3). The live window over the last ten cards (`LearningGuard`, E17) compared a change's pass rate against whatever different cards ran before and assumed 1.0 on an empty history, which (3) forbids; it is kept as an **advisory signal only** — it reports a drop as `flagged` (a `learning/flagged` event naming the change), never rolls back or retires anything, and reports "insufficient data" instead of a verdict when there is no history (`guardrails.ts`, `execute.ts`, `wave2.ts` `observeOutcome`).
19. **A harness change's admission needs a significant gain:** a one-sided exact test (or an interval excluding zero) over at least two paired runs on the suite path, with the suite hash checked. A delta of zero is not a gain. The one exception is rule 16c's inconclusive case — simpler by the diff, or cheaper by a paired Wilcoxon test on median tokens per card, with no loss the suite resolves — which is recorded as "not established", never as a gain.
20. **Volume thresholds.** Below its minimum an inlet reports "insufficient data" instead of acting:

    | Inlet | Minimum before it may act |
    | --- | --- |
    | Playbook rules | 3 occurrences of the same signal |
    | Budgets and routes | `MIN_ARM_TRIALS` (5) per arm, with a Wilson interval that excludes the incumbent |
    | Skills | 3 instances of the trajectory, and its checks pass |
    | Exemplars | 5 accepted cards in the class, each structurally complete |
    | Synthesised tasks | None; each is validated by revert-and-fail |
    | Generated tests | None; advisory until promoted |

21. **A cheap pre-filter must be calibrated.** A fast surrogate score used to discard proposals before the full suite is calibrated against an anchor set scored both ways, with a monotone (isotonic) map, and is used only once the anchor set holds `MIN_ARM_TRIALS` pairs.
22. **What public data may seed.** Difficulty may be initialised from the SWE-bench Verified human annotations (1,699 instances, three annotators each), to calibrate the 1–10 scale only, never to rank TypeScript cards (the labels are Python time-to-fix estimates, 46% of them one repository). The pre-filter's calibration *form* may start from public (surrogate, ground-truth) pairs. Public outcome matrices may enter only as derived pass/fail booleans, never patch text. **Exemplars, playbook rules and routing are local-only by construction**: public trajectories carry another harness's tool vocabulary, review corpora have no join key to this harness's gates, and public data has no tool-arm dimension. Nothing is imported without the owner's yes.
23. **Excluded from v1:** weight updates (fine-tuning, RL) of any model. **Permanently excluded from self-modification:** the loop driver, the gate runner, sandbox boundaries and permission tables.
24. **Diagnostics** (`sekhemet doctor`'s playbook check and `qualify`) measure each skill and rule against a bare baseline on the suite: net pass-rate gain, token overhead in Zone 2 (a rule or skill adding more than 300 tokens to Zone 2 is flagged as **context debt** when its admission record shows no gain: for a rule, a paired credit (rule 16b) of zero or less once it has 20 pairs, or fewer than 20 pairs after 40 comparable cards; for a skill, a suite A/B recorded "not established" — a "significant gain of at least 3 points" was the earlier test, which the 30-card suite cannot detect), and conflicting, redundant or obsolete rules, each offered for retirement in one action. The diagnostics read the real outcomes, skills and rules — including rules on the ledger — not an empty input.
25. **Mutation as a measure.** A mutation campaign (the generated-tests inlet, `improve --mutants`) first runs the tests on the unmutated checkout and refuses to score if they fail; a change with no mutable lines scores "not applicable"; a language the campaign cannot mutate is reported, never silently skipped.

### The research register

26. Every candidate technique moves through `spotted → triaged → shortlisted → benched → adopted | rejected`, never skipping a state on the way to adopted (rejection is allowed from any state). From `shortlisted` on it carries an **adoption threshold and the date it was set**, and that date is on or before its last move, so the bar is fixed before the bench. `benched`, `adopted` and `rejected` entries carry evidence. `sekhemet register advance <id> <state> --evidence …` refuses an illegal move; `sekhemet register check` and its test fail the build when an entry breaks a rule. Entries adopted before the register existed say so and still owe a bench run against their threshold. **At most two techniques are adopted per phase** of the modernization plan: with only 20-point effects detectable on the suite, adopting more at once makes their effects impossible to tell apart (NEW-measurement-3). A **phase**, for this count, is one of the plan's workstream groups **B2, B3 and B4** (and each later phase the plan names); Phase A and Phase C each count as one (confirmation review N8).

### Comparing model combinations: the quick and overnight benchmarks (NEW-measurement-5)

30. **What it is for.** On the Configuration page ([dashboard.md](dashboard.md) NEW-dashboard-6) a person chooses a **combination** — one model per role: Worker, Planner, Reviewer, Researcher — from the models they have, up to the strongest their hardware can run ([models.md](models.md) NEW-models-12 owns the scan, the fit and the recommendation). Two tiers tell them how effective a combination is, so they can mix and match: the **quick** tier (rules 31–36) answers **in minutes, not hours**; the **overnight** tier (rule 37) settles, unattended, what the quick tier could not tell apart, and is the full-suite confirmation the quick tier offers. Both serve a person's choice: a person may assign any model that has passed [models.md](models.md) rule 27a's qualification on this host, on the strength of either, or of neither (rule 30a there), and a winning combination is applied only by a person's choice, never by the harness. Neither admits a harness change under DEC-28 (rule 16a) or qualifies a model ([models.md](models.md) owns qualification); only a recorded bake-off — which the overnight tier runs — may change the recorded baseline `RunProfile` or a shipped default ([models.md](models.md) rule 30a).
30a. **Readiness by role.** The Worker and Planner screens, the end-to-end check and the Configuration page arrive in **B4.1**. The Reviewer's screen and the overnight tier's Reviewer set arrive with **B4.8**, which rebuilds the Reviewer procedure they exercise and builds the seeded defects; the Researcher's screen and the overnight tier's Researcher set arrive with **B4.4**, which builds the research pipeline and its golden set. Until its workstream lands, a role's score reads **`not_measured`** — never a score on a partial set (MS-T11-7) — and a comparison leaves that role out and says so (final check F7).
31. **Role by role, never combination by combination.** Each role has a small, fixed, versioned **screening set** (rule 29), run once per candidate model:
    - **Worker:** **6** frozen-suite cards across kinds, chosen from those a capable model finishes in under two minutes, each from its reference `main` (rule 8), each capped at **2 minutes**. A card's score is the **fraction of its acceptance tests passing** when it finishes or hits the cap — a graded value from 0 to 1, so a card that gets most of the way reads differently from one that gets nowhere. A card stopped by the cap is `time_budget_exhausted` and scored on the tests passing at that moment, and the result says how many cards hit the cap, so a slow model reads as slow, not as wrong;
    - **Planner:** **3** golden briefs, each scored by its **recall** — the share of its annotated requirements the plan covers (the implicit-requirement recall of MS-T7-7);
    - **Reviewer:** **10** seeded defects, each scored **1 if detected** at its location and 0 if not; false findings per diff are reported beside;
    - **Researcher:** **5** golden questions, answered over a cached offline corpus pinned by hash, each graded **0, ½ or 1** against its sourced answer (wrong or unsourced, partly right, right and sourced); nothing leaves the machine.

    A role's score is the mean of its items' scores, and the items' own scores are kept, because comparisons are made item by item (rule 35). **Secondary measures** are shown beside the score, per role where they apply: seconds per card (or per item), the valid tool-call rate, steps to pass, and whether the model fits (rule 34). A combination's score is assembled from its roles' scores, never measured as a whole. Beside it, **one short end-to-end check** of the chosen combination runs **2 cards**, each capped at **3 minutes**, through its Planner, Worker and Reviewer, so an interaction between roles (a plan the Worker cannot follow, a Reviewer that rejects every diff) is caught; its outcome is shown per card and is never folded into a role's score.
32. **A time budget stated before it runs.** Before anything is loaded, the page shows an **estimate** in minutes per role and per model, including load time, from the recorded throughput of that model on this host (the registry's figures when none is recorded). The targets, **each including load**: the Worker's screen at most about **17 minutes** (6 cards × 2 minutes, plus up to 5 minutes to load, as from the reference machine's USB drive); the Planner's, the Reviewer's and the Researcher's at most about **5 minutes** each; the end-to-end check at most about **10 minutes** with its swaps (2 cards × 3 minutes, plus the role switches). A full combination with nothing cached therefore comes in **under about 45 minutes** (17 + 3 × 5 + 10 = 42). An estimate over any of these targets is marked as such before the person confirms. A person may **stop it at any time** and keep the partial results: every completed role's score is cached, and the screen is recorded as partial.
33. **Scores are cached and reused.** A role's score is cached under the key (model, quantisation, engine, settings, host, harness context version) and the screening set's hash (rule 29), so trying a new combination re-runs only the roles whose model changed, plus the end-to-end check. The context version covers the harness only ([context.md](context.md) rule 27), so approving a project rule does not invalidate a cached score; a harness change does.
34. **Hardware-aware candidates.** Only models that fit the machine are offered to run, from the scan and qualification ([models.md](models.md) NEW-models-12, rule 11). A model that does not fit is **shown as "needs N GB"**, not hidden, and is never loaded. A combination whose models cannot co-reside shows its **swap cost in time** (seconds per role switch, from the residency plan in [models.md](models.md)), and the end-to-end check runs with that swapping, so its time is the time the person would see.
35. **Honest about small samples; compared paired.** Two candidates for a role are compared **on the same items**, by an exact two-sided **sign test** on the per-item differences (items where they score the same are set aside), as rule 10 requires; they are **"indistinguishable on the quick benchmark"** when that test does not reject at 0.05, and are then never ranked as if different. Two combinations are ranked only on the roles in which their models differ and the test resolves. The resolution is small, and the page says so:
    - **Worker, 6 cards:** the test separates two models only when one scores higher on **all six** cards (p = 2/64 ≈ 0.031); five of six with one tie, or five to one, does not (p ≈ 0.063 and ≈ 0.22). Graded scores make ties rarer than pass/fail would, so a large difference in correctness can show; a small one cannot.
    - **Reviewer, 10 defects:** resolved when, for example, one detects at least 6 defects the other misses and the other none it misses (p ≈ 0.031).
    - **Planner, 3 briefs, and Researcher, 5 questions:** never resolved on correctness at 0.05 (the most extreme outcomes give p = 0.25 and ≈ 0.063); these roles are told apart on the quick tier only by the secondary measures.

    So the page says, in its copy: **the quick tier resolves speed, fit and large differences in correctness; the overnight tier resolves close calls.** The secondary measures (rule 31) are shown beside every score, and where the scores are indistinguishable the page says what the overnight tier would add, and offers to schedule it.
36. **Results are recorded.** Each screen writes one recorded `RunProfile` (rule 9a) and its scores, intervals, cache keys and screening-set hashes to the ledger as one `measure/benchmarked` event with `tier: "quick"`, so the Configuration page can show the history of what was tried, and [models.md](models.md)'s recommendation per role reads the scores from there.
37. **The overnight tier** — a longer, more thorough comparison that runs unattended in the machine's overnight window, the complement of `[machine] reserved_hours`, optionally narrowed by `[machine] overnight_hours` ([models.md](models.md) rule 20b owns the scheduling):
    - **What it runs:** for each combination a person picks — by default the top combinations the quick tier could not separate, **up to 3** — the full frozen suite end to end with that combination's Worker, the planning measure (rule 14) with its Planner, and the Reviewer's and the Researcher's full evaluation sets (rule 29: the seeded defects, the research golden set) once B4.8 and B4.4 have built them (rule 30a; until then those roles read `not_measured`).
    - **Paired and repeated, in counterbalanced blocks:** at least **two runs per combination**, with fixed seeds (rule 10). Pairing is **by card** — combinations are compared only on cards both ran — but the cards run in **blocks**: all of one combination's cards for a run, then the next combination's, and on the second run the combinations in **reversed order** (A, B, C, then C, B, A). No two Workers co-reside on the 24 GB host ([models.md](models.md) rule 22), so card-by-card interleaving would need a model swap per card; blocks need **one swap per block**, and the reversed order balances any drift across the night. A difference the quick tier called indistinguishable is then resolved where the data allows, by the paired exact test at 0.05, per role and for the suite as a whole.
    - **An estimate before it starts:** from recorded throughput and load times — about two hours per full-suite run (the plan's *Machine time*), so one combination needs about **5 hours**: two suite runs, the planning measure and the role sets — how many hours the picked combinations need and how many fit tonight's window, after the night's backlog unless the person put the benchmark first. A 5-hour window fits one combination and a 10-hour window two (*3 combinations need about 15 hours; tonight's window, 01:00–06:00, fits one; all three finish on the third night*).
    - **It stops cleanly** at the window's end, keeping completed runs, and resumes the next night from where it stopped; it never runs inside reserved hours — **not even when the person is idle** (runtime's idle exception is for queue rounds only) — nor while a card is running ([models.md](models.md) rule 20b, MD-N3-4, MD-N3-5).
    - **Results:** one recorded `RunProfile` per combination and its paired results, as a `measure/benchmarked` event with `tier: "overnight"`. The morning brings a **report** — on the Configuration page and in Seshat's standup ([planner-pm.md](planner-pm.md)) — giving the ranking with intervals, which differences were **resolved** (*A is better than B on the Worker's cards*) and which are **still indistinguishable**, with the smallest difference the runs could have detected.
    - **It is the bake-off** that [models.md](models.md) rule 30a requires to change the recorded baseline or a shipped default; applying its winner, there or for a person's own use, is always a person's choice.

## 5. Changes for v1

### M9 — one measurement path

- **MS-M9-1** WHEN `m0`, the bake-off, the rule gate or the suite runs a card THE SYSTEM SHALL execute it through the product's card execution, and the rendered first prompt SHALL be byte-identical to the product's for the same card, build and settings.
- **MS-M9-2** WHEN a model adapter is wrapped for instrumentation THE SYSTEM SHALL expose `contextWindow`, `nativeTools` and `preferredToolArm` unchanged and meter cached prompt tokens.
- **MS-M9-3** WHEN the suite runs THE SYSTEM SHALL use the runner module in `packages/eval`, covered by tests of dependency blocking, acceptance of passing cards, timeout attribution and per-attempt token totals.
- **MS-M9-4** WHEN any measured run starts THE SYSTEM SHALL resolve one `RunProfile` from configuration and flags, write it into the run's evidence, and run with the roles and policies the product ships switched on unless the profile names an arm under test.
- **MS-M9-5** WHEN a flag would change the value of another setting THE SYSTEM SHALL refuse it; WHEN `--settings <file>` names a settings file THE SYSTEM SHALL record the file's content hash in the evidence. ([surface.md](surface.md) SUR-44/45 are the CLI layer's share of these two criteria: surface parses and refuses; this spec resolves, records and runs.)
- **MS-M9-6** WHEN a Worker is adopted or re-qualified THE SYSTEM SHALL run the M0 protocol through the one measurement path and record its valid-tool-call rate with an exact interval; WHEN the rate is below 70% THE SYSTEM SHALL record the pivot condition in `SUITE_RUNS.md`, show it on the Machine view and notify the owner, and SHALL NOT change the product's scope itself (rule 28a, [O20](../../reference/OPEN_QUESTIONS.md#owner-decisions)).

### M10 — mutation scores that cannot lie

- **MS-M10-1** WHEN the tests fail on the unmutated checkout THE SYSTEM SHALL refuse to score the campaign and report why.
- **MS-M10-2** WHEN a change has no mutable lines THE SYSTEM SHALL record the score as not applicable (`null`), not 1.
- **MS-M10-3** WHEN the changed files are in a language the campaign cannot mutate THE SYSTEM SHALL report the files as not measured.
- **MS-M10-4** WHEN the built-in mutation gate runs on a card ([gates.md](gates.md)) THE SYSTEM SHALL apply the same baseline rule.

### M12 — statistics that fit the sample

- **MS-M12-1** WHEN a suite run is summarised THE SYSTEM SHALL report passed / measured with a Clopper–Pearson 95% interval, and blocked cards as a separate count.
- **MS-M12-2** WHEN two runs are compared THE SYSTEM SHALL compare only cards run in both, report the discordant counts and an exact McNemar p-value, and state the smallest difference detectable at 80% power.
- **MS-M12-3** WHEN two runs differ by one task and the exact test is not significant THE SYSTEM SHALL NOT report "improved" (the current `suite.spec.ts:125` expectation is reversed).
- **MS-M12-4** WHEN a claim of an effect under 20 points is written from a 30-card comparison THE SYSTEM SHALL mark it "not established" in the summary.
- **MS-M12-5** WHEN repeated runs exist THE SYSTEM SHALL report pass@k and pass^k per card.

### T7 — paired, independent trials and the planning measure

- **MS-T7-1** WHEN a measured run starts THE SYSTEM SHALL keep the Worker model loaded until the run ends, and report load time separately.
- **MS-T7-2** WHEN a fixture card has a reference solution THE SYSTEM SHALL verify that the frozen tests fail on the seed and pass on the reference before any run uses it, and the reference SHALL be covered by the suite hash.
- **MS-T7-3** WHEN a single card is run in independent mode THE SYSTEM SHALL start it from a `main` that holds its predecessors' reference work, and its result SHALL not depend on any earlier card's outcome.
- **MS-T7-4** WHEN two arms are compared THE SYSTEM SHALL interleave them card by card with fixed seeds, and MAY stop early only under a sequential test whose error rate is stated.
- **MS-T7-5** WHEN the planning measure runs on a fixture THE SYSTEM SHALL report, per generated card, SPIDR shape, scope (files, lines), fail-at-seed, pass-on-reference and mutants killed; and, end to end, the share of held-out hand-written acceptance tests passing on the final `main`, next to — never merged into — the suite score.
- **MS-T7-6** WHEN the context pruner is evaluated THE SYSTEM SHALL compare it on the suite with structure-preserving random line dropping at the same token budget and record the result against register R3.

- **MS-T7-7** WHEN the planning measure runs THE SYSTEM SHALL also score **implicit-requirement recall**: the share of annotated unstated requirements in the golden set of briefs (at least 10 briefs, ReqElicitGym-style, T11) that end up in the accepted requirement graph, reported with an exact interval ([PROJECT_DONE_AND_DEPTH.md](../../research/PROJECT_DONE_AND_DEPTH.md) §3).
- **MS-T7-8** WHEN the planning measure runs THE SYSTEM SHALL score the **premature-completion rate**: the share of projects or slices the system marked proven that the held-out acceptance suite (T11), never shown to the planner, shows are not, reported with an exact interval ([PROJECT_DONE_AND_DEPTH.md](../../research/PROJECT_DONE_AND_DEPTH.md) §3).

### T8 — admission by the one rule: a significant paired gain for harness changes

*Built in B2.4, not left to B5's structure work: B2.5's evidence-gated-commit verdict ([worker-loop.md](worker-loop.md) rule 29a applies MS-T8-13), B4.0a's rule credit ([context.md](context.md) CX-N4-6 calls MS-T8-14) and the release gate's CX-N6-2 all read its verdicts (confirmation review N7b). The credit function reads `attempt/finished` records, which the loop starts writing only in B4.0a ([worker-loop.md](worker-loop.md) NEW-worker-loop-5, WL-N5-1): B2.4 builds it and tests it on **scripted** `attempt/finished` records, and it runs live from B4.0a (final check m-l).*

- **MS-T8-1** WHEN a harness change's candidate run passes the same number of tasks as the baseline THE SYSTEM SHALL NOT admit it as a gain.
- **MS-T8-2** WHEN a harness change is evaluated THE SYSTEM SHALL use at least two paired runs on the suite path with the suite hash checked, and admit it as a gain only if a one-sided exact test rejects "no gain" at 0.05 (the inconclusive case is MS-T8-13).
- **MS-T8-3** WHEN an admitted change is watched THE SYSTEM SHALL compare cards run with and without it (paired), and roll it back automatically, flagging it, when the paired comparison shows a drop; with no history, it SHALL NOT assume a baseline of 1.0.
- **MS-T8-4** WHEN an inlet is below its volume threshold THE SYSTEM SHALL report "insufficient data" and propose nothing; one struggle SHALL NOT create a rule in force.
- **MS-T8-5** WHEN a skill candidate is proposed THE SYSTEM SHALL run its own checks in the gate host's sandbox first and discard it if they fail.
- **MS-T8-6** WHEN a trajectory has an unclosed tool call or out-of-order events THE SYSTEM SHALL NOT admit it as an exemplar or a skill source.
- **MS-T8-7** WHEN a pre-filter score discards a proposal THE SYSTEM SHALL have calibrated it on at least `MIN_ARM_TRIALS` anchor pairs; below that, every proposal SHALL go to the suite.
- **MS-T8-8** WHEN the eval package is built THE SYSTEM SHALL contain no inlet function unreachable from a command (reachability check), each having been wired into one of the six inlets or cut as dead code under [DEC-09](../DECISIONS.md#dec-09) (the owner's rule that unreachable code is cut, which is the sign-off; §8 Q2).
- **MS-T8-9** WHEN an inlet records a signal THE SYSTEM SHALL tag it with its source and how it was verified, and an inlet SHALL NOT propose from signals that are all unverified model syntheses.
- **MS-T8-10** WHEN an admitted change is rolled back THE SYSTEM SHALL demote every generated test promoted because of it to advisory, and say so on each test's card.
- **MS-T8-11** WHEN `sekhemet tune` runs in a repository with fewer than `MIN_ARM_TRIALS` recorded attempts per class THE SYSTEM SHALL propose from the machine's global tuning report and label the proposal as inherited.
- **MS-T8-12** WHEN a task is synthesised from a fixing commit THE SYSTEM SHALL install its dependencies in an ephemeral worktree for that task, keep it only if the test fails on the commit before the fix and passes on the fix, and scrub file paths from its problem statement.
- **MS-T8-13** WHEN a harness change's paired A/B is inconclusive THE SYSTEM SHALL record it as adoptable only if (a) the paired pass-rate result is not a loss a one-sided exact test resolves at 0.05, and (b) either the change is **simpler** — computed from the change, not entered: stable-zone prompt tokens (Worker's tokenizer), tool count, switch count and lines of code each unchanged or lower, and at least one lower — or it is **cheaper** on median tokens per card, the cost measure recorded in the A/B's entry before its first card ran, by a one-sided paired Wilcoxon signed-rank test at 0.05 over the cards run in both arms; it SHALL write the verdict "not established — simpler" or "not established — cheaper" with the context version or harness commit and the smallest paired loss detectable at 80% power; in every other inconclusive case it SHALL record "not adopted". A scripted A/B whose candidate has a lower median but a Wilcoxon p above 0.05, and adds a switch, SHALL be recorded "not adopted"; an A/B entry whose cost measure was written after its first card SHALL be refused.
- **MS-T8-14** WHEN a rule's credit is needed THE SYSTEM SHALL compute it with one function in `packages/eval` from `attempt/finished` records alone — rotation membership, pairs of first attempts on comparable cards, helpful minus harmful over every pair since the rule came into force — and SHALL test it for harm only when its pair count first reaches 20, 40 and 80, retiring it when a one-sided exact binomial test on the discordant pairs gives P ≤ 0.05/3; below 20 pairs it SHALL report "insufficient data". Scripted tests: 20 pairs with 1 helpful and 9 harmful SHALL give credit −8 and retire the rule (P ≈ 0.011); 20 pairs with 2 helpful and 8 harmful SHALL give −6 and keep it (P ≈ 0.055); 19 pairs with 0 helpful and 10 harmful SHALL report "insufficient data" and keep it; and a rule whose 21st to 39th pairs are all harmful SHALL NOT be retired before its 40th pair.
- **MS-T8-15** WHEN a verified lesson is recorded during a production run and the owner has not allowed probation ([O15](../../reference/OPEN_QUESTIONS.md#owner-decisions)) THE SYSTEM SHALL record it as a candidate for a person's approval with its evidence and SHALL NOT apply it to any card before that approval; WHEN probation is allowed, a lesson's in-run credit SHALL be computed by the MS-T8-14 function over the pairs completed in the run, with no minimum.

*Justification:* the evidence cannot say which build produced it, the suite hash misses the card specs, and trials leak learned state into each other — a result must say what produced it.

- **MS-N1-4** WHEN a measured run executes THE SYSTEM SHALL use an isolated configuration directory, model registry and exemplar store, SHALL NOT make any rule or exemplar learned during the run available to a later card of the run, and SHALL record in each card's evidence the rules and exemplars it saw.

*Justification:* the doctor's playbook check is called with no outcomes, skills or cards, so net gain and context debt can never appear.

- **MS-TQ-2** WHEN the first blocking acceptance-test mutation threshold is proposed THE SYSTEM SHALL derive it from at least one planning-measure run and record it in the register with its date before any project uses it.
- **MS-TQ-3** WHEN mutation cost is benchmarked on the reference machine THE SYSTEM SHALL record seconds per mutant for acceptance-test-only runs and for suite runs separately.
- **MS-N4-1** WHEN a pass rate, a paired comparison, an inlet signal or a competence row is computed THE SYSTEM SHALL exclude attempts whose `builtBy.kind` is `person`, and the summary SHALL state how many were excluded.

### NEW-measurement-5 — comparing model combinations: the quick and overnight benchmarks

*Justification:* the owner's Configuration page ([DEC-29](../DECISIONS.md#dec-29--the-owners-answers-to-the-decision-queue) O2) runs "the benchmark" so a person can compare the models they have and mix and match one per role; the owner clarified that it must assess a **combination**, across their models up to the strongest their hardware runs, and must not take long. The frozen suite takes about two hours per model (rule 7, the plan's *Machine time*), so the page needs a screen built role by role, cached, compared paired item by item, and honest about how little 6 cards can tell apart (rule 35: on 6 cards only a model better on every card is separated); and the owner asked for a second, overnight tier that settles, unattended, what the screen cannot. *Readiness:* the Worker and Planner screens, the end-to-end check and the page are built in B4.1; the Reviewer's screen and overnight set with B4.8, the Researcher's with B4.4; until then those roles read `not_measured` (rule 30a).

- **MS-N5-1** WHEN a person starts a quick benchmark for a combination THE SYSTEM SHALL show, before loading any model, an estimate in minutes per role and per model including load time, computed from recorded throughput on this host (else the registry's figures), SHALL mark a Worker screen whose estimate exceeds 17 minutes, a Planner, Reviewer or Researcher screen whose estimate exceeds 5 minutes, an end-to-end check whose estimate exceeds 10 minutes, and a screen whose total exceeds 45 minutes (each including load), and SHALL run nothing until the person confirms.
- **MS-N5-2** WHEN a combination differs from an already screened one only in one role's model THE SYSTEM SHALL run only that role's screening set and the end-to-end check, reusing each other role's cached score whose key (model, quantisation, engine, settings, host, harness context version, screening-set hash) matches; a test that changes only the Reviewer SHALL observe no Worker, Planner or Researcher screening request.
- **MS-N5-3** WHEN a Worker screening card finishes or reaches its time cap (2 minutes by default) THE SYSTEM SHALL score it as the fraction of its acceptance tests passing at that moment (a card with 3 of 4 tests passing scores 0.75), SHALL stop a capped card with `time_budget_exhausted`, and SHALL report the number of cards that hit the cap beside the Worker's score; WHEN a Researcher answer is graded THE SYSTEM SHALL record 0, ½ or 1; a Planner brief SHALL be scored by its recall and a Reviewer defect by 1 if detected at its location, else 0.
- **MS-N5-4** WHEN two candidates for a role are compared THE SYSTEM SHALL compare them on the same items by an exact two-sided sign test on the per-item differences, ties set aside, and SHALL label them "indistinguishable on the quick benchmark" and NOT order them when the test does not reject at 0.05; scripted cases: two Workers where one scores higher on all 6 cards SHALL be ordered (p ≈ 0.031), one higher on 5 cards with 1 tie SHALL be indistinguishable (p ≈ 0.063), and two Researchers SHALL be indistinguishable even at 5 answers to 0. No quick-tier comparison SHALL use interval overlap.
- **MS-N5-4a** WHEN role scores are shown THE SYSTEM SHALL show beside each score its secondary measures — seconds per card or item, the valid tool-call rate, steps to pass, and whether the model fits — and the page SHALL state that the quick tier resolves speed, fit and large differences in correctness, and the overnight tier close calls.
- **MS-N5-4b** WHEN a role's workstream has not built its screening set (the Reviewer's before B4.8, the Researcher's before B4.4) THE SYSTEM SHALL show that role's score as `not_measured`, SHALL leave the role out of every comparison and say so, and SHALL NOT score it on a partial set (MS-T11-7).
- **MS-N5-5** WHEN a candidate model does not fit the host by [models.md](models.md)'s memory plan THE SYSTEM SHALL list it as "needs N GB" and SHALL NOT load or run it; WHEN a combination's models cannot co-reside THE SYSTEM SHALL show its swap cost in seconds per role switch before the run.
- **MS-N5-6** WHEN a person stops a screen THE SYSTEM SHALL stop at the current card's end or its cap, whichever is first, keep and cache every completed role's score, and record the screen as partial.
- **MS-N5-7** WHEN a combination is screened THE SYSTEM SHALL run 2 cards, each capped at 3 minutes, through its Planner, Worker and Reviewer and report each card's outcome beside the role scores, never folded into them.
- **MS-N5-8** WHEN a screen ends, completed or partial THE SYSTEM SHALL append one `measure/benchmarked` event with `tier: "quick"`, its `RunProfile`, scores, intervals, cache keys and screening-set hashes; WHEN DEC-28 admission, qualification or a change to the recorded baseline or a shipped default is computed THE SYSTEM SHALL NOT read quick-tier results (a search test finds no such reader).
- **MS-N5-9** WHEN a person schedules an overnight benchmark THE SYSTEM SHALL show, before it is queued, the hours the picked combinations need, how many fit tonight's overnight window — from recorded throughput and load times, after the night's backlog unless the person put the benchmark first — and on which night it would finish (with about 5 hours per combination, a 5-hour window SHALL be shown as fitting one combination and a 10-hour window two); WHEN the person picks none THE SYSTEM SHALL default to the top combinations the quick tier could not separate, at most 3.
- **MS-N5-10** WHEN an overnight benchmark runs THE SYSTEM SHALL run each combination at least twice with fixed seeds on the full frozen suite, and once on the planning measure and on the Reviewer's and Researcher's full evaluation sets where those are built (else `not_measured`), in counterbalanced blocks — all of one combination's cards for a run, then the next combination's, the order reversed on the second run — with one model swap per block and none within one; and SHALL compare combinations only on cards run by both, by the paired exact test at 0.05. A scripted run of three combinations SHALL run in the order A, B, C, C, B, A and record exactly one Worker swap per block boundary.
- **MS-N5-11** WHEN an overnight benchmark ends or stops at the window's end THE SYSTEM SHALL append one `measure/benchmarked` event per combination with `tier: "overnight"` and its `RunProfile`, and SHALL produce a morning report — on the Configuration page and in Seshat's next standup — that ranks the combinations with their intervals and names, per pair and per role, which differences were resolved and which are still indistinguishable, with the smallest difference detectable at 80% power; it SHALL NOT assign any combination.
- **MS-N5-12** WHEN the overnight window ends mid-run, or a person reserves the machine THE SYSTEM SHALL stop as [models.md](models.md) MD-N3-5 requires, keep every completed run, and resume the next night from where it stopped; WHEN the machine is reserved or a card is running THE SYSTEM SHALL NOT start it, even when the person has been idle inside reserved hours (MD-N3-4).

*[models.md](models.md) owns the change (NEW-models-14, [DEC-45](../DECISIONS.md#dec-45--smart-swap)); this spec owns how its parameters are admitted and calibrated (rules 16a, 16d). Workstream: B4.0a part 3 for MS-NM14-1–3; B4.1 for MS-NM14-4, with the placement action. Each is tested with recorded fixture days, fake adapters and a fake clock, loading no model.*

- **MS-NM14-3** WHEN a measurement run (the frozen suite, a bake-off, an A/B, qualification) ends THE SYSTEM SHALL unload its models; WHEN a calibration night starts THE SYSTEM SHALL record its protocol in one `measure/calibration` event before the first load, SHALL check DEC-42's host limits before each load, SHALL run `decide()` as designed with every load recorded, SHALL NOT start while a suite or measurement run holds the runner, and SHALL unload everything at its end.

- **MS-NM14-4** WHEN a placement gain is shown THE SYSTEM SHALL show it as *measured* only from at least three recorded cold loads of the same weights on each volume, as the difference of the medians, and otherwise as an estimate from the volumes' probed read rates.

## 7. Later

- **Calibrating against published systems** by fitting an item-response model to the public per-instance SWE-bench results (~10⁵ outcomes), so difficulty is on a published scale. Limits that bind it: the data is Python-heavy and concentrated in few repositories, so it calibrates a scale, never ranks TypeScript work; and success is dominated by the scaffold (16.7% vs 47.9% on the same instances), so nothing about routing or models may be fitted from it.
