# Design research: roles, the AI as a teammate, and team collaboration

*Web research, 2026-09-24. Question: what do professional teams expect from roles, collaboration, sign-in, shared inference and status reporting, and how should an AI PM (Seshat) and an AI Agent join a human team without directing it? Scope: a solo non-coder, and a team sharing one install on its own hardware. This builds on [DESIGN_RESEARCH_TEAMS_DATA_CHANGE.md](DESIGN_RESEARCH_TEAMS_DATA_CHANGE.md) §2.1 (owner and delegate, CODEOWNERS routing, independent accept) and [DESIGN_RESEARCH_TEAM_SERVER.md](DESIGN_RESEARCH_TEAM_SERVER.md) (engine adapter, fair share, interactive-first, aging), and does not repeat them. It bears on [DEC-06](../design/DECISIONS.md#dec-06), which limits v1 to one permission beyond reading.*

**How to read the sources.** Claims were read on the primary page on 2026-09-24 unless marked **[search]** (from a search summary; primary page not opened). Nothing here enters the product without the owner's yes.

## Summary

- Trackers converge on four tiers: **admin**, **member**, a **limited contributor** (GitHub *Triage*, Azure *Stakeholder*) and a **viewer**. Job titles are never roles. Approval is a **rule on the work** (required reviewers, code owners), not a role.
- Every agent integration studied keeps a human accountable, invokes the agent with ordinary verbs (delegate, @mention), shows its state, stops it on request, and attributes its work to the person who started it.
- Non-bossy AI means **proposals a person accepts, with the reason shown**, one-click dismissal, calm plain wording, and never assigning work to people.
- Good self-hosted sign-in: a one-time admin setup, invited or pending accounts, strict OIDC role mapping, proxy headers trusted only from allow-listed addresses, and NIST and OWASP rules for passwords and sessions.
- Stakeholders want a human-set **On track / At risk / Off track**, a short weekly update and a burn-up with a **forecast range**. Engineers want flow measures, a cycle-time scatter and cumulative flow.

## 1. Roles and permissions

| Tool | Roles | What stands out |
| --- | --- | --- |
| Jira (team-managed space) | Administrator, Member, Viewer; custom roles allowed; the three defaults cannot be deleted | Space access is *Open* (everyone a Member), *Limited* (everyone a Viewer who can view and comment) or *Private* ([Atlassian](https://support.atlassian.com/jira-software-cloud/docs/manage-how-people-access-your-team-managed-project/)). Viewer needs no extra app licence [search] |
| Linear | Workspace Owner (Enterprise), Admin, Member, Guest (Business+); Team Owner per team | On Free, everyone is an admin; Guests see only the teams they are added to ([Linear](https://linear.app/docs/members-roles)) |
| GitHub repository | Read, Triage, Write, Maintain, Admin | *Triage* manages issues, labels and assignment without push or merge; *Maintain* manages settings without destructive actions ([GitHub](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)) |
| Azure DevOps | Access levels Stakeholder / Basic; groups Readers, Contributors, Project Administrators | Stakeholders are free and unlimited. They can create and edit work items and drag status on a board, but cannot reorder a backlog, see code or edit dashboards ([Microsoft](https://learn.microsoft.com/en-us/azure/devops/organizations/security/stakeholder-access)). A Deny generally overrides an Allow ([Microsoft](https://learn.microsoft.com/en-us/azure/devops/organizations/security/about-permissions)) |
| Shortcut | Owner, Admin, Member, Observer | Observers see everything, change nothing, and are not billed; Free has only Admin [search] ([Shortcut help](https://help.shortcut.com/hc/en-us/articles/360033599771-Managing-User-Roles)) |

- *Implication:* the minimum set small teams already know is **Admin, Member, Viewer** (Jira's defaults). The one tier worth adding is a limited contributor, Azure's *Stakeholder*: a person who files and discusses issues but does not build, merge or configure. That is the non-developer who talks to the PM.
- *Implication:* reading is cheap to grant everywhere (free viewers and observers). Approval rights are never a role. They come from branch rules and code owners (companion doc, decisions 3–4).

## 2. AI agents as teammates

- **Linear.** Agents are admin-installed app users without a paid seat. Assigning to an app makes it the **delegate**, not the assignee. On invocation the agent should post a `thought` activity **within 10 seconds** ([Linear developers](https://linear.app/developers/agents)). Linear's Agent Interaction Guidelines have six rules: disclose that it is an agent; work through the platform's native actions; acknowledge at once; show internal state (thinking, awaiting input, executing, done); stop when asked and resume only when re-engaged; and final responsibility stays with a human ([Linear AIG](https://linear.app/developers/aig)).
- **Jira / Rovo.** Agents act inside Jira's existing permissions and approval workflows. Approved agent updates enter the work item's history ([Atlassian HITL guide](https://www.atlassian.com/software/jira/guides/agentic-engineering/human-in-the-loop)). That guide names three patterns: **approval** before irreversible actions, **review** of output before it ships, and **escalation** to a person when context is missing. Its framing is that oversight belongs in the workflow, not in a separate tool. In "governed agent loops" (2026-09-10), agents take unassigned work to a pull request, an AI review runs before the human review, and developers keep the merge button ([Atlassian blog](https://www.atlassian.com/blog/jira/governed-agent-loops)). The person who adds an agent controls it, and its output stays private until shared (companion doc §2.1).
- **GitHub Copilot cloud agent.** Only users with write access can trigger it. It pushes to one branch. Its commits list the requester as **co-author**, and each commit links to the session log. The requester **cannot approve** the pull request. Workflows wait for a person to approve them. It cannot mark its own PR ready ([GitHub](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). People steer it with `@copilot` comments ([GitHub](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)).
- **Devin and Cursor.** Both start from delegation or an @mention (Devin also from playbook labels). Devin streams its plan and edits into Linear and attributes each session to the person who started it ([Devin](https://docs.devin.ai/integrations/linear); [Cursor](https://cursor.com/docs/integrations/linear) [search]).
- **GitLab Duo agents and flows.** Each agent has its own avatar and handle. Sessions show *running*, *awaiting input*, *paused* or *completed* in four places: the activity timeline, the sessions panel, an indicator on the work item, and notifications. Input requests offer Approve / Deny / Modify. The log records who triggered each session ([GitLab Pajamas](https://design.gitlab.com/patterns/duo-agents-and-flows/)).

*Implication:* the shared rules: a human is accountable; the agent is visibly an agent, invoked with ordinary verbs; it acknowledges at once, shows its state where the work is, and stops on request; and the person who triggered it is recorded and, on GitHub, cannot approve the result.

## 3. AI that assists rather than directs

- **Microsoft HAX** (18 guidelines, CHI 2019, evaluated with 49 practitioners) ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/); [list](https://www.microsoft.com/en-us/haxtoolkit/library/)). Most relevant: G2 (show how well it works), G5 (match social norms), G8 (easy dismissal), G9 (easy correction), G10 (narrow scope when in doubt), G11 (explain why), G16 (show consequences), G17 (global controls).
- **Google PAIR.** People should keep control of tasks they value, feel responsible for, or see as high-stakes. Let them opt out and respect the choice. Keep a manual path ([PAIR, feedback and controls](https://pair.withgoogle.com/chapter/feedback-controls/)). Show confidence as categories or as alternatives, not raw percentages. The aim is that people know when to use their own judgement ([PAIR, explainability and trust](https://pair.withgoogle.com/chapter/explainability-trust/)).
- **GitLab Pajamas.** The AI suggests and the user decides. High-risk actions need opt-in and a review step before they run. Descriptive UI uses the third person; an agent's own replies use the first person. Generated content is labelled, with one verification notice per context ([Pajamas](https://design.gitlab.com/usability/ai-human-interaction)).
- **Atlassian Rovo voice.** Rovo aims to be trustworthy, insightful and collaborative. It leads with the answer and states its confidence and limits. It avoids filler openers, over-eager or promotional wording, and false reassurance ([Atlassian Design](https://atlassian.design/rovo-ui/voice-and-tone)). Atlassian's general guidance lowers boldness for new or anxious users ([Atlassian Design](https://atlassian.design/foundations/content/voice-tone)).
- **Linear Triage Intelligence.** It suggests team, project, assignee, labels and duplicates. Each suggestion shows its reason on hover and can be accepted or dismissed. Only a team admin can set a property to auto-apply ([Linear](https://linear.app/docs/triage-intelligence)).
- **Reactance.** Greater AI autonomy is associated with a felt threat to freedom ([JBEM 2025](https://www.tandfonline.com/doi/full/10.1080/08838151.2025.2485319) [search]). This is one study and is read here only as direction.

*Implication:* the AI's authority should come only from evidence and the person's own settings. Scope, priority, assignment and acceptance stay with people. Every AI output that would change shared state is a proposal, with its reason and a one-step dismissal.

## 4. Collaboration mechanics teams expect

- **Subscriptions.** Linear and GitHub subscribe you automatically when you create an issue, are assigned it, are mentioned in it or comment on it. GitHub labels each notification with its *reason* (`mention`, `review requested`, `assigned`) and can filter by reason ([GitHub](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications); [Linear](https://linear.app/docs/inbox)).
- **Inbox triage.** GitHub has Done and Saved, and unsaved items expire after three months. Linear has mark read, snooze, reminders and a Priority tab ([Linear](https://linear.app/docs/inbox)). Linear's email digests batch by urgency and are sent only if the item is still unread in the inbox ([Linear](https://linear.app/docs/notifications)).
- **Watch versus mention.** A watcher gets the full lifecycle; a mention is a single targeted ping. Atlassian advises watching sparingly because of notification volume ([Atlassian](https://www.atlassian.com/blog/jira/using-watchers-and-mentions-effectively)).
- **Presence.** Jira shows who is online in board, list and timeline views, and which card someone is editing or dragging [search] ([Atlassian](https://support.atlassian.com/jira-work-management/docs/collaborate-in-real-time/)).
- **Reviews and approvals.** GitHub offers three review verdicts: Comment, Approve, Request changes ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)). Rulesets add a required approval count, dismissal of stale approvals on a new push, code-owner review, approval from someone other than the last pusher, and resolved conversations before merge ([GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
- **Audit log.** Each entry records the actor, action, target, time and country. Only owners can see it; it keeps 180 days and exports to JSON or CSV ([GitHub](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization)). Jira's audit log records who changed configuration and who deleted what [search] ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/audit-activities-in-jira-applications/)).

*Implication:* the ledger already holds the audit data. What is missing is the reading side: an inbox with reasons, subscription rules, a watch/mention split, presence, and GitHub's three review verdicts.

## 5. Sign-in on the team's own hardware, and sharing one model

**Accounts and first run**
- **Open WebUI** is the closest analogue, a self-hosted multi-user LLM front end. The first account becomes admin. New sign-ups default to **pending**, which has no access until an admin promotes them ([Open WebUI](https://docs.openwebui.com/features/authentication-access/rbac/roles/)). Two failure modes: with OIDC, the first account is *not* made admin ([issue #3496](https://github.com/open-webui/open-webui/issues/3496) [search]); and an OIDC role claim resets a manual promotion at each login [search]. It supports SCIM provisioning ([Open WebUI SSO](https://docs.openwebui.com/features/authentication-access/auth/sso/) [search]).
- **Proxy header trust.** Grafana trusts `X-WEBAUTH-USER` only from allow-listed proxy addresses and can create users on first sight. It warns that an empty groups header removes the user from all teams ([Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/auth-proxy/)). Gitea leaves CSRF protection to the proxy when header auth is used ([Gitea](https://docs.gitea.com/administration/authentication)).
- **OIDC role mapping.** Grafana maps a claim to a role with `role_attribute_path`. `role_attribute_strict` denies login when no valid role is found. It also supports PKCE and an allowed-domains list ([Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/generic-oauth/)).
- **NIST SP 800-63B-4** ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)): passwords at least 15 characters when used alone and 8 with MFA; no composition rules and no forced rotation; check against a blocklist. Syncable passkeys are allowed at AAL2 but not AAL3. At AAL2, reauthenticate after at most 24 hours overall and 1 hour idle.
- **OWASP sessions** ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)): `__Host-` cookies with Secure, HttpOnly and SameSite; at least 64 bits of entropy; a new session ID at login and on any privilege change; idle and absolute timeouts enforced on the server; log session events.
- **SCIM 2.0** (RFC 7643/7644) lets an identity provider create, update and deactivate users through `/Users` and `/Groups` [search] ([Clerk guide](https://clerk.com/articles/scim-2-0-explained-a-practical-guide-for-saas-auth)).
- **Libraries** (GitHub API, 2026-09-24; all MIT, all pushed this month): SimpleWebAuthn, `openid-client`, oauth2-proxy.

**Sharing one inference server**
- **llama.cpp** serves concurrent users through `--parallel` slots. The context size is **split equally across slots**, and requests queue in memory when all slots are busy ([llama.cpp discussion, 2026-06-10](https://github.com/ggml-org/llama.cpp/discussions/24401)).
- **vLLM** schedules `fcfs` or `priority`; a lower value runs first and arrival order breaks ties. `max_num_seqs` (default 128) caps concurrency ([vLLM](https://docs.vllm.ai/en/latest/api/vllm/config/scheduler/)). Higher-priority requests preempt running ones [search].
- **VTC** (OSDI 2024) measures fairness by the cost of input and output tokens served per client. It proves a 2× bound on the service gap between backlogged clients while never leaving capacity idle. Plain rate limits waste capacity when load is light ([arXiv 2401.00588](https://arxiv.org/abs/2401.00588)).
- **LiteLLM**, a gateway, sets per-user `max_parallel_requests` and tokens- and requests-per-minute limits, and can reserve a share of capacity for a priority level [search] ([LiteLLM](https://docs.litellm.ai/docs/proxy/users)).

*Implication:* fairness belongs in Sekhemet's own queue, keyed by person and costed in tokens, because llama.cpp has no per-user notion and vLLM's priority is per request. A per-person cap on concurrent agent issues keeps one person's backlog from taking every slot.

## 6. Status for stakeholders and for engineers

- **Kanban Guide (v2025.5)** requires four measures: WIP, throughput, work item age and cycle time. It also requires a Service Level Expectation, a time with a probability (for example 85% within eight days), taken from past cycle times and shown on the board ([Kanban Guide](https://kanbanguides.org/the-kanban-guide/)).
- **Monte Carlo forecasting** answers two questions: *when will these N items be done* and *how many will be done by a date*. It samples past throughput and reports percentiles (50/70/85/95) ([Nave](https://getnave.com/blog/monte-carlo-simulation-explained/), vendor). It assumes a stable system, uses throughput not cycle time, is re-run as work progresses, and is best stated as trade-offs ([ProKanban, 2025-06-30](https://www.prokanban.org/blog/trustingmcs)). The sources disagree on data needed (Nave: 20–30 items; ProKanban: far fewer).
- **Linear's project graph** plots scope (grey line), started and completed work, and a projected completion date from weekly velocity once there is enough history. A set target date appears as a red line ([Linear](https://linear.app/docs/project-graph) [search]). **Project updates** carry On track / At risk / Off track and are posted by the lead, with scheduled reminders. After one missed cycle plus three days the project shows *Update missing*, and the health icon turns grey as it ages ([Linear](https://linear.app/docs/initiative-and-project-updates)).
- **Atlassian's weekly update** has five parts: status colour, what happened, what's next, risks or blockers, and asks. It should open with a tight headline and 1–3 sentences ([Atlassian playbook](https://www.atlassian.com/team-playbook/plays/weekly-project-updates)). In Atlassian Home, projects update weekly and goals monthly [search].
- **Azure DevOps** offers release burndown and burnup (with scope creep), cumulative flow, cycle and lead time control charts and velocity, all viewable by Stakeholders ([Microsoft](https://learn.microsoft.com/en-us/azure/devops/report/dashboards/analytics-widgets)). Jira has a cycle-time scatterplot, a CFD and a control chart ([Atlassian](https://support.atlassian.com/jira-software-cloud/docs/view-and-understand-your-cycle-time-report/)).
- **DORA** now has five metrics (lead time, deployment frequency, recovery time, change fail rate, rework rate). It warns against making them targets or comparing teams ([DORA](https://dora.dev/guides/dora-metrics/)).

*Implication:* stakeholders trust a **person's** health call backed by a burn-up with a range. Engineers trust flow charts. Neither group expects leaderboards of people, and DORA advises against them.

## Recommendations for Sekhemet

Each recommendation names its findings. Those that go beyond DEC-06 need the owner's decision.

1. **Role set: four permission tiers, with job titles as labels only** (§1). **Admin** (settings, members, models, the inference queue), **Member** (create, edit and move issues; start and guide the Agent; review), **Stakeholder** (create and comment on issues, talk to Seshat, answer questions addressed to them; cannot start the Agent, change scope or priority, or accept) and **Viewer** (read and comment; free to add). Product owner, developer, reviewer and researcher are profile labels that set a person's home view and notification defaults, never permissions. **Accept** stays a per-project rule, not a role: who may accept, required code-owner accepters, and the independence rule (companion doc, decisions 3–4). On a single machine the tiers are hidden and the one person holds all of them. *Reopens DEC-06 ("roles beyond that" are out of v1): owner decision.*
2. **AI-as-teammate rules** (§2). (a) The Agent is only ever a **delegate**; the issue always has a human owner. (b) The Agent and Seshat appear as labelled app identities with an "AI" badge, never as members, and never take a seat or a role. (c) They are invoked the way people are: assign to Agent, `@Agent` or `@Seshat` in a comment. (d) They acknowledge within seconds and show one of *queued / working / needs you / paused / done / failed* on the tile, the issue and the inbox. (e) *Stop* takes effect at the next step boundary, and nothing resumes without a person re-engaging it (DEC-34). (f) Every Agent action records the person who started it, and the Agent never has more permission than that person. (g) On a server, the person who started an Agent run is not an independent accepter (GitHub's rule).
3. **Seshat facilitates; it does not manage** (§2, §3). Seshat never assigns work to a person, changes another person's issue, or sets a project's health. For triage (assignee, labels, duplicates, priority, a split) it posts **suggestions with a reason**, each accepted or dismissed in one action, as Linear's Triage Intelligence does. Only an Admin can turn on auto-apply, per property. Reminders ("update due", "3 issues waiting for review") come from the product in neutral system text, not in Seshat's voice, and go to the owner of the item.
4. **Language rules** (§3), for Seshat's and the Agent's text and for the UI's text about them:

   | Do | Don't |
   | --- | --- |
   | "Suggested: split into 2 issues. Why: two acceptance criteria touch separate files." [Split] [Dismiss] | "You should split this issue." |
   | "Needs a decision from Priya: keep the old API? Default if no answer by Friday: keep it." | "Priya must decide by Friday." |
   | "The checks failed on 2 of 5 criteria. Details" | "You broke the build." |
   | "I'm not sure this matches the brief (low confidence). Two readings: A, B." | A single confident answer with no alternatives when evidence is thin |
   | Lead with the answer, then the evidence | "Great question! I'd be happy to help…", false cheer, exclamation marks |
   | Name the owner of the decision: "Your call" / "The owner decides" | "I've decided", "I've assigned", "I approved" |
   | Third person in the UI ("Ask the Agent to…"); first person only in the AI's own replies | Personality, feelings or a human persona (*Seshat* is a product name, as DEC-31 allows) |

   Show **why** on every proposal (HAX G11); dismissal is one click with no follow-up nag (G8); offer alternatives, not percentages, when unsure (PAIR); be plainer and less bold with beginners (Atlassian).
5. **Collaboration mechanics** (§4). (a) Automatic subscription on create, assign, mention, comment and review request; a *Watch* toggle; mention and watch kept separate. (b) An **Inbox** grouped by reason (*Needs you*, *Mentioned*, *Review requested*, *Watching*, *Agent finished*), with Done, Snooze and Save. Email or chat digests go out only for items still unread, under the existing notification budget. (c) Review verdicts that mirror GitHub's: *Accept*, *Send back* (with line comments) and *Comment*. An accept is dismissed when new commits land. Unresolved threads block accept when the project requires it. (d) Light presence: avatars of who is viewing an issue, and a marker on a card someone is editing or dragging. (e) An Admin-only **Audit** view over the ledger (actor, action, target, time), exportable, including every role change, sign-in and model change.
6. **Sign-in: none for one person, proper accounts for a team** (§5). *Solo:* bind to loopback, no login, no roles UI. The OS user is the one principal. *Team:* (a) first run prints a **one-time setup token** to the server console; presenting it creates the Admin (avoiding "first sign-up wins" and Open WebUI's OIDC gap). (b) New people join by **single-use, expiring invite links** that carry a preset tier. Open sign-up is off by default, and when turned on, new accounts are *pending*. (c) Local accounts sign in with a **passkey** (SimpleWebAuthn, a proposal), with a password as fallback under NIST rules (15+ characters alone, no composition rules, no rotation, blocklist). (d) **OIDC** (`openid-client`, a proposal) with PKCE, claim-to-tier mapping and strict mode. A tier set in Sekhemet is not silently overwritten unless the Admin chose IdP-managed tiers. (e) The trusted-header proxy from DEC-06 is accepted only from allow-listed addresses, with CSRF enforced by Sekhemet itself. (f) Sessions follow OWASP: `__Host-` cookie, new ID at login and on tier change, 1-hour idle and 24-hour absolute limits. (g) SCIM is Later: one team on one server can live with invites and OIDC.
7. **Sharing the model fairly** (§5, extending the team-server doc). The harness's queue, not the engine, owns fairness: (a) fair share per person, costed in **input and output tokens** (VTC), not in request counts; (b) Seshat's interactive replies ahead of Agent steps, with aging (already proposed); (c) an Admin-set **per-person cap on concurrent Agent issues** (default 1 per person until slots allow more); (d) the slot count comes from qualification, and on llama.cpp the per-slot context is the total divided by the slots, so adding slots can shrink the context a card needs; (e) people can see where they are: "2nd in queue, about 6 minutes", and "Priya's issue is running; yours starts next". Map priority onto vLLM's `priority` field when that engine is used.
8. **Status: one page per audience, same data** (§6).
   - *Stakeholders and viewers:* the release's **health** (On track / At risk / Off track), **set by the project lead**. Seshat drafts the weekly update in the five-part format (status, done, next, risks, asks), and a person edits and posts it. Show *Update missing* when it is late. Add a **release burn-up** with a grey scope line and a **forecast range** (50% and 85% dates by Monte Carlo on issue throughput), "not enough history yet" below a minimum count, and the target date as a line. Also: requirements done ("5 of 11"), blocked issues and open decisions with their owners, and scope added or removed since the last update.
   - *Engineers:* cumulative flow; a cycle-time scatter with the 85th-percentile line as the team's SLE; work item age on the board; weekly throughput; review queue and ReviewWIP; checks pass rate. Add an **Agent vs person** split as a filter, not as a separate chart.
   - *Never:* per-person velocity, leaderboards, Agent-vs-human rankings, DORA numbers as targets, or a forecast shown as a single date.

### For the owner

Recommendations 1 (tiers beyond DEC-06), 3 (Seshat never assigns people) and 6(c)–(d) (passkeys and OIDC in v1, with two libraries to approve) need a yes. The rest refine specs already planned: integrations (inbox), dashboard (status pages), runtime (queue) and security (sessions).
